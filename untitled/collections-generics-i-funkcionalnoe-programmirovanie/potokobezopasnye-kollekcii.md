# Потокобезопасные коллекции

Представим сервис доставки. Пользователи оформляют заказы, рестораны подтверждают их, курьеры обновляют статусы. Приложение должно обрабатывать много таких действий, не дожидаясь полного завершения каждого предыдущего.

Для этого программа может использовать несколько **потоков выполнения**.

Поток выполнения — это отдельная последовательность выполняемых инструкций. Например, один поток обрабатывает оформление заказа одного пользователя, а другой — обновление статуса доставки другого. Их действия могут выполняться параллельно.

Проблема возникает, когда разные потоки обращаются к **одному и тому же объекту коллекции**. Например, один добавляет заказ в список, пока другой перебирает тот же список.

Обычные `ArrayList`, `HashMap` и `HashSet` не рассчитаны на такое совместное использование с изменениями без дополнительной защиты.

> **Потокобезопасные коллекции** предназначены для совместного использования несколькими потоками. Они сами обеспечивают необходимое согласование своих операций.

Большинство рассматриваемых классов находится в пакете `java.util.concurrent`. Пока нам достаточно понимать их назначение и поведение; способы создания потоков и внутренние механизмы согласования будут разобраны в другом модуле.

***

## Copy-On-Write

В сервисе доставки есть список способов уведомления клиента: например, `PUSH` и `EMAIL`.

При каждом изменении статуса заказа приложение перебирает этот список и отправляет уведомления по всем доступным каналам. Сам список меняется редко: иногда администратор подключает новый способ уведомления или отключает старый.

Получается, что **чтений много, а изменений мало**.

Если изменять тот же массив, по которому прямо сейчас идёт обход, придётся согласовывать работу читающего и изменяющего потоков. Другой подход — оставить используемый массив в покое, а изменение выполнить в новой копии.

Именно на этой идее основан **Copy-On-Write — «копирование при записи»**.

***

`CopyOnWriteArrayList` хранит элементы в массиве. Рассмотрим добавление нового элемента:

1. Текущий массив содержит `PUSH`, `EMAIL`
2. В памяти создаётся новый массив, куда копируются существующие элементы и добавляется `SMS`
3. Переменная в коллекции переключается со старого на новый массив
4. Уже созданные итераторы продолжают читать старый массив

**Итератор** — объект, который последовательно обходит элементы коллекции. Цикл `for-each` тоже использует итератор.

У `CopyOnWriteArrayList` итератор работает со **снимком массива на момент создания** — он сохраняет ссылку на существующую версию и работает в памяти со старым массивом. Последующие добавления, удаления и замены элементов не меняют этот снимок, потому что они происходят уже в другой области памяти, в копии массива.

Это поведение можно увидеть даже без запуска нескольких потоков:

```java
CopyOnWriteArrayList<String> channels = new CopyOnWriteArrayList<>();

channels.add("PUSH");
channels.add("EMAIL");

for (String channel : channels) {
    System.out.println(channel);

    if (channel.equals("PUSH")) {
        channels.add("SMS");
        channels.remove("EMAIL");
    }
}

System.out.println(channels);
```

Вывод:

```
PUSH
EMAIL
[PUSH, SMS]
```

По шагам:

1.  Перед началом цикла итератор находит по ссылке старый массив с `PUSH` и `EMAIL`.

    <figure><img src="../.gitbook/assets/image (9).png" alt=""><figcaption></figcaption></figure>
2. После вывода `PUSH` мы изменяем сам список, но при этом создается копия массива в другом участке памяти, и изменения происходят в ней.
3.  Ссылка в коллекции `channels` переключается на новый массив, но итератор за этим не следит, он продолжает работать со старым массивом по ссылке, которая была активна на момент начала цикла.

    <figure><img src="../.gitbook/assets/image (10).png" alt=""><figcaption></figcaption></figure>
4. Итератор продолжает обход своего старого массива, который не изменился, поэтому выводит `EMAIL`.
5. Последний `println()` смотрит уже на текущую ссылку в коллекции и находит по ней уже новый массив: `PUSH` и `SMS`.

**Новый обход увидит новое состояние, а уже начатый спокойно завершится по старому.**

Изменение настроек способов уведомления не сломает уже начавшуюся рассылку.

***

#### Цена копирования

Так как при добавлении нового элемента полностью копируется массив, добавление требует работы порядка `O(n)`, где `n` — размер списка. Также нужна память для нового массива. Старый массив остаётся нужен, пока его используют старые итераторы.

Для небольшого списка настроек это может быть приемлемо. Для большого списка, в который постоянно добавляются новые элементы — дорого. Например, хранить список всех заказов таким образом было бы неэффективно.

> Copy-On-Write подходит, когда чтений значительно больше, чем изменений.

## `CopyOnWriteArraySet`

В списке способов уведомления дубли не нужны, поэтому подходит `CopyOnWriteArraySet`:

```java
Set<String> channels = new CopyOnWriteArraySet<>();

System.out.println(channels.add("PUSH")); // true
System.out.println(channels.add("EMAIL")); // true
System.out.println(channels.add("EMAIL")); // false

System.out.println(channels); // [PUSH, EMAIL]
```

Внутри `CopyOnWriteArraySet` использует `CopyOnWriteArrayList`.

Уникальность проверяется через поиск элемента с использованием `equals()`. **Хеш-таблицы здесь нет**: чтобы определить наличие элемента, может потребоваться перебрать весь массив. Поэтому `contains()` имеет линейную сложность `O(n)` по количеству сравнений.

## `ConcurrentHashMap`

Для статусов заказов нужен другой характер работы: значения постоянно читаются, добавляются и обновляются. Копировать весь `Map` при каждом изменении было бы дорого. Для такой задачи предусмотрен `ConcurrentHashMap` — потокобезопасная хеш-таблица.

Работа с ней выглядит аналогично:

```java
Map<Long, String> statuses = new ConcurrentHashMap<>();

statuses.put(10L, "Принят");
statuses.put(20L, "Готовится");

statuses.put(10L, "Передан курьеру");

System.out.println(statuses.get(10L)); // Передан курьеру
```

У `ConcurrentHashMap`:

* порядок не гарантируется;
* `null` запрещён и для ключей, и для значений;
* так как данные не копируются, в отличие от Copy-On-Write мы можем в цикле увидеть изменения, которых не было на момент его начала.

***

Допустим, два курьера почти одновременно нажали **«Взять заказ»**. Нужно назначить заказ только одному из них. В `Map` храним номер заказа и ID назначенного курьера:

```java
ConcurrentHashMap<Long, Long> assignedCouriers = new ConcurrentHashMap<>();
```

Если записи нет, заказ пока свободен. Попробуем сначала проверить наличие записи, а затем добавить её:

```java
if (!assignedCouriers.containsKey(orderId)) {
    assignedCouriers.put(orderId, courierId);
    System.out.println("Заказ назначен вам");
}
```

На первый взгляд, код выглядит правильно, но на самом деле возможна проблема:

<figure><img src="../.gitbook/assets/image (8).png" alt="" width="563"><figcaption></figcaption></figure>

Оба курьера увидели, что операция успешно выполнилась, и хотят забрать заказ, но в `Map` остался только Олег. Проблема в том, что **проверка и добавление — два отдельных действия**. Между ними другой поток успевает выполнить свой код.

Для такой задачи нужна объединённая операция:

```java
Long previousCourier = assignedCouriers.putIfAbsent(orderId, courierId);

if (previousCourier == null) {
    System.out.println("Заказ назначен вам");
} else {
    System.out.println("Заказ уже занят");
}
```

`putIfAbsent()` означает **«добавить, только если такого ключа ещё нет»**. Метод возвращает:

* `null`, если записи не было и текущий вызов добавил её;
* идентификатор уже назначенного курьера, если запись существовала. В этом случае значение не заменяется.

У `ConcurrentHashMap` проверка и добавление выполняются **атомарно — как одно неделимое действие**. Поэтому, если свободный заказ одновременно пытаются взять два курьера, только один добавит запись. Второй обнаружит уже существующее назначение и получит отказ. Кто именно окажется первым, заранее неизвестно.

## Очередь

Допустим, после оформления заказа нужно отправить уведомление клиенту, но отправка может занимать время. Чтобы другие заказы не ждали, приложение может не отправлять уведомление самостоятельно в основном потоке, который обрабатывает заказы, а добавить задание на отправку уведомления в очередь, откуда его заберет и выполнит отдельный поток-обработчик.

Очередь — коллекция для хранения элементов, ожидающих обработки. Вообще для очередей используется правило **FIFO — First In, First Out, «первым пришёл — первым вышел»**. Например, если добавить номера заказов `10`, `20`, `30`, а потом брать задачи из очереди, будем получать их тоже в порядке `10`, `20`, `30` — первый добавленный заказ и обработан будет первым.

Однако в Java интерфейс `Queue` не требует FIFO от всех реализаций. Например, `PriorityQueue` выбирает элемент не по порядку добавления, а по приоритету.

### `ConcurrentLinkedQueue`

`ConcurrentLinkedQueue` — потокобезопасная FIFO-очередь, основанная на связанных между собой узлах — как `LinkedList`.

```java
Queue<Long> notifications = new ConcurrentLinkedQueue<>();

notifications.offer(10L);
notifications.offer(20L);

Long orderId = notifications.poll();

if (orderId != null) {
    System.out.println("Отправляем уведомление по заказу " + orderId);
    // Отправляем уведомление по заказу 10
}

System.out.println(notifications); // [20]
```

`poll()` одновременно получает элемент и удаляет его из очереди. Если несколько обработчиков забирают задания из общей очереди, каждое задание получит только один из них.

Но очередь разрешает повторы: если дважды добавить `10L`, в ней будут два задания с этим номером.

У `ConcurrentLinkedQueue` нет заданного ограничения вместимости. Если задания поступают быстрее, чем обрабатываются, очередь будет расти.

Также `poll()` не ждёт появления задания: для пустой очереди он возвращает `null`. Поэтому такую очередь называют неблокирующей. `null` в качестве элемента запрещён.

***

### `BlockingQueue`

Обработчику часто нужно не просто проверить очередь, а **дождаться нового задания**, если на данный момент она пуста. И наоборот — у очередей с лимитом очередь может быть заполнена, тогда мы можем хотеть, чтобы обработчик **дождался, пока освободится место** и добавил элемент, а не упал с ошибкой.

Для этого есть интерфейс `BlockingQueue`, который расширяет `Queue`.

**Блокирующая операция** при необходимости приостанавливает выполняющий её поток до появления нужного условия. Другие потоки приложения при этом могут продолжать работу.

<table><thead><tr><th width="188.703125">Задача</th><th>Без ожидания</th><th>С ожиданием</th></tr></thead><tbody><tr><td>Добавить элемент</td><td><code>offer(e)</code> возвращает <code>false</code>, если места нет</td><td><code>put(e)</code> ждёт свободного места</td></tr><tr><td>Извлечь элемент</td><td><code>poll()</code> возвращает <code>null</code>, если очередь пуста</td><td><code>take()</code> ждёт появления элемента</td></tr></tbody></table>

Есть также варианты `offer()` и `poll()`, которые могут ждать в течение указанного времени, и либо выполнить операцию, если появилась возможность, либо вернуть значения как в таблице выше, если за заданное время возможности так и не появилось.

`BlockingQueue` не разрешает элементы `null`.

***

### `ArrayBlockingQueue`

`ArrayBlockingQueue` хранит элементы в массиве **фиксированной вместимости**:

```java
BlockingQueue<Long> notifications = new ArrayBlockingQueue<>(2);
```

Здесь одновременно могут ожидать не более двух заданий.

```java
System.out.println(notifications.offer(10L)); // true
System.out.println(notifications.offer(20L)); // true
System.out.println(notifications.offer(30L)); // false - место кончилось

System.out.println(notifications.poll()); // 10

System.out.println(notifications.offer(30L)); // true - место освободилось poll()
System.out.println(notifications); // [20, 30]
```

Третье добавление сначала не получилось: оба места были заняты. После извлечения `10L` одно место освободилось, и повторная попытка добавления `30L` завершилась успешно.

Если бы вместо первого `offer(30L)` был вызван `put(30L)`, текущий поток ожидал бы свободного места. Но до следующей строки с `poll()` он самостоятельно не дошёл бы, так как заблокирован на `put(30L)` — освободить место должен другой поток.

Размер массива после создания очереди увеличить нельзя, только освободить в ней место, убрав существующие элементы.

***

### `LinkedBlockingQueue`

`LinkedBlockingQueue` хранит элементы в связанных узлах. Размер можно задать:

```java
BlockingQueue<Long> notifications = new LinkedBlockingQueue<>(100);
```

Теперь в очереди может находиться не более 100 элементов. При заполнении `offer()` вернёт `false`, а `put()` будет ждать.

Есть и конструктор без аргументов:

```java
BlockingQueue<Long> notifications = new LinkedBlockingQueue<>();
```

У него предел равен `Integer.MAX_VALUE`, то есть `2 147 483 647` элементов.

Узлы создаются по мере добавления элементов; массив на всю вместимость заранее не выделяется.

### Где используются блокирующие очереди

#### Производитель и потребитель

В сервисе доставки одна часть программы создаёт задания на отправку уведомлений, а другая их выполняет.

Сторону, которая добавляет задания, называют **производителем**, а сторону, которая их забирает из очереди и выполняет — **потребителем**.

Очередь связывает их: производитель может добавить задание, даже если потребитель сейчас занят другой работой. Ограничение вместимости не даёт бесконтрольно накапливать ожидающие задания. Для этого подходят `ArrayBlockingQueue` и `LinkedBlockingQueue`.

#### Пулы потоков

**Пул потоков** — группа потоков, которые выполняют поступающие задачи.

Например, есть три потока и десять заданий на отправку уведомлений. Пока все потоки заняты, часть заданий может ждать в очереди. Освободившийся поток берёт следующее задание.

В Java пул потоков по умолчанию использует `BlockingQueue` для хранения задач. Конкретная очередь выбирается при настройке пула.

При этом заполненная очередь пула **не обязательно заставляет отправителя ждать**: реакция зависит от настроек пула. Он может создать дополнительный рабочий поток в допустимых пределах или отклонить задачу (об этом подробнее — в одном из следующих модулей).

{% hint style="danger" icon="circle-question" %}
В очередь добавляют по 100 заданий в секунду, а обработчики успевают выполнять только 60 заданий в секунду. Из-за этого очередь постоянно заполняется до предела. Решит ли проблему расширение вместимости очереди со 100 элементов до 10 000?
{% endhint %}

<summary>Ответ</summary>

Нет. Скорость обработки это не увеличивает, и все равно остается прирост 40 новых заданий в секунду — большая очередь заполнится медленнее, но рано или поздно это все равно произойдет.

Нужно устранить постоянное отставание обработчиков: ускорить обработку, увеличить доступные ресурсы или ограничить поступление заданий.

## Вопросы

{% hint style="info" icon="gitbook" %}
#### **Опишите базовый принцип работы "Copy-On-Write" коллекций (`CopyOnWriteArrayList`, `CopyOnWriteArraySet`) и типичные сценарии их применения.**

Copy-On-Write означает копирование при изменении — создается новый массив, туда переносят существующие элементы, и уже с новым массивом производится нужная операция. При этом ранее созданные итераторы (запущенные циклы) продолжают обход старого массива. Это позволяет обходить коллекцию независимо от последующих изменений.

`CopyOnWriteArrayList` — список, а `CopyOnWriteArraySet` — множество на его основе, проверяющее уникальность через `equals()`. Такие коллекции подходят для небольших, редко изменяемых списков с частым чтением — например, для хранения набора правил, которые проверяются при каждом запросе, но обновляются редко (способы доставки, доступные платежные провайдеры). Частые изменения дорогие из-за того, что при каждом изменении нужно копировать массив.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### **Назовите основные классы потокобезопасных коллекций (например, `ConcurrentHashMap`, `ConcurrentLinkedQueue`) и их общее предназначение.**

`ConcurrentHashMap` предназначен для использования безопасного `Map` в нескольких потоках; `ConcurrentLinkedQueue` — для FIFO-очереди; `ConcurrentLinkedDeque` — для очереди с доступом с обоих концов. `CopyOnWriteArrayList` и `CopyOnWriteArraySet` подходят для частых чтений и редких изменений. `ArrayBlockingQueue` и `LinkedBlockingQueue` позволяют ожидать появления элементов или свободного места.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### **Какие реализации интерфейса `Queue` вы знаете (`ArrayBlockingQueue`, `LinkedBlockingQueue`) и в каких общих системах (например, пулы потоков) они могут применяться?**

Среди реализаций `Queue` есть обычные `ArrayDeque`, `LinkedList`, `PriorityQueue`, а есть потокобезопасные — `ConcurrentLinkedQueue`, `ArrayBlockingQueue`, `LinkedBlockingQueue`.

`ArrayBlockingQueue` основана на массиве ограниченного размера. `LinkedBlockingQueue` использует связанные узлы; её размер можно задать, а можно не задавать — по умолчанию предел равен `Integer.MAX_VALUE`. Обе поддерживают FIFO и методы `put()` и `take()` с ожиданием.

Они применяются для передачи заданий от производителей потребителям, фоновой обработки и хранения ожидающих задач в пулах потоков.
{% endhint %}
