# Клиент-серверная архитектура, HTTP

Представим приложение для доставки еды. Пользователь открывает каталог ресторанов, выбирает блюда, оформляет заказ и следит за его статусом.

Чтобы приложение работало, необходимо где-то хранить информацию о ресторанах, меню, пользователях и заказах. Нужно также проверять доступность блюд (в ресторане могли закончиться нужные ингредиенты), рассчитывать общую стоимость заказа и сохранять изменения.

Некоторые приложения могут работать полностью локально — например, заметки без облачной синхронизации. Но сервису доставки такая модель не подойдет — нужно централизованное место, в котором пользователи смогут оставлять, а рестораны забирать заказы — нужен **сервер**.

***

## Клиент-серверная архитектура

> **Клиент-серверная архитектура** — способ организации системы, при котором клиент обращается к серверу с запросами, а сервер обрабатывает их и возвращает ответы.

**Клиент** — сторона, которая инициирует запрос. Например, браузер, мобильное приложение или утилита в терминале.

**Сервер** — программа, которая принимает запросы, обрабатывает их и предоставляет клиентам данные или выполняет запрошенные действия.

В примере с сервисом доставки мобильное приложение — клиент, а Java-приложение на Spring Boot — сервер.

<figure><img src="../.gitbook/assets/image (37).png" alt=""><figcaption></figcaption></figure>

Допустим, пользователь открывает заказ `#101`:

1. Клиент отправляет серверу запрос: получи информацию о заказе `#101`.
2. Сервер принимает запрос и сначала проверяет, есть ли у пользователя права на просмотр заказа — например, права есть, если это его заказ, либо если он суперадминистратор (тогда ему доступны все заказы).
3. Если проверка доступа пройдена, сервер получает данные заказа из БД.
4. Сервер формирует ответ и отправляет его клиенту.
5. Клиент отображает информацию на экране.

При этом серверу не обязательно знать, как именно мобильное приложение отображает заказ. Ему достаточно вернуть согласованные данные.

Например:

```json
{
  "id": 101,
  "status": "COOKING",
  "total": 1500
}
```

Клиент может показать статус `COOKING` как «Готовится» и нарисовать соответствующую иконку, но сервер об этом не знает. Такое разделение позволяет одному серверу обслуживать несколько разных клиентов — мобильное приложение, веб-сайт и внутреннюю административную панель.

***

### Преимущества клиент-серверной архитектуры

* **Централизованное хранение данных.** Все клиенты работают с общей информацией. Например, если статус заказа поменялся, это видят и клиент, и ресторан.
* **Разделение ответственности.** Клиент отвечает за взаимодействие с пользователем, а сервер — за обработку запросов, бизнес-правила и работу с данными.
* **Независимое развитие.** Можно изменить внутреннюю реализацию сервера, не меняя клиентские приложения, если контракт взаимодействия (формат запросов и ответов) не поменялся.

***

### Недостатки клиент-серверной архитектуры

* **Зависимость от сети.** Если соединение пропало, клиент не сможет получить свежие данные с сервера. Некоторые функции можно сделать доступными без интернета, но для этого нужны дополнительные механизмы.
  * Также если сам сервер недоступен, зависимые от него функции перестают работать.
* **Задержки.** Каждый сетевой запрос требует времени на передачу данных и обработку ответа.
* **Нагрузка на сервер.** Если тысячи клиентов одновременно отправляют запросы, серверу необходимы достаточные ресурсы. При росте нагрузки систему приходится масштабировать (например, выделять серверу больше памяти или запускать несколько его копий, чтобы между ними распределить нагрузку).

***

## HTTP

Мы разобрались, что клиент отправляет серверу запросы, а сервер возвращает ответы. В запросе клиент должен сообщить:

* какие данные он хочет получить
* какую операцию необходимо выполнить
* какие значения он передаёт серверу

А сервер должен сообщить, удалось ли выполнить операцию, и вернуть результат. Для этого предназначен HTTP.

> **HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня, который определяет правила обмена запросами и ответами между клиентом и сервером.

Название исторически связано с передачей гипертекста — веб-страниц, содержащих ссылки на другие страницы. Но сегодня HTTP используется не только для HTML: через него передают JSON, изображения, файлы и другие данные.

***

### Структура HTTP-запроса

Представим, что пользователь открывает заказ `#101` в приложении доставки. Клиент (приложение) отправляет:

```bash
GET /api/orders/101 HTTP/1.1
Host: api.delivery.example
Accept: application/json
```

* `GET` — HTTP-метод. Он определяет, **какую операцию** клиент хочет выполнить. В данном случае — получить данные.
* `/api/orders/101` — **путь к ресурсу**. Вместе с адресом сервера он образует URL — адрес ресурса.
* `HTTP/1.1` — **версия протокола**, здесь HTTP/1.1. У HTTP/2 и HTTP/3 способ передачи сообщений отличается, но основные методы и коды ответов имеют тот же смысл.
* `Host` и `Accept` — **заголовки** (headers). Они передают **дополнительную информацию** о запросе. Например, `Accept: application/json` означает, что клиент готов получить ответ в формате JSON.

У HTTP-запроса также может быть **тело** (body). Например, при создании заказа клиенту нужно отправить выбранные блюда, их количество и адрес доставки:

```json
{
  "items": [
    { "dishId": 10, "quantity": 2 },
    { "dishId": 20, "quantity": 1 }
  ],
  "deliveryAddress": "Москва, ул. Лесная, 10"
}
```

***

### Структура HTTP-ответа

Сервер получает запрос, находит заказ и возвращает:

```shellscript
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 101,
  "status": "COOKING",
  "total": 1500
}
```

* `200 OK` — **HTTP-статус**. 200 означает, что запрос был успешно обработан.
* `Content-Type` — заголовок ответа. Указывает **формат** передаваемых данных.
* JSON — тело ответа. Содержит информацию о заказе, которую клиент сможет отобразить пользователю.

В обычном HTTP-взаимодействии каждый запрос получает свой ответ. Даже если операция завершилась ошибкой, сервер обычно возвращает HTTP-ответ с соответствующим статусом.

***

### Основные HTTP-методы

***

#### `GET`

Пример — получить информацию о заказе:

```shellscript
GET /api/orders/101 HTTP/1.1
Host: api.delivery.example
```

`GET` не должен выполнять изменения данных — технически сделать это можно, но не рекомендуется. Например, получение заказа не должно менять его статус.

***

#### `POST`

Пример — пользователь оформляет новый заказ.

```shellscript
POST /api/orders HTTP/1.1
Host: api.delivery.example
Content-Type: application/json

{
  "restaurantId": 5,
  "items": [
    {
      "dishId": 20,
      "quantity": 2
    }
  ]
}
```

Сервер проверяет данные, создаёт заказ и может вернуть:

```shellscript
HTTP/1.1 201 Created
Location: /api/orders/105
Content-Type: application/json

{
  "id": 105,
  "status": "NEW"
}
```

`201 Created` означает, что ресурс был создан. `Location` указывает адрес нового ресурса.

***

#### `PUT`

Представим, что пользователь изменяет сохранённый адрес доставки:

```shellscript
PUT /api/addresses/15 HTTP/1.1
Host: api.delivery.example
Content-Type: application/json

{
  "city": "Москва",
  "street": "Лесная",
  "house": "10",
  "apartment": "25"
}
```

Смысл `PUT` — привести ресурс по указанному адресу к состоянию, описанному в запросе. Если  ранее у пользователя не было сохраненного адреса, создается новый. Если был, его данные полностью меняются на данные из запроса.

Важно учитывать, что в `PUT` должен передаваться объект полностью. Например, если мы хотим поменять только номер квартиры, и оставить без изменений все остальное, нельзя написать просто

```shellscript
{
  "apartment": "30"
}
```

В случае `PUT` такое тело читается как "у адреса теперь есть ТОЛЬКО квартира, все остальные поля, которые ранее были заполнены, нужно очистить". Поэтому если мы хотим поменять только `apartment`, а остальные поля оставить как есть, их все равно придется передать:

```shellscript
{
  "city": "Москва",
  "street": "Лесная",
  "house": "10",
  "apartment": "30"
}
```

Поэтому для изменения только одного или нескольких полей удобнее использовать `PATCH`.

***

#### `PATCH`

Вернемся к примеру с адресом — если хотим поменять только номер квартиры, в PATCH можно передать только его:

```shellscript
PATCH /api/addresses/15 HTTP/1.1
Host: api.delivery.example
Content-Type: application/json

{
  "apartment": "30"
}
```

Остальные поля не будут очищены, они останутся без изменений. Например, если город сейчас Москва, он же и останется.

***

#### `DELETE`

Пример — удалить продукт из корзины:

```shellscript
DELETE /api/cart/items/20 HTTP/1.1
Host: api.delivery.example
```

При успешном выполнении сервер может вернуть:

```shellscript
HTTP/1.1 204 No Content
```

`204 No Content` означает, что запрос успешно выполнен, но тело ответа не требуется.

`DELETE` не обязательно означает физическое удаление строки из БД: сервер может реализовать логическое удаление (так же называют мягкое удаление) — оставить строку, но пометить ее как неактивную (например, `is_active=false` или `status=DELETED`).

***

Есть также HTTP-методы `HEAD` и `OPTIONS`.

* `HEAD` похож на `GET`, но сервер не возвращает тело ответа, только метаданные ресурса.
* `OPTIONS` позволяет узнать поддерживаемые способы взаимодействия с ресурсом.

***

### Идемпотентность HTTP-методов

> **Идемпотентность** — свойство операции, при котором многократное выполнение одного и того же запроса имеет тот же эффект на состояние системы, что и однократное выполнение.

Например, пользователь добавил комментарий к заказу, "Позвонить перед доставкой". Если повторить одну и ту же операцию с одними и теми же данными несколько раз, комментарий к заказу останется тем же. Это идемпотентная операция.

Другой пример — пользователь нажал на кнопку "добавить" в карточке товара "хлеб". Если он 5 раз нажмет на эту кнопку, у него в корзине будет 5 булок хлеба. Это не идемпотентная операция.

В HTTP:

| **Метод** | **Идемпотентный?** |
| --------- | ------------------ |
| `GET`     | Да                 |
| `POST`    | Не гарантируется   |
| `PUT`     | Да                 |
| `PATCH`   | Не гарантируется   |
| `DELETE`  | Да                 |

`POST` по желанию разработчика можно реализовать идемпотентным, но это не гарантируется самим методом. Не зная реализации, мы не можем рассчитывать на идемпотентность. А вот PUT всего обязан быть идемпотентным.

> :exclamation:**Идемпотентность ≠ всегда одинаковый ответ.**
>
> Это часто путают.
>
> Например, два `DELETE` одного и того же ресурса подряд могут вернуть статусы: первый — `204` без тела (успешно), а второй — `404` (не найдено) с телом `{ "error": "Не удалось найти ресурс" }`.
>
> Несмотря на разные ответы и статусы, операция все равно идемпотентна, потому что **итоговое состояние ресурса одинаково**. У него будет `is_active=false` — как если мы выполним операцию 1 раз, так и если выполним ее 10 раз.

{% hint style="warning" icon="eyes" %}
Идемпотентность — одно из самых важных понятий для Java-разработчика. Вы постоянно будете сталкиваться с ним: при изучении разных тем, на собеседованиях, при выполнении проектных задач.
{% endhint %}

В контексте HTTP идемпотентность важна при сетевых сбоях.

Если клиент отправил запрос, сервер его **выполнил**, но соединение оборвалось до того, как клиент получил ответ `"OK"`, он может попытаться выполнить его еще раз. В таком случае не идемпотентная операция опасна — ее повтор может вызвать повторное списание денег за один и тот же заказ, дубль сообщения в чате и т. д.

***

### HTTP-статусы

Для обозначения результата в HTTP используются коды состояния (status codes). Все коды сгруппированы **по первой цифре.**

<table data-header-hidden><thead><tr><th width="148"></th><th></th></tr></thead><tbody><tr><td><strong>Класс</strong></td><td><strong>Значение</strong></td></tr><tr><td><code>1xx</code></td><td>Информационные ответы, запрос ещё обрабатывается</td></tr><tr><td><code>2xx</code></td><td>Успешное выполнение</td></tr><tr><td><code>3xx</code></td><td>Перенаправление или необходимость дополнительных действий для получения ресурса</td></tr><tr><td><code>4xx</code></td><td>Ошибка со стороны клиента — например, неправильный формат поля в запросе</td></tr><tr><td><code>5xx</code></td><td>Ошибка со стороны сервера — например, неожиданно вылетело исключение в коде</td></tr></tbody></table>

Самые часто встречающиеся коды:

* `200 OK` — запрос успешно выполнен.\
  Например, успешно получили заказ:\
  <mark style="color:green;">`GET /api/orders/101`</mark> <mark style="color:green;"></mark><mark style="color:green;">→</mark> <mark style="color:green;"></mark><mark style="color:green;">`200 OK`</mark><mark style="color:green;">, тело ответа</mark> <mark style="color:green;"></mark><mark style="color:green;">`{"id":101,"status":"COOKING","total":1500}`</mark>
* `201 Created` — успешно создан новый ресурс.\
  Например, успешно создан новый заказ:\
  <mark style="color:green;">`POST /api/orders`</mark><mark style="color:green;">, в теле данные нового заказа →</mark> <mark style="color:green;"></mark><mark style="color:green;">`201 Created`</mark> <mark style="color:green;"></mark><mark style="color:green;">с телом</mark> <mark style="color:green;"></mark><mark style="color:green;">`{"id":105,"status":"NEW"}`</mark>
* `204 No Content` — запрос успешно выполнен, но в ответе нечего показать в теле.\
  Например, после удаления товара из корзины:\
  <mark style="color:green;">`DELETE /api/cart/items/20`</mark> <mark style="color:green;"></mark><mark style="color:green;">→</mark> <mark style="color:green;"></mark><mark style="color:green;">`204 No Content`</mark><mark style="color:green;">, тело ответа отсутствует</mark>
* `301 Moved Permanently` — ресурс постоянно перенесён на другой адрес.\
  Например, раньше меню было доступно по endpoint-у `/api/restaurants/5/menu`, но в процессе обновления приложения адрес поменяли на `/api/menus/5`.\
  Если устаревший клиент отправит запрос <mark style="color:green;">`GET /api/restaurants/5/menu`</mark><mark style="color:green;">, сервер может ответить</mark> <mark style="color:green;"></mark><mark style="color:green;">`301 Moved Permanently`</mark> <mark style="color:green;"></mark><mark style="color:green;">без тела с заголовком</mark> <mark style="color:green;"></mark><mark style="color:green;">`Location: /api/menus/5`</mark>, и браузер автоматически откроет новый адрес из заголовка (сделает еще один запрос по новому адресу, на который уже получит `200 OK` с телом) — клиент даже не заметит ошибки.
* `302 Found` — временное перенаправление.\
  То же самое, что и `301`, но в случае `301` клиент может считать, что адрес теперь всегда будет такой, и может смело поменять свой запрос на новое API, а в случае `302` адрес поменялся временно и потом может поменяться обратно, поэтому менять запрос со стороны клиента не нужно.
* `400 Bad Request` — сервер не может обработать запрос из-за ошибки клиента, например некорректного формата поля.\
  <mark style="color:green;">`POST /api/orders`</mark> <mark style="color:green;"></mark><mark style="color:green;">с телом</mark> <mark style="color:green;"></mark><mark style="color:green;">`{"quantity":-2}`</mark> <mark style="color:green;"></mark><mark style="color:green;">→</mark> <mark style="color:green;"></mark><mark style="color:green;">`400 Bad Request`</mark><mark style="color:green;">, тело ответа</mark> <mark style="color:green;"></mark><mark style="color:green;">`{"message":"Количество товара должно быть больше 0"}`</mark>
* `401 Unauthorized` — для выполнения запроса не хватает данных аутентификации.\
  <mark style="color:green;">Например клиент в запросе</mark> <mark style="color:green;"></mark><mark style="color:green;">`GET /api/orders/101`</mark> <mark style="color:green;"></mark><mark style="color:green;">не передал токен пользователя.</mark>
* `403 Forbidden` — данные для аутентификации есть, но по ним сервер определил, что у пользователя нет доступа к запрашиваемым данным.\
  Например, пользователь пытается открыть чужой заказ, или у него роль обычного покупателя, а он пытается выполнить запрос на добавление нового блюда в меню ресторана.
*   `404 Not Found` — запрошенный ресурс не найден.

    <mark style="color:green;">`GET /api/orders/999`</mark> <mark style="color:green;"></mark><mark style="color:green;">→</mark> <mark style="color:green;"></mark><mark style="color:green;">`404 Not Found`</mark><mark style="color:green;">, если заказа с таким ID нет</mark>.
* `405 Method Not Allowed` — HTTP-метод не поддерживается для данного ресурса.\
  `POST /api/orders/101` → `405 Method Not Allowed`, если `POST` поддерживается только для `/api/orders`, а для `/api/orders/101` доступны только `GET` и `PATCH`.
* `409 Conflict` — запрос конфликтует с текущим состоянием ресурса.\
  Например, клиент уже отменил заказ, а ресторан пытается начать его готовить:\
  <mark style="color:green;">`PATCH /api/orders/101`</mark> <mark style="color:green;"></mark><mark style="color:green;">с телом</mark> <mark style="color:green;"></mark><mark style="color:green;">`{"status":"COOKING"}`</mark> <mark style="color:green;"></mark><mark style="color:green;">→</mark> <mark style="color:green;"></mark><mark style="color:green;">`409 Conflict`</mark><mark style="color:green;">.</mark>
* `429 Too Many Requests` — клиент отправляет слишком много запросов за период времени.
* `500 Internal Server Error` — непредвиденная ошибка со стороны сервера при обработке запроса. Например, получили `NullPointerException`, который не предусмотрели при разработке.
* `503 Service Unavailable` — сервис временно недоступен, например из-за перегрузки или выпуска обновления.

{% hint style="danger" icon="circle-question" %}
Пользователь добавляет в календарь событие через `POST /api/events` с телом `{ "eventName": "Созвон", "start": "10:00", "end": "9:00" }` (время начала позже времени конца). Какой HTTP статус вернуть?
{% endhint %}

<summary>Ответ</summary>

Данные запроса некорректны — подойдет `400 Bad Request`. В теле желательно вернуть сообщение ошибки — например, `{ "error": "Время окончания должно быть позже времени начала" }`.

</details>

### HTTP и HTTPS

Часто в HTTP-запросе передаются персональные данные пользователя. При обычном HTTP содержимое не защищено шифрованием на транспортном уровне. Тот, кто может перехватывать сетевой трафик, потенциально способен прочитать передаваемые данные или вмешаться в соединение.

Для решения этой проблемы используется HTTPS.

> **HTTPS (HTTP Secure)** — это HTTP, передаваемый через защищённое соединение с использованием TLS (Transport Layer Security).

TLS обеспечивает три важные вещи:

* конфиденциальность — передаваемые данные шифруются
* целостность — изменения данных в процессе передачи (например, злоумышленником-перехватчиком) автоматически обнаруживаются
* проверку подлинности сервера — клиент проверяет цифровой сертификат, чтобы убедиться, что устанавливает защищённое соединение с нужным сервером

Например:

```
http://api.delivery.example
```

и:

```
https://api.delivery.example
```

обращаются к сервису по разным схемам.

При HTTPS сами HTTP-методы, статусы и смысл запросов остаются прежними. Меняется способ защиты их передачи.

HTTPS не заменяет авторизацию — со стороны сервера все еще нужно предусмотреть аутентификацию и права доступа.

## Вопросы

{% hint style="info" icon="gitbook" %}
#### Что такое клиент-серверная архитектура? Преимущества и недостатки.

**Клиент-серверная архитектура** — способ организации приложения, при котором клиент отправляет запросы серверу, а сервер обрабатывает их и возвращает ответы.

Клиент обычно отвечает за интерфейс со стороны пользователя (сайт, мобильное приложение), а сервер — за бизнес-логику и работу с данными. Например, мобильное приложение доставки (клиент) отправляет запрос на получение заказа, а сервер читает данные из БД и возвращает их в формате JSON.

Преимущества — централизованная работа с данными, разделение ответственности, возможность независимо обновлять клиент и сервер и обслуживать разных клиентов через общий API.

Недостатки — зависимость от сети и доступности сервера, сетевые задержки, необходимость масштабировать сервер при высокой нагрузке.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое HTTP?

**HTTP** — протокол прикладного уровня, определяющий правила обмена запросами и ответами между клиентом и сервером.

HTTP-запрос содержит метод, адрес ресурса, заголовки и при необходимости тело. Ответ содержит статус, заголовки и при необходимости тело.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Основные методы HTTP.

* `GET` — получение данных
* `POST` — обработка переданных данных, чаще всего создание нового ресурса на основе запроса
* `PUT` — полная замена состояния ресурса — если он существует, полное его обновление, если не существует, создание
* `PATCH` — частичное изменение ресурса (можно передать только те поля, которые хотим изменить, а остальные останутся как сейчас)
* `DELETE` — удаление ресурса
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Классы HTTP-статусов (`1xx`–`5xx`), основные коды.

* `1xx` — информационные
* `2xx` — успешное выполнение запроса
  * `200 OK` — запрос успешно выполнен
  * `201 Created` — успешно создан новый ресурс
  * `204 No Content` — запрос успешно выполнен, но в ответе нечего показать в теле (часто используется при удалении)
* `3xx` — перенаправления
  * `301 Moved Permanently` — ресурс постоянно перенесён на другой адрес (обычно указывается в ответе в заголовке `Location`)
  * `302 Found` — ресурс перенесен временно, в будущем может снова быть доступен по старому адресу
* `4xx` — ошибки со стороны клиента
  * `400 Bad Request` — сервер не может обработать запрос из-за ошибки клиента, например некорректного формата поля
  * `401 Unauthorized` — для выполнения запроса не хватает данных аутентификации, например, не передан токен
  * `403 Forbidden` — данные для аутентификации есть, но по ним сервер определил, что у пользователя нет доступа к запрашиваемым данным, например, он пытается получить чужие данные
  * `404 Not Found` — запрошенный ресурс не найден
  * `405 Method Not Allowed` — HTTP-метод не поддерживается для данного ресурса
  * `409 Conflict` — запрос конфликтует с текущим состоянием ресурса
  * `429 Too Many Requests` — клиент отправляет слишком много запросов за период времени
* `5xx` — ошибки со стороны сервера
  * `500 Internal Server Error` — непредвиденная ошибка со стороны сервера
  * `503 Service Unavailable` — сервис временно недоступен
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Отличия HTTP от HTTPS.

**HTTPS** — HTTP поверх защищённого соединения TLS. Оно обеспечивает шифрование и целостность передаваемых данных, а также проверку подлинности сервера. При этом методы и статусы остаются теми же, как в HTTP.
{% endhint %}
