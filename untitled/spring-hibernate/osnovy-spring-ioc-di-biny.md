# Основы Spring (IoC, DI, бины)

Представим, что мы разрабатываем backend сервиса доставки еды. Пользователь оформляет заказ, сервер сохраняет его и отправляет пользователю уведомление о том, что заказ принят.

Для этого нам понадобится несколько классов:

* `OrderService` — обрабатывает заказы.
* `NotificationSender` — отвечает за отправку уведомлений.
* `EmailNotificationSender` — реализация отправки уведомлений по email.

Посмотрим, как организовать взаимодействие этих классов сначала без Spring, а затем с его помощью.

Начнём с обычного Java-кода. Представим, что `OrderService` самостоятельно создаёт объект для отправки уведомлений:

```java
public class OrderService {

    private final EmailNotificationSender notificationSender = new EmailNotificationSender();

    public void confirmOrder(long orderId) {
        notificationSender.send(orderId, "Заказ принят");
    }
}
```

Здесь `OrderService` не только выполняет бизнес-логику, но и самостоятельно решает, какой объект использовать для отправки уведомлений.

В принципе, такой код работает. Например, при вызове:

```java
OrderService orderService = new OrderService();
orderService.confirmOrder(101);
```

пользователь получит уведомление о заказе `#101`. Но представим, что мы захотели вместо email отправлять SMS. Придётся менять сам `OrderService`:

```java
private final SmsNotificationSender notificationSender = new SmsNotificationSender();
```

Получается, что бизнес-логика обработки заказов зависит от конкретного способа отправки уведомлений. Это нарушает принципы SOLID и создаст проблемы при росте сложности проекта. Чем больше зависимостей у сервиса, тем больше объектов ему приходится самостоятельно создавать и настраивать.

При разработке небольшого приложения это может быть терпимо. Но в большом backend-приложении десятки или сотни классов зависят друг от друга, и ручное создание всех объектов становится сложным.

Для решения подобных проблем используется Spring.

***

## Что такое Spring?

**Spring Framework** — Java-фреймворк, предоставляющий инфраструктуру для разработки приложений. Одна из его основных возможностей — автоматическое управление объектами приложения и их зависимостями.

В Spring также есть инструменты для быстрой и удобной веб-разработки, работы с данными, безопасности и других задач. Но его основной механизм описывается двумя терминами — IoC и DI.

***

### Принцип IoC — Inversion of Control

Сейчас `OrderService` самостоятельно создаёт `EmailNotificationSender`:

```java
private final EmailNotificationSender notificationSender = new EmailNotificationSender();
```

Чтобы в случае необходимости можно было легко поменять способ отправки уведомлений (например, вместо email отправлять SMS), вместо конкретного `EmailNotificationSender` создаём интерфейс:

```java
public interface NotificationSender {

    void send(long orderId, String message);
}
```

Интерфейс описывает возможность — отправить уведомление. Можно использовать интерфейс, не зная деталей реализации. Конкретный способ отправки будет в реализации интерфейса:

```java
public class EmailNotificationSender implements NotificationSender {

    @Override
    public void send(long orderId, String message) {
        System.out.println("Email по заказу #" + orderId + ": " + message);
    }
}
```

Теперь `OrderService` может зависеть от интерфейса, а не от конкретной реализации:

```java
@RequiredArgsConstructor
public class OrderService {

    private final NotificationSender notificationSender;

    public void confirmOrder(long orderId) {
        notificationSender.send(orderId, "Заказ принят");
    }
}
```

Посмотрим, что изменилось. Раньше `OrderService` сам создавал нужный объект. Теперь он получает готовый объект извне, через конструктор.

Например, в классе `Main` можно написать:

```java
NotificationSender sender = new EmailNotificationSender();
OrderService orderService = new OrderService(sender);
orderService.confirmOrder(101);
```

Результат:

```
Email по заказу #101: Заказ принят
```

Если теперь понадобится отправлять SMS, можно создать другую реализацию `NotificationSender` и передать уже её в конструктор `OrderService`. Сам `OrderService` менять не придётся.

Это пример инверсии управления.

> **Inversion of Control (IoC, инверсия управления)** — принцип, при котором управление определёнными аспектами работы объекта, например созданием и предоставлением его зависимостей, передаётся внешнему механизму.

Принцип IoC можно применять в обычной Java — выше мы реализовали его без Spring. Spring просто предоставляет готовый механизм, который берёт значительную часть повторяющегося кода на себя.

***

### Dependency Injection — DI

> **Dependency Injection (DI, внедрение зависимостей)** — способ реализации IoC, при котором объект получает необходимые ему зависимости извне, а не создаёт или ищет их самостоятельно.

Получается, IoC — более общий принцип, при котором управление объектом передается какому-то механизму вне объекта, например, фреймворку или просто другому классу. DI — более узкий термин, это реализация инверсии управления, которая касается именно создания объектов и передачи им их зависимостей. DI — это IoC, но IoC — это не только DI; например, паттерн Factory, который мы изучали ранее, тоже является способом реализации инверсии управления.

Ранее мы сами создавали и связывали объекты:

```java
NotificationSender sender = new EmailNotificationSender();
OrderService orderService = new OrderService(sender);
```

Но когда приложение большое и объектов много, вручную собирать все зависимости неудобно. Spring предоставляет для этого готовый механизм — IoC-контейнер.

> **IoC-контейнер** — компонент фреймворка Spring, который управляет объектами приложения: создаёт их, предоставляет зависимости и управляет жизненным циклом.

Spring может самостоятельно:

1. Определить, какие объекты должны находиться под его управлением, а какие нет.
2. Создать необходимые объекты.
3. Найти зависимости, нужные каждому из них.
4. Передать готовые зависимости через конструкторы, сеттеры или поля.

Таким образом, создание и связывание объектов больше не нужно прописывать вручную в каждом месте приложения.

***

## Spring Bean

Мы выяснили, что Spring может самостоятельно создавать объекты и внедрять их зависимости. Но ведь в Java-приложении может быть множество объектов:

```java
OrderService orderService = new OrderService(sender);
String message = "Заказ принят";
List<Long> orderIds = new ArrayList<>();
```

Spring не должен управлять каждым созданным объектом — в примере выше мы хотим, чтобы он управлял только `OrderService`. У `String` и `List<Long>` вообще нет зависимостей, и это простые объекты, которые мы хотим создавать и управлять ими вручную.

> **Spring Bean (бин)** — объект, который регистрируется в IoC-контейнере Spring и находится под его управлением.

С точки зрения Java бин — обычный объект, он не устроен как-то иначе. Главное, что созданием, конфигурацией и зависимостями бинов управляет Spring, а остальными обычными объектами он не управляет.

**Есть несколько основных способов сообщить Spring, что объект является бином.**

***

### 1. `@Component`

Помечаем класс аннотацией `@Component`. Например:

```java
@Component
public class EmailNotificationSender implements NotificationSender {

    @Override
    public void send(long orderId, String message) {
        System.out.println("Email по заказу #" + orderId + ": " + message);
    }
}
```

Аннотация `@Component` сообщает Spring, что этот класс может быть зарегистрирован как бин. Нужно еще включить в приложении component scanning — сканирование указанных пакетов приложения в поисках возможных бинов. Иначе Spring попросту не будет их искать, даже если мы правильно пометим нужные классы аннотациями.

Например, если у нашего приложения пакет `com.example.delivery`, мы можем включить сканирование всех классов в нем так:

```java
@Configuration
@ComponentScan("com.example.delivery")
public class AppConfig {
}
```

Если `EmailNotificationSender` находится в сканируемом пакете, Spring сможет зарегистрировать его и создать соответствующий бин.

Сейчас в проектах чаще всего используют Spring Boot, который основан на Spring Framework. В Spring Boot сканирование компонентов включено через аннотацию `@SpringBootApplication` над главным классом, и самим писать `@ComponentScan` обычно не нужно.

По умолчанию Spring для класса, помеченного аннотацией `@Component`, создает ровно один объект. Если этот бин используется в нескольких других бинах, то это все равно один и тот же экземпляр, а не несколько разных. Можно поменять это поведение, если указать другой scope бина — к этому вернемся позже.

***

#### `@Service`, `@Repository`, `@Controller`

Помимо `@Component`, в Spring есть специализированные аннотации, которые сами помечены метааннотацией `@Component`.

<table data-header-hidden><thead><tr><th width="251"></th><th></th></tr></thead><tbody><tr><td><code>@Component</code></td><td>Бин, для которого не подходит ни один более специализированный вариант</td></tr><tr><td><code>@Service</code></td><td>Сервисы с бизнес-логикой</td></tr><tr><td><code>@Repository</code></td><td>Работа с данными — например, выполнение SQL-запросов</td></tr><tr><td><code>@Controller</code></td><td>Контроллеры, обрабатывающие веб-запросы</td></tr></tbody></table>

Так как эти аннотации — специализированные варианты `@Component`, они, как и `@Component`, позволяют регистрировать классы как бины.

Например, `OrderService` логично пометить `@Service`:

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final NotificationSender notificationSender;

    public void confirmOrder(long orderId) {
        notificationSender.send(orderId, "Заказ принят");
    }
}
```

А `EmailNotificationSender` можно оставить с `@Component`.

Если оба класса зарегистрированы как бины, Spring увидит, что конструктору `OrderService` нужен `NotificationSender`, сам найдёт подходящий бин и передаст его в конструктор при создании `OrderService`. Именно поэтому у `OrderService` нигде не вызывается `new` вручную, и внутри него не создаётся `EmailNotificationSender` — со Spring это не нужно.

***

### 2. `@Bean`

Не всегда есть возможность пометить класс аннотацией — например, мы не создаем класс сами, а используем готовый из сторонней библиотеки. Мы не можем просто открыть её исходный код и добавить туда `@Component`.

Для таких случаев удобно использовать аннотацию `@Bean`.

Представим, что `EmailNotificationSender` — готовый класс из библиотеки для отправки email, не помеченный `@Component`.

Создадим конфигурацию:

```java
@Configuration
public class NotificationConfig {

    @Bean
    public NotificationSender notificationSender() {
        return new EmailNotificationSender();
    }
}
```

Теперь Spring знает, как получить бин типа `NotificationSender`:

1. Если класс `NotificationConfig` зарегистрирован в контексте (например, найден при сканировании), Spring распознаёт аннотацию `@Configuration`.
2. Проверяет методы этого класса и воспринимает метод `notificationSender()` как метод для создания бина, потому что он помечен аннотацией `@Bean`.
3. Использует этот метод для создания бина.
4. Добавляет бин в контекст — теперь его можно использовать, если он понадобится как зависимость другим бинам.

Разница с `@Component`:

* `@Component` ставится на класс, и Spring создает объект этого класса.
* `@Bean` ставится на метод (обычно внутри класса, помеченного аннотацией `@Configuration`). Тип возвращаемого значения у этого метода должен соответствовать типу бина, который мы хотим создать. Spring получает объект бина путем выполнения метода.

***

### 3. XML-конфигурация

Раньше бины описывали в XML. Например, фрагмент XML-конфигурации:

```xml
<bean
    id="notificationSender"
    class="com.example.delivery.EmailNotificationSender"
/>
```

Здесь мы явно указываем Spring класс, объект которого нужно создать, и имя бина.

В современных приложениях обычно используют аннотации и Java-конфигурацию, но XML по-прежнему поддерживается и может встречаться в legacy-проектах.

Существуют и другие способы регистрации бинов, но для начального знакомства достаточно понимать три основных подхода.

***

### Bean и обычный Java-объект

Вернёмся к `OrderService`. Если мы создадим его вручную:

```java
OrderService service = new OrderService(...);
```

**получим обычный Java-объект, даже если класс `OrderService` помечен `@Service`.**

Аннотация сама по себе не превращает любой объект этого класса в Spring Bean. Бином будет тот экземпляр, который зарегистрирован в IoC-контейнере — например, который создаст автоматически сам Spring, а не мы явно через `new`.

Это важно, потому что Spring внедряет зависимости и выполняет другую инфраструктурную работу только применительно к объектам, находящимся под его управлением. Если мы вручную создадим `OrderService`, Spring не внедрит в него `NotificationSender`.

***

## Способы внедрения зависимостей

До этого мы использовали только один способ внедрения зависимости — через конструктор. Но Spring поддерживает и другие варианты.

Основных способов три:

1. Через конструктор (Constructor Injection).
2. Через сеттер (Setter Injection).
3. Через поле (Field Injection).

Разберём их на примере `OrderService` и `NotificationSender`.

***

### 1. Внедрение через конструктор — Constructor Injection

Этот способ мы уже использовали:

```java
@Service
public class OrderService {

    private final NotificationSender notificationSender;

    public OrderService(NotificationSender notificationSender) {
        this.notificationSender = notificationSender;
    }

    public void confirmOrder(long orderId) {
        notificationSender.send(orderId, "Заказ принят");
    }
}
```

Чаще всего то же самое пишут через `@RequiredArgsConstructor` — результат тот же.

Когда Spring создаёт `OrderService`, он:

1. Видит конструктор с единственным аргументом — `NotificationSender`.
2. Ищет уже зарегистрированный бин, подходящий по типу (`NotificationSender` или его реализации).
3. Если ранее он уже создавал и регистрировал такой бин, использует его, если нет, создаёт нужный бин впервые и сохраняет в контекст, чтобы потом переиспользовать.
4. Передаёт бин типа `NotificationSender` в конструктор `OrderService`.
5. Если бы в конструкторе `OrderService` было больше зависимостей (например, еще `OrderRepository`, `OrderMapper` и т. д.), Spring аналогично передал бы и их.

Раньше над конструктором ставили `@Autowired`, но сейчас если конструктор только один, Spring и так понимает, что его нужно использовать для внедрения зависимостей, и `@Autowired` над ним ставить не обязательно.

***

### 2. Внедрение через сеттер — Setter Injection

Пример:

```java
@Service
public class OrderService {

    private NotificationSender notificationSender;

    @Autowired
    public void setNotificationSender(NotificationSender notificationSender) {
        this.notificationSender = notificationSender;
    }
}
```

`@Autowired` в этом случае обязательна.

В данном случае Spring:

1. Создаёт объект `OrderService`, но зависимость `notificationSender` ещё не установлена.
2. Находит сеттер с `@Autowired`.
3. Вызывает его, передавая подходящий `NotificationSender`.

То есть зависимость устанавливается **после создания объекта**.

Такой способ может быть полезен для необязательных зависимостей, но нужно помнить, что `@Autowired` по умолчанию требует наличия зависимости. Чтобы разрешить её отсутствие, это нужно настроить отдельно, например через `@Autowired(required = false)`. Теперь если зависимость есть, она внедрится через сеттер после создания объекта, если нет — ничего страшного, объект и так уже создался без нее. Через конструктор тоже можно передать необязательную зависимость, например с помощью `Optional<NotificationSender>`, но это нужно предусмотреть явно.

Недостатки по сравнению с конструктором: поле нельзя сделать `final` (можем случайно его потом поменять и сломать объект), в случае с установкой обязательной зависимости через setter объект какое-то время уже существует, но в неполном состоянии, если его пытаться в этот момент использовать, можем получить ошибки.

***

### 3. Внедрение через поле — Field Injection

Пример:

```java
@Service
public class OrderService {

    @Autowired
    private NotificationSender notificationSender;
}
```

Spring создаст `OrderService`, а затем присвоит полю подходящий бин.

На первый взгляд это самый короткий вариант. Но у него есть существенные недостатки: поле нельзя сделать `final`, потому что Spring должен присвоить значение уже после создания объекта, а еще чтобы внедрить значение в `private` поле, Spring будет вынужден использовать рефлексию.

***

### Почему Constructor Injection — рекомендуемый способ?

Главное преимущество — **обязательные зависимости передаются сразу при создании объекта**. Поэтому обязательные зависимости доступны уже после вызова конструктора, а при внедрении через сеттер или поле объект сначала создаётся и только затем ему устанавливают зависимости.

Другие преимущества:

* Ошибки конфигурации обнаруживаются при создании бина. Если Spring не может найти обязательную зависимость, создание бина сразу завершится ошибкой.
* Зависимости явно видны в конструкторе. Сразу понятно, что нужно классу для работы.
* Поля можно сделать `final`. Плюс — неизменяемость; после создания объекта нельзя присвоить полям другую ссылку и случайно "сломать" тем самым бин.
* Удобно тестировать. Можно создать `OrderService` с тестовой реализацией `NotificationSender`, не запуская Spring. При Setter Injection это тоже возможно, но зависимость нужно устанавливать отдельным вызовом сеттера — больше кода, и можно случайно пропустить этот шаг. При Field Injection с приватным полем установить просто так значение вообще не получится, нужна будет рефлексия.

## Что, если подходят несколько бинов?

Вернёмся к примеру с уведомлениями. Пока у нас была только одна реализация:

```java
@Component
public class EmailNotificationSender implements NotificationSender {
    // ...
}
```

Теперь добавим ещё одну:

```java
@Component
public class SmsNotificationSender implements NotificationSender {
    // ...
}
```

Обе реализации зарегистрированы как Spring Bean и реализуют один интерфейс, `NotificationSender`. А в `OrderService` мы запрашиваем:

```java
public OrderService(NotificationSender notificationSender) {
    this.notificationSender = notificationSender;
}
```

Возникает вопрос: какой именно бин должен передать Spring? `EmailNotificationSender` или `SmsNotificationSender`?

Если оставить реализацию как есть, при создании `OrderService` возникнет ошибка из-за неоднозначной зависимости — `NoUniqueBeanDefinitionException`.

Для её решения можно использовать `@Primary` или `@Qualifier`.

***

### `@Primary`

Представим, что по умолчанию все уведомления должны отправляться через email. Можем пометить соответствующий бин:

```java
@Primary
@Component
public class EmailNotificationSender implements NotificationSender {
    // ...
}
```

Теперь при внедрении:

```java
public OrderService(NotificationSender notificationSender) {
    this.notificationSender = notificationSender;
}
```

Если явно не указано, какой бин выбрать, Spring отдаст предпочтение варианту по умолчанию — `EmailNotificationSender`.

***

### `@Qualifier`

Теперь представим, что только для заказов мы хотим использовать SMS, при этом все остальные уведомления (акции, действия с аккаунтом и т. п.) продолжают использовать способ отправки по умолчанию, через email.

Для удобства можно дать бинам имена:

```java
@Component("emailSender")
@Primary
public class EmailNotificationSender implements NotificationSender {
    // ...
}
```

```java
@Component("smsSender")
public class SmsNotificationSender implements NotificationSender {
    // ...
}
```

Затем используем `@Qualifier`:

```java
@Service
public class OrderService {

    private final NotificationSender notificationSender;

    public OrderService(
            @Qualifier("smsSender") NotificationSender notificationSender
    ) {
        this.notificationSender = notificationSender;
    }
}
```

Теперь Spring выберет `SmsNotificationSender`, несмотря на то что `EmailNotificationSender` помечен `@Primary`.

***

## Циклические зависимости

Мы уже знаем, что один бин может зависеть от другого. Например, пусть `OrderService` использует `DeliveryService` для сохранения способа доставки заказа.

Но представим, что `DeliveryService` тоже использует `OrderService` — например, чтобы получить общий вес всех товаров в заказе для курьерской службы.

Получается замкнутый круг.

> **Циклическая зависимость (Circular Dependency)** — ситуация, когда несколько объектов зависят друг от друга так, что их цепочка зависимостей образует цикл.

Циклическая зависимость не обязательно всегда с двумя бинами, их может быть любое количество: A → B → C → ... → E → A.

Для примера с заказами:

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final DeliveryService deliveryService;
}
```

```java
@Service
@RequiredArgsConstructor
public class DeliveryService {

    private final OrderService orderService;
}
```

Когда Spring попытается создать `OrderService`, произойдёт следующее:

1. Для создания `OrderService` нужен `DeliveryService`.
2. Spring начинает создавать `DeliveryService`.
3. Для создания `DeliveryService` нужен `OrderService`.
4. Но `OrderService` ещё не создан — мы как раз пытались создать его на первом шаге.

Получается бесконечная зависимость:

```
Чтобы создать A, нужен B.
Чтобы создать B, нужен A.
```

Цикл с обязательными зависимостями через конструкторы Spring разрешить не может. При создании таких бинов возникнет ошибка, например `BeanCurrentlyInCreationException`.

***

### Как исправить циклическую зависимость?

Первое, что нужно сделать, — понять, почему два сервиса так сильно зависят друг от друга. Чаще всего это признак неудачной архитектуры, и избавиться от цикла можно, если просто иначе распределить ответственность между сервисами.

Это предпочтительное решение, поскольку устраняется сама причина проблемы: слишком сильная взаимная зависимость сервисов.

Если все же перепроектировать связи сейчас нельзя, есть другие способы:

#### 1. Отложить получение зависимости через `@Lazy`

Spring позволяет не подставлять реальный объект зависимости сразу, а отложить это до момента первого обращения к нему. Для этого можно использовать `@Lazy` на параметре конструктора:

```java
@Service
public class DeliveryService {

    private final OrderService orderService;

    public DeliveryService(@Lazy OrderService orderService) {
        this.orderService = orderService;
    }
}
```

Теперь, когда Spring будет создавать `DeliveryService`, вместо готового `OrderService` он передаст прокси — специальный объект-посредник, через который позднее можно обратиться к настоящему бину.

#### 2. Использовать Setter Injection вместо Constructor Injection

В отличие от внедрения через конструктор, Setter Injection позволяет сначала создать Java-объект, а уже потом установить его зависимости. Например:

```java
@Service
public class DeliveryService {

    private OrderService orderService;

    @Autowired
    public void setOrderService(OrderService orderService) {
        this.orderService = orderService;
    }
}
```

Если `OrderService` тоже использует Setter Injection, то контейнер при разрешённой обработке циклических ссылок может:

1. Создать экземпляр `OrderService` без зависимостей.
2. Создать экземпляр `DeliveryService` без зависимостей.
3. Установить зависимости через сеттеры.
4. Завершить инициализацию обоих бинов.

Но здесь есть важный нюанс: в Spring Boot начиная с версии 2.6 разрешение циклических зависимостей по умолчанию отключено. Его можно включить:

```
spring.main.allow-circular-references=true
```

#### 3. Получать зависимость через `ObjectProvider`

Ещё один вариант — не внедрять сам `OrderService`, а передать объект, который умеет получить его позднее. Spring предоставляет для этого `ObjectProvider<T>`:

```java
@Service
@RequiredArgsConstructor
public class DeliveryService {

    private final ObjectProvider<OrderService> orderServiceProvider;

    public int getOrderWeight(long orderId) {
        return orderServiceProvider.getObject().getTotalWeight(orderId);
    }
}
```

Во время создания `DeliveryService` Spring внедряет только `ObjectProvider`, поэтому ему не требуется немедленно создавать `OrderService`. Настоящий `OrderService` будет получен при вызове `getOrderWeight()`.

Этот способ похож на `@Lazy`, но получение зависимости происходит явно, через вызов `getObject()`.

## Вопросы

{% hint style="info" icon="gitbook" %}
#### Что такое Spring? Принцип IoC и Dependency Injection (DI).

**Spring Framework** — Java-фреймворк для разработки приложений, предоставляющий готовую инфраструктуру для управления объектами, их зависимостями и другими аспектами работы приложения.

**IoC (Inversion of Control)** — принцип инверсии управления; вместо того чтобы самостоятельно создавать и находить свои зависимости, объект получает их от внешнего механизма (например, от фреймворка). IoC — общая идея, у которой есть разные конкретные реализации, например, Factory паттерн или DI.

**DI (Dependency Injection)** — один из способов реализации IoC, при котором зависимости передаются объекту извне через конструктор, сеттер или поле.

Например, `OrderService` не создаёт внутри себя `new EmailNotificationSender`, а получает готовый `NotificationSender` извне.

В Spring созданием объектов и внедрением их зависимостей занимается IoC-контейнер.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое Spring Bean? Способы создания бинов.

**Spring Bean** — объект, зарегистрированный в IoC-контейнере Spring и находящийся под его управлением.

Основные способы регистрации бинов:

* Через `@Component` и специализированные аннотации `@Service`, `@Repository`, `@Controller` — Spring находит такие классы при сканировании пакетов.
* Через `@Bean` в классе конфигурации, помеченном `@Configuration` — метод возвращает объект, который регистрируется как бин.
* Через XML-конфигурацию с элементами `<bean>`. Более старый, но поддерживаемый способ.

Объект, созданный вручную через `new`, автоматически не становится Spring Bean, даже если его класс помечен `@Service`.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Способы внедрения зависимостей (конструктор, сеттер, поле).

Зависимости можно внедрять тремя основными способами: через конструктор, сеттер или поле.

Конструктор — предпочтительный способ, потому что зависимости передаются при создании объекта, и он сразу существует со всеми обязательными связями. Также при этом способе проще всего тестирование — можно передать в конструктор вместо реальной реализации тестовую заглушку. Еще плюсы: можно сделать зависимости `final`, чтобы случайно их не поменять, а при взгляде на конструктор можно быстро понять, какие зависимости нужны бину.

Сеттер или поле с `@Autowired` позволяют установить зависимости после создания объекта. Объект какое-то время существует, пока обязательные зависимости ещё не внедрены, что увеличивает риск ошибок при преждевременном использовании объекта. Также поля нельзя сделать `final`. Тестирование тоже усложняется, особенно в случае private полей — для них приходится использовать рефлексию.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое циклические зависимости и как их исправить?

Циклическая зависимость возникает, когда бины зависят друг от друга по замкнутой цепочке, например `OrderService -> DeliveryService -> OrderService`. При внедрении через конструкторы Spring не может создать объекты, потому что для `OrderService` нужен готовый `DeliveryService` и наоборот.

Рекомендуемый способ исправления — пересмотреть ответственность классов и устранить цикл (например, перенести часть логики). Если это невозможно, можно использовать `@Lazy` или `ObjectProvider` — они позволяют отложить получение реального бина до момента обращения к нему. При определённой конфигурации можно также использовать Setter Injection (он позволяет Spring сначала создать объекты и затем связать их).
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что делать, если для внедрения подходят несколько бинов? `@Primary`, `@Qualifier`

Если для внедрения подходят несколько бинов одного типа, Spring не поймет, какой из них нужно внедрить, и возникнет `NoUniqueBeanDefinitionException`.

Если есть вариант, который подходит в большинстве случаев, можно пометить его аннотацией `@Primary` — тогда если будет несколько кандидатов, Spring по умолчанию выберет бин с этой аннотацией. Эта аннотация ставится **над самим бином**.

`@Qualifier("<название бина>")` позволяет уточнить, какой именно бин нужно внедрить, по его названию. Эта аннотация ставится **в конкретном месте внедрения**.
{% endhint %}
