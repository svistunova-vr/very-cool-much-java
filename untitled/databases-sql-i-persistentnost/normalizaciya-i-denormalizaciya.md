# Нормализация и денормализация

## Зачем нужна нормализация?

Почему вообще нужно разносить данные по разным таблицам? Почему бы не хранить всё в одной большой таблице?

<table data-header-hidden><thead><tr><th width="98"></th><th></th><th></th><th></th><th></th><th width="147"></th><th></th></tr></thead><tbody><tr><td><code>order_id</code></td><td><code>order_date</code></td><td><code>user_id</code></td><td><code>user_name</code></td><td><code>product_id</code></td><td><code>product_name</code></td><td><code>quantity</code></td></tr><tr><td>101</td><td>01.10.2026</td><td>1</td><td>Анна</td><td>10</td><td>Мышь</td><td>2</td></tr><tr><td>101</td><td>01.10.2026</td><td>1</td><td>Анна</td><td>20</td><td>Клавиатура</td><td>1</td></tr><tr><td>102</td><td>03.10.2026</td><td>1</td><td>Анна</td><td>10</td><td>Мышь</td><td>1</td></tr><tr><td>103</td><td>04.10.2026</td><td>2</td><td>Иван</td><td>30</td><td>Монитор</td><td>1</td></tr></tbody></table>

На первый взгляд всё удобно: открыли одну таблицу и сразу видим заказ, пользователя и товары.

Но довольно быстро появляются проблемы. Например, имя Анна хранится несколько раз:

```
order 101 → Анна
order 101 → Анна
order 102 → Анна
```

Если пользователь поменял имя на "Анна Петрова", придётся обновить **несколько строк**. Если одну строку забыли изменить:

```
101 → Анна Петрова
101 → Анна
102 → Анна Петрова
```

база начинает содержать противоречивые данные.

То же самое происходит с названием товара:

```
product_id = 10
name = Мышь
```

оно может повторяться в сотнях или тысячах заказов. Если название нужно будет поменять, действие будет выполняться долго, есть риск пропустить какую-то запись или допустить опечатку.

Именно такие проблемы пытается уменьшить нормализация.

> **Нормализация** — проектирование структуры реляционной БД таким образом, чтобы уменьшить избыточное хранение данных и избежать проблем при их добавлении, изменении и удалении.

***

Основная проблема избыточных данных — не сам факт, что какое-то значение повторилось. Повторение иногда совершенно нормально. Например:

```
orders.user_id

1
1
1
2
```

`user_id = 1` повторяется потому, что у пользователя несколько заказов. Это нормальная связь `1:M`.

Проблема появляется, когда мы **в нескольких местах независимо храним один и тот же факт**. Например:

```
user_id = 1
user_name = Анна
```

Если имя пользователя хранится и в `users`, и во всех его заказах, один и тот же факт "у пользователя #1 имя Анна" записан много раз (сравним с повторением в заказах Анны — там факты разные — "Анне принадлежит заказ #101", "Анне принадлежит заказ #102", ...).

После нормализации имя пользователя хранится только здесь:

```
users

id | name
---+--------------
1  | Анна Петрова
```

А заказы содержат только `user_id = 1`. Чтобы поменять имя пользователя, не надо менять заказы.

***

Таблица без нормализации может создать неудобства не только при изменении, но и при добавлении данных. Представим таблицу, где данные о товаре существуют только вместе с заказом:

```
order_id | product_id | product_name
```

Мы хотим добавить новый товар:

```
product_id = 40
product_name = Наушники
```

но его пока никто не заказал. Куда его записать?

Если информация о товаре хранится только внутри строк заказа, получается, что **товар нельзя создать до первого заказа**.

После разделения `products` и `orders` товар можно добавить независимо от заказов.

***

Аналогично с удалением:

```
order_id | product_id | product_name
---------+------------+-------------
101      | 40         | Наушники
```

Это пока единственный заказ с товаром #40. Если удалить заказ #101, мы одновременно потеряем единственную запись о том, что товар:

```
40 | Наушники
```

вообще существовал.

После нормализации данные о товаре находятся отдельно, поэтому удаление заказа их не уничтожает.

***

## Нормальные формы

Нормализация описывается через **нормальные формы (NF)**. На практике чаще всего рассматривают первые три, хотя всего их больше.

Каждая следующая нормальная форма предполагает выполнение предыдущей:

```
3NF
↓
обязательно соответствует 2NF
↓
обязательно соответствует 1NF
```

***

### Первая нормальная форма

Представим таблицу заказов:

| `id` | `user_id` | `products`                |
| ---- | --------- | ------------------------- |
| 101  | 1         | Мышь, Клавиатура, Монитор |
| 102  | 2         | Наушники                  |

В одном столбце `products` мы храним сразу несколько значений:

```
Мышь, Клавиатура, Монитор
```

Как найти все заказы, содержащие именно товар «Мышь»?

Приходится разбирать содержимое строки. Ещё хуже если в таблице встречаются разные форматы:

```
Мышь,Клавиатура
```

```
Мышь Клавиатура
```

```
Мышь; Клавиатура
```

Для реляционной БД намного удобнее, когда в одной ячейке хранится **одно значение**.

> **Первая нормальная форма (`1NF`)** требует, чтобы значения в таблице были атомарными: в каждой ячейке находилось одно значение, а не список или набор повторяющихся значений.

Вместо:

```
products = "Мышь, Клавиатура, Монитор"
```

нужно представить товары отдельными записями. Например:

```
order_items

order_id | product_id
---------+-----------
101      | 10
101      | 20
101      | 30
102      | 40
```

Теперь одна строка содержит один факт: `order 101 содержит product 10`.

***

"Атомарное значение" не означает, что строку типа "Анна Петрова" обязательно нужно разделить на:

```
Анна
Петрова
```

Атомарность зависит от того, **как мы собираемся работать с данными**.

Если приложению нужен адрес только чтобы отображать его целиком в профиле, можно хранить его одной строкой `"Москва, ул. Ленина, 10"`.

Если же нам нужно искать по части адреса — например, найти всех клиентов из Москвы — то тогда эти данные лучше хранить в отдельных столбцах.

***

### Вторая нормальная форма

В `2NF` используется новое понятие — **зависимость столбца от ключа**.

Возьмём промежуточную таблицу связи заказов с товарами:

| `order_id` | `product_id` | `quantity` | `order_date` | `product_name` |
| ---------- | ------------ | ---------- | ------------ | -------------- |
| 101        | 10           | 2          | 01.10.2026   | Мышь           |
| 101        | 20           | 1          | 01.10.2026   | Клавиатура     |
| 102        | 10           | 1          | 03.10.2026   | Мышь           |

Допустим, первичный ключ — `PRIMARY KEY (order_id, product_id)`. То есть конкретную строку определяет **сочетание двух значений**:

```
order_id + product_id
```

Например, `order_id=101`, `product_id=10` — конкретный товар в конкретном заказе.

Посмотрим на `quantity`:

```
order_id = 101
product_id = 10
quantity = 2
```

Количество зависит именно от сочетания:

```
Order #101 + Product #10
```

В другом заказе количество того же товара может быть другим:

```
Order #102 + Product #10
quantity = 1
```

То есть quantity зависит от **всего** составного ключа.

А вот `order_date` зависит только от `order_id` — для всех товаров в заказе #101 дата заказа одинакова:

```
101 | 10 | ... | 01.10.2026
101 | 20 | ... | 01.10.2026
```

`product_name` наоборот зависит только от `product_id` — товар с `id=10` всегда называется "Мышь", независимо от того, в каком заказе он находится.

> **Вторая нормальная форма (`2NF`)** — таблица находится в `1NF`, и каждый неключевой столбец зависит от **всего составного ключа**, а не только от его части.

Здесь нарушение возникает из-за **частичной зависимости**.

***

#### Как исправить

Данные заказа выносим в `orders`:

```
orders

id  | order_date
----+------------
101 | 01.10.2026
102 | 03.10.2026
```

Данные товара — в `products`:

```
products

id | name
---+------------
10 | Мышь
20 | Клавиатура
```

А в `order_items` оставляем то, что относится именно к **сочетанию заказа и товара**:

```
order_items

order_id | product_id | quantity
---------+------------+---------
101      | 10         | 2
101      | 20         | 1
102      | 10         | 1
```

Теперь никакие неключевые (т. е. не входящие в составной ключ) поля не зависят только от половины составного PK.

Проблема `2NF` появляется именно тогда, когда ключ **составной**.

Если таблица имеет простой PK, например, id, то у него физически нет «части», от которой мог бы зависеть другой столбец.

Поэтому таблица в `1NF` с простым ключом автоматически не имеет нарушения `2NF` из-за частичной зависимости.

***

### Третья нормальная форма

Теперь представим таблицу заказов:

| `id` | `user_id` | `user_email`     | `total` |
| ---- | --------- | ---------------- | ------- |
| 101  | 1         | anna@example.com | 4500    |
| 102  | 1         | anna@example.com | 1200    |
| 103  | 2         | ivan@example.com | 800     |

Посмотрим на `user_email` — он относится не к заказу, а к пользователю. То есть `user_email` зависит от `user_id`, который сам является неключевым столбцом таблицы `orders`.

Получилась цепочка:

```
PRIMARY KEY (id)
    ↓
неключевой столбец (user_id)
    ↓
другой неключевой столбец (user_email)
```

Такая зависимость называется **транзитивной**.

> **Третья нормальная форма (`3NF`)** — таблица находится в `2NF`, а неключевые столбцы не зависят друг от друга транзитивно.

***

#### Как исправить

```
users

id | email
---+-----------------
1  | anna@example.com
2  | ivan@example.com
```

```
orders

id  | user_id | total
----+---------+------
101 | 1       | 4500
102 | 1       | 1200
103 | 2       | 800
```

Теперь в `orders` хранится только `user_id`, а email при необходимости можно получить через связь:

```
orders.user_id → users.id
```

Если Анна изменит email:

```
anna@example.com
↓
anna.dev@example.com
```

его нужно изменить только в `users`.

***

Все три формы вместе можно описать правилом:

> Неключевые данные должны зависеть от **ключа, всего ключа и ничего кроме ключа**.

* **1NF** — в одной ячейке одно значение
* **2NF** — неключевое поле зависит от всего составного ключа, а не только от его части
* **3NF** — неключевое поле не должно зависеть от другого неключевого поля

Важно помнить, что цель нормализации не в том, чтобы получить как можно больше маленьких таблиц. Например, у пользователя есть:

```
id
login
email
registration_date
```

Все эти свойства относятся к одному пользователю. Нет смысла создавать отдельные таблицы:

```
user_logins
user_emails
user_registration_dates
```

Нормализация нужна только там там, где структура данных создаёт зависимости и избыточность, способные привести к аномалиям.

***

## Денормализация

У нормализации есть цена.

Представим, что нам нужно показать сводную таблицу заказов:

```
номер заказа | дата | имя пользователя | количество товаров
```

Данные находятся в разных таблицах:

```
orders
users
order_items
```

Чтобы собрать результат, СУБД должна объединить их данные.

```
orders
   ↓
 users
   ↓
order_items
```

Чем сложнее отчёт, тем больше таблиц может понадобиться прочитать и объединить. Часто это совершенно нормально, но бывают сценарии, когда запросы выполняются очень часто, объём данных огромный, а результат нужен очень быстро. В таких случаях осознанно делают обратный шаг.

> **Денормализация** — намеренное добавление избыточности в данные ради ускорения или упрощения конкретных запросов.

Ключевое слово здесь — **намеренное**. Мы понимаем, что данные дублируются, понимаем связанные с этим риски и сознательно платим эту цену ради производительности.

***

### Пример денормализации

Допустим, есть:

```
orders

id
user_id
total
```

и:

```
order_items

order_id
product_id
quantity
```

Чтобы узнать количество товаров в заказе, можно каждый раз считать строки `order_items`. Но представим очень большой маркетплейс, где список заказов открывается постоянно. Можно сознательно добавить в `orders` новое поле `items_count`:

```
orders

id  | user_id | total | items_count
----+---------+-------+------------
101 | 1       | 4500  | 3
```

Хотя количество товаров уже можно вычислить из `order_items`. То есть информация теперь хранится в двух местах: `order_items` и `orders`.

Чтение становится проще и быстрее: раньше надо было к `orders` присоединить `order_items` и самостоятельно посчитать количество, а теперь можно использовать готовое поле `orders.items_count`.

Но появляется новая проблема: при добавлении товара в `order_items` нужно не забыть обновить `orders.items_count`. Иначе данные могут разойтись.

***

{% hint style="danger" icon="circle-question" %}
Частная клиника хранит информацию о приёмах пациентов. Пока все данные складывают в одну таблицу:

| `visit_id` | `visit_date` | `patient_id` | `patient_name` | `doctor_id` | `doctor_name` | `department_id` | `department_name` | `services`                    |
| ---------- | ------------ | ------------ | -------------- | ----------- | ------------- | --------------- | ----------------- | ----------------------------- |
| 101        | 05.10.2026   | 1            | Анна Петрова   | 10          | Иванов И.И.   | 3               | Кардиология       | `S01: Консультация, S07: ЭКГ` |
| 102        | 05.10.2026   | 2            | Олег Сидоров   | 10          | Иванов И.И.   | 3               | Кардиология       | `S01: Консультация`           |
| 103        | 06.10.2026   | 1            | Анна Петрова   | 15          | Смирнова А.В. | 5               | Неврология        | `S01: Консультация, S12: ЭЭГ` |

* на одном приёме ровно один пациент
* приём проводит один врач
* каждый врач работает в одном отделении
* за один приём может быть оказано несколько услуг
* одна и та же услуга может оказываться на разных приёмах
* одна услуга в рамках одного приёма встречается не более одного раза
* у каждой услуги есть свой `id`, название и цена

Приведите структуру к **1NF, затем к 2NF и затем к 3NF**.
{% endhint %}

<details>

<summary>Решение</summary>

Сейчас в одной строке данные сразу о нескольких сущностях: приём, пациент, врач, отделение, услуги. Часть информации повторяется (например, `doctor_id = 10`).

#### `1NF`

В исходной таблице одна ячейка содержит сразу **несколько услуг**:

```
services = "S01: Консультация, S07: ЭКГ"
```

Это нарушение `1NF` — в одной ячейке должно находиться одно значение.

Исправление (не забегая вперед на 2NF и 3NF) — каждую услугу одного приёма превращаем в отдельную строку.

Получаем на этом шаге:

| `visit_id` | `visit_date` | `patient_id` | `patient_name` | `doctor_id` | `doctor_name` | `department_id` | `department_name` | `service_id` | `service_name` | `service_price` |
| ---------- | ------------ | ------------ | -------------- | ----------- | ------------- | --------------- | ----------------- | ------------ | -------------- | --------------- |
| 101        | 05.10.2026   | 1            | Анна Петрова   | 10          | Иванов И.И.   | 3               | Кардиология       | S01          | Консультация   | 2500            |
| 101        | 05.10.2026   | 1            | Анна Петрова   | 10          | Иванов И.И.   | 3               | Кардиология       | S07          | ЭКГ            | 1500            |
| 102        | 05.10.2026   | 2            | Олег Сидоров   | 10          | Иванов И.И.   | 3               | Кардиология       | S01          | Консультация   | 2500            |
| 103        | 06.10.2026   | 1            | Анна Петрова   | 15          | Смирнова А.В. | 5               | Неврология        | S01          | Консультация   | 2500            |
| 103        | 06.10.2026   | 1            | Анна Петрова   | 15          | Смирнова А.В. | 5               | Неврология        | S12          | ЭЭГ            | 3000            |

Теперь одну строку можно однозначно определить парой `visit_id` + `service_id`, потому что по условию одна и та же услуга не повторяется дважды внутри одного приёма. Можем на этом шаге считать:

```
PRIMARY KEY (visit_id, service_id)
```

#### `2NF`

Сейчас у нас составной ключ `(visit_id, service_id)`.

Теперь смотрим, от чего зависят остальные столбцы: `visit_date`, `patient_id`, `doctor_id` и другие поля зависят только от `visit_id`. Как это понять? Для `visit_id = 101` они одинаковы независимо от того, какая услуга находится в строке.

А `service_name` и `service_price` зависят только от `service_id`.

Получается, `(visit_id, service_id)` — составной ключ, но часть столбцов зависит только от `visit_id`, а другая часть — только от `service_id`.

Это **частичные зависимости**, то есть нарушение 2NF.

Исправление — разделить данные:

* `visits`

| `id` | `visit_date` | `patient_id` | `patient_name` | `doctor_id` | `doctor_name` | `department_id` | `department_name` |
| ---- | ------------ | ------------ | -------------- | ----------- | ------------- | --------------- | ----------------- |
| 101  | 05.10.2026   | 1            | Анна Петрова   | 10          | Иванов И.И.   | 3               | Кардиология       |
| 102  | 05.10.2026   | 2            | Олег Сидоров   | 10          | Иванов И.И.   | 3               | Кардиология       |
| 103  | 06.10.2026   | 1            | Анна Петрова   | 15          | Смирнова А.В. | 5               | Неврология        |

```
PRIMARY KEY (id)
```

* `services`

| `id` | `name`       | `price` |
| ---- | ------------ | ------- |
| S01  | Консультация | 2500    |
| S07  | ЭКГ          | 1500    |
| S12  | ЭЭГ          | 3000    |

```
PRIMARY KEY (id)
```

* `visit_services`

| `visit_id` | `service_id` |
| ---------- | ------------ |
| 101        | S01          |
| 101        | S07          |
| 102        | S01          |
| 103        | S01          |
| 103        | S12          |

```
PRIMARY KEY (visit_id, service_id)
```

Также тут два FK:

```
visit_services.visit_id
        ↓
visits.id
```

```
visit_services.service_id
        ↓
services.id
```

Теперь в `visit_services` нет полей, которые зависят только от одной половины составного ключа — привели к 2NF.

#### `3NF`

Остались еще зависимости, не связанные с составным ключом:

* В `visits` `patient_name` зависит не от `id` приема, а от `patient_id`
* Аналогично в `visits` `doctor_name` зависит от `doctor_id`
* `department_id` зависит от `doctor_id`
* `department_name` зависит от `department_id`

Для `3NF` неключевые данные не должны зависеть от других неключевых данных. Поэтому выделяем сущности в отдельные таблицы.

## Вопросы

{% hint style="info" icon="gitbook" %}
#### **Что такое нормализация базы данных и зачем она нужна?**

**Нормализация** — проектирование структуры реляционной базы данных таким образом, чтобы уменьшить дублирование одного и того же факта и избежать аномалий при добавлении, изменении и удалении данных.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### **Первая, вторая и третья нормальные формы.**

* **`1NF`** — в каждой ячейке хранится одно атомарное значение, а не список.
* **`2NF`** — таблица находится в `1NF`, и каждый неключевой столбец зависит от всего составного ключа, а не только от его части. Проблема `2NF` актуальна только для составных ключей.
* **`3NF`** — таблица находится в `2NF`, и неключевые столбцы не должны транзитивно зависеть друг от друга. Например, `orders.user_email` избыточен, если email определяется через `orders.user_id`.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### **Что такое денормализация и когда её применяют?**

**Денормализация** — намеренное добавление избыточности в данные ради ускорения или упрощения часто выполняемых запросов.

Например, количество товаров можно при каждом запросе заново вычислять из `order_items`, но при очень частом чтении его эффективнее сохранить в `orders.items_count`.

За ускорение чтения приходится платить усложнением записи, дополнительным расходом памяти и риском рассинхронизации копий. Поэтому обычно сначала проектируют нормализованную схему, а денормализацию добавляют позже под конкретный сценарий.
{% endhint %}
