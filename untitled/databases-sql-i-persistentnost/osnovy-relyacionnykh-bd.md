# Основы реляционных БД

Представим интернет-магазин: есть пользователи, они оформляют заказы, в заказах находятся товары. Пока приложение работает, часть данных можно было бы хранить прямо в коде:

```java
List<User> users;
List<Order> orders;
```

Но после перезапуска приложения эти объекты **исчезнут**. Поэтому данные нужно хранить отдельно от Java-процесса.

***

## База данных и СУБД

Допустим, мы хотим хранить:

* пользователей
* заказы
* товары
* платежи

Набор таких организованных данных — это **база данных**.

> **База данных (БД)** — организованная совокупность данных, предназначенная для долговременного хранения и использования.

Например, у интернет-магазина может существовать база данных `shop`, в которой данные хранятся в таблицах:

* `users`
* `orders`
* `products`
* `payments`

Но сама база данных **просто хранит данные** — она не умеет принимать соединения от Java-приложения, искать нужные строки, проверять ограничения, сохранять изменения и поддерживать одновременную работу нескольких сервисов с одной БД.

Для этого нужна отдельная программа — **система управления базами данных**.

> **СУБД** — программное обеспечение, которое управляет БД: хранит данные, позволяет читать и изменять их, следит за ограничениями и организует одновременный доступ нескольких сервисов.

Например, PostgreSQL, MySQL, Oracle — это СУБД. Если мы используем PostgreSQL, упрощённо взаимодействие выглядит так:

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2F7VE8rK6RpFeWCz1YtVmW%2Fimage.png?alt=media&#x26;token=b9e10b82-7b61-4541-91fe-55117b49c591" alt="" width="540"><figcaption></figcaption></figure>

Поэтому фраза "У нас база PostgreSQL" в разговорной речи встречается постоянно, но технически это неправильно: **PostgreSQL — СУБД**, а конкретная база, которой она управляет, например, `shop` — **БД**.

***

## Реляционная база данных

В основном при обсуждении БД речь идет о **реляционных базах данных**, например PostgreSQL.

Главная идея реляционной модели: данные организованы в **таблицы**, а между таблицами можно задавать **связи**.

***

### Таблица

> **Таблица** хранит множество однотипных записей с одинаковой структурой.

Например, таблица пользователей `users`:

| `id` | `name` | `email`           |
| ---- | ------ | ----------------- |
| 1    | Анна   | anna@example.com  |
| 2    | Иван   | ivan@example.com  |
| 3    | Мария  | maria@example.com |

Структура таблицы задаётся её столбцами:

```
id
name
email
```

Все строки этой таблицы имеют **один и тот же набор столбцов**. Нельзя сделать так, чтобы у одной строки были поля `id`, `name`, `email`, а у другой внезапно появились свои дополнительные поля `phone` и `address`.

Если для какой-то записи значение столбца отсутствует, структура строки от этого не меняется: столбец всё равно существует, просто его значение может отсутствовать:

| 4 | Игорь | `NULL` |
| - | ----- | ------ |

В таблице `users` одна строка представляет одного конкретного пользователя.

***

### Столбец

```
id
name
email
```

— это **столбцы**. Столбец описывает определённое свойство записи. Например, `name` содержит имя пользователя, а `email` — его email.

У каждого столбца также есть тип данных:

```
id       → число
name     → текст
email    → текст
```

***

### Строка

Например:

```
1 | Анна | anna@example.com
```

— **строка таблицы**. Она представляет одну конкретную запись.

```
строка пользователя #1

id    = 1
name  = Анна
email = anna@example.com
```

***

## Первичный ключ — `PRIMARY KEY`

Представим:

<table data-header-hidden><thead><tr><th width="215"></th><th></th></tr></thead><tbody><tr><td>id</td><td>name</td></tr><tr><td>1</td><td>Алексей</td></tr><tr><td>2</td><td>Анна</td></tr><tr><td>3</td><td>Алексей</td></tr></tbody></table>

Имя пользователя не подходит для однозначной идентификации: `name = Алексей` нашло бы сразу двух людей.

Поэтому у каждой записи обычно есть специальный идентификатор — в нашем случае `id`. Пользователь с `id = 1` — это уже однозначно одна строка.

> **Первичный ключ**, или Primary Key (`PK`) — столбец или набор столбцов, который однозначно идентифицирует строку таблицы.

***

### Свойства `PRIMARY KEY`

#### Значение должно быть уникальным

Так нельзя:

| id | name |
| -- | ---- |
| 1  | Анна |
| 1  | Иван |

Если `id` является `PRIMARY KEY`, СУБД не позволит сохранить вторую строку с тем же значением.

***

#### `PRIMARY KEY` не может быть `NULL`

`NULL` означает отсутствие значения.

Такое значение:

```
id = NULL
```

не позволяло бы идентифицировать строку.

Поэтому столбцы, входящие в `PRIMARY KEY`, не могут содержать `NULL`.

***

#### В таблице один `PRIMARY KEY`

Но это не означает, что первичный ключ обязательно состоит из одного столбца. Он может быть **составным**.

Например:

```
(student_id, course_id)
```

могут образовывать один первичный ключ. Главное, что другого `PRIMARY KEY` в этой же таблице быть не может.

***

#### Первичный ключ не обязан называться `id`

Например, `user_id`, `payment_id`, `order_number` технически тоже могут быть первичными ключами.

И первичный ключ не обязан быть числом, он может иметь любой тип данных.

Главное требование — **однозначно идентифицировать строку**.

На практике чаще всего для идентификатора создают отдельный столбец, чаще всего с названием `id`. Например:

```
users

id    login
1     dima
2     ivan
```

`login` тоже уникальный, и технически его можно было бы использовать как PK, но это **бизнес-данные**. Они потенциально могут измениться:

```
dima
↓
dima.dev
```

Если на `login` ссылаются десятки других таблиц через внешние ключи (о них поговорим позже), такое изменение становится намного болезненнее.

Поэтому обычно добавляют специальный столбец, который служит только для идентификации, а не используют бизнес-поле. При создании сущности столбец заполняют:

```
id = 1
```

и потом он не меняется в течение всего срока жизни строки.

Неизменяемость PK — хорошая практика, но технически это не обязательное требование для первичного ключа. Обязательные — только уникальность и отсутствие `NULL`.

***

## Внешний ключ — `FOREIGN KEY`

Добавим таблицу заказов:

| `id` | `user_id` | `total` |
| ---- | --------- | ------- |
| 101  | 1         | 4500    |
| 102  | 1         | 1200    |
| 103  | 2         | 800     |

`orders.user_id = 1` — это ссылка на строку в таблице `users` с `id = 1`.

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2FQVS7y9Um4SwXKEqjwgd5%2Fimage.png?alt=media&#x26;token=a97fa69b-9f47-4029-a0d6-380c6051815e" alt=""><figcaption></figcaption></figure>

> **Внешний ключ**, или Foreign Key (`FK`) — столбец или набор столбцов одной таблицы, который ссылается на ключ другой таблицы и позволяет СУБД контролировать целостность этой связи.

В нашем случае `orders.user_id` — внешний ключ, а `users.id` — ключ, на который он ссылается.

Обычно FK ссылается именно на `PRIMARY KEY`, но это не обязательно — он может ссылаться на другой столбец, если значения в нем уникальны.

***

### Зачем нужен внешний ключ?

Без ограничения `FOREIGN KEY` мы могли бы записать:

<table data-header-hidden><thead><tr><th width="201"></th><th width="224"></th></tr></thead><tbody><tr><td><code>id</code></td><td><code>user_id</code></td></tr><tr><td>104</td><td>999</td></tr></tbody></table>

Хотя пользователя с `users.id = 999` **вообще не существует**. Тогда в данных появилась бы "битая" ссылка. Приложение считало бы, что у заказа есть владелец, но найти его при этом невозможно. Это **нарушение целостности данных**.

Если же `orders.user_id` является `FOREIGN KEY`, при попытке сохранить заказ с `user_id = 999` СУБД проверит, точно ли существует строка в таблице `users` с `id = 999`. Если нет, сохранение будет прервано с ошибкой.

***

### FK не обязан быть уникальным

У Анны может быть три заказа:

<table data-header-hidden><thead><tr><th width="155"></th><th width="235"></th></tr></thead><tbody><tr><td><code>id</code></td><td><code>user_id</code></td></tr><tr><td>101</td><td>1</td></tr><tr><td>102</td><td>1</td></tr><tr><td>105</td><td>1</td></tr></tbody></table>

`user_id = 1` повторяется, но это нормально, ведь FK говорит о том, на какую существующую запись из другой таблицы мы ссылаемся. Один пользователь может быть связан со множеством заказов.

Это уже приводит нас к типам связей.

***

## Связи между таблицами

Тип связи говорит о том, **сколько записей одной таблицы может быть связано с записями другой таблицы**.

### Связь `1:M` — один ко многим

Один пользователь может оформить много заказов, но каждый конкретный заказ принадлежит одному пользователю:

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2FygEvLSQJA9VdrROdSBnq%2Fimage.png?alt=media&#x26;token=9d6eae4d-4418-41ad-b621-9e36814c6100" alt=""><figcaption></figcaption></figure>

Это **один ко многим — `1:M`. FK хранится на стороне `M`**.

В нашем случае 1 — `users`, M — `orders`, поэтому FK хранится в `orders` — это столбец `user_id`.

Если бы было наоборот, и мы хранили бы `order_id` в `users`, пришлось бы каким-то образом положить в одну строку пользователя сразу много идентификаторов заказов:

```
user #1
order_id = 101, 102, 103, ...
```

Это неудобно как с точки зрения пользователя, так и с точки зрения СУБД, которая должна проверять Foreign Key ограничения. Поэтому принятый способ:

```
orders

id   user_id
101     1
102     1
103     1
```

Каждая строка заказа содержит только одну ссылку на владельца. Одинаковый `user_id` может повторяться во многих строках, так как у пользователя может быть много заказов.

***

### Связь `M:M` — многие ко многим

Теперь рассмотрим заказы и товары. Один заказ может содержать много товаров:

```
Order #101

ноутбук
мышь
клавиатура
```

Но и один товар может встречаться во множестве заказов:

```
Mouse

Order #101
Order #205
Order #318
```

Это связь **многие ко многим — `M:M`.**

Здесь одного FK уже недостаточно. Нельзя сделать просто `orders.product_id`, потому что у заказа может быть много товаров. Также нельзя сделать и только `products.order_id`, потому что один товар может входить в много заказов. Поэтому **связь выносится в отдельную таблицу**.

Например, `order_items`:

```
order_id | product_id
---------+-----------
101      | 10
101      | 20
101      | 30
205      | 10
```

Строка "`101 | 10`" означает: "order #101 содержит product #10".

В этой таблице **два внешних ключа**:

* `order_items.order_id` -> `orders.id`
* `order_items.product_id` -> `products.id`

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2FQyOC90Tk4JKrnzqCsN8n%2Fimage.png?alt=media&#x26;token=811ef747-52c7-4de4-95ff-e26473d5b0ef" alt=""><figcaption></figcaption></figure>

***

Промежуточная таблица полезна ещё и сама по себе. У связи заказа и товара обычно есть **собственные данные**. Например, количество или цена.

| `order_id` | `product_id` | `quantity` | `price` |
| ---------- | ------------ | ---------- | ------- |
| 101        | 10           | 2          | 1500    |
| 101        | 20           | 1          | 3000    |

В заказе #101 — товар #10, количество = 2, цена = 1500.

То есть промежуточная таблица хранит не только факт связи, но и **свойства самой связи**. Количество товара относится не только к `Product #10`, и не только к `Order #101`, а именно к их сочетанию:

```
Order #101 + Product #10
```

***

#### Первичный ключ промежуточной таблицы

Вспомним про составные PK. Если один товар должен встречаться в заказе только один раз, можно использовать:

```
PRIMARY KEY (order_id, product_id)
```

Отдельно `order_id = 101` может повторяться. И `product_id = 10` тоже может повторяться. Но их комбинация будет уникальной.

***

### Связь `1:1` — один к одному

Представим две таблицы, `users` и `user_profiles`. В `users` хранится основная информация о пользователе — логин, почта, дата и время регистрации. В `user_profiles` — дополнительная информация, которую пользователь заполняет в профиле: дата рождения, город и т. п.

У одного пользователя может быть только один профиль. И один профиль принадлежит только одному пользователю. Это связь **один к одному — `1:1`.**

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2FUkbURnLK0NovhqsMXSXS%2Fimage.png?alt=media&#x26;token=42e7c700-2a61-4017-975c-f8dbda5d69ee" alt=""><figcaption></figcaption></figure>

Просто создать FK (`user_profiles.user_id` -> `users.id`) недостаточно, для связи 1:1 этот FK должен быть еще и `UNIQUE`:

<figure><img src="https://819230696-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2Fd8RpbzBTi02qD2ZNgN27%2Fuploads%2F4POJBkpXjdhGpO9V80wy%2Fimage.png?alt=media&#x26;token=f5d2d164-b6c7-473d-bdca-980f1124f727" alt=""><figcaption></figcaption></figure>

Один пользователь имеет **не более одного** профиля означает, что профиль может быть еще не создан. Обязательность существования записи с обеих сторон — отдельный вопрос, для связи 1:1 это не обязательно.

{% hint style="danger" icon="circle-question" %}
Есть таблицы `employees` (сотрудники) и `departments` (отделы). В отделе много сотрудников, но каждый сотрудник относится только к одному отделу. Какой это тип связи? Что добавить в таблицы, чтобы его реализовать?
{% endhint %}

<details>

<summary>Ответ</summary>

Это связь **один ко многим — `1:M`**:

```
departments
     1
     │
     M
employees
```

Один отдел может быть связан со многими сотрудниками, но каждый сотрудник — только с одним отделом.

Поэтому внешний ключ нужно добавить на сторону `M`, то есть в таблицу `employees`:

```
departments

id | name
---+---------
1  | Backend
2  | Analytics
```

```
employees

id | name | department_id
---+------+--------------
10 | Анна | 1
11 | Иван | 1
12 | Олег | 2
```

Если сотрудник **обязательно** должен состоять в каком-то отделе, обычно добавляют ещё `NOT NULL`:

```
department_id BIGINT NOT NULL REFERENCES departments(id)
```

</details>

{% hint style="danger" icon="circle-question" %}
У каждого автомобиля должен быть один текущий владелец, но один человек может владеть несколькими автомобилями. Сейчас схема выглядит так:

```
owners

id | name | car_id
---+------+-------
1  | Анна | 100
2  | Иван | 103
```

```
cars

id  | model
----+---------
100 | BMW
101 | Audi
102 | Volvo
103 | Kia
```

`owners.car_id` — `FOREIGN KEY` на `cars.id`.

Правильно ли она спроектирована?
{% endhint %}

<details>

<summary>Ответ</summary>

Нет, схема спроектирована неправильно. По требованиям:

```
один владелец
      1
      │
      M
автомобили
```

Это связь **`1:M`**: один человек может владеть несколькими автомобилями, а каждый автомобиль принадлежит одному человеку. Сейчас FK находится не на той стороне:

```
owners.car_id → cars.id
```

Из-за этого в одной строке владельца можно сохранить только **один** `car_id`:

```
Анна | car_id = 100
```

Куда тогда записать второй автомобиль — непонятно.

Кроме того, если на `owners.car_id` нет `UNIQUE`, база даже позволит:

```
Анна | 100
Иван | 100
```

то есть один автомобиль окажется одновременно у двух владельцев.

Для связи `1:M` FK должен находиться на стороне **M**, то есть в `cars`:

```
owners

id | name
---+------
1  | Анна
2  | Иван
```

```
cars

id  | model | owner_id
----+-------+---------
100 | BMW   | 1
101 | Audi  | 1
102 | Volvo | 1
103 | Kia   | 2
```

Связь:

```
cars.owner_id
      ↓
owners.id
```

Если по условию **каждый автомобиль обязательно должен иметь владельца**, то:

```
owner_id BIGINT NOT NULL REFERENCES owners(id)
```

Так Анна может встречаться в `cars.owner_id` сколько угодно раз, но у каждой конкретной машины хранится ровно один текущий владелец.

</details>

## Вопросы

{% hint style="info" icon="gitbook" %}
#### Что такое база данных и СУБД? Чем отличается БД от СУБД?

**База данных** — организованная совокупность данных, предназначенная для долговременного хранения и использования. Например, БД интернет-магазина может содержать данные о пользователях, заказах и товарах.

**СУБД** — программное обеспечение, которое управляет базами данных: хранит и изменяет данные, выполняет запросы, проверяет ограничения и организует совместную работу нескольких клиентов.

Например, PostgreSQL — это СУБД, а конкретная база `shop`, которой она управляет, — БД. На практике СУБД часто называют БД.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое таблица, строка, столбец?

* **Таблица** хранит множество однотипных записей с одинаковой структурой (набором полей).
* **Столбцы** описывают свойства этих записей, например `id`, `name`, `email`.
* **Строка** представляет одну конкретную запись, например, конкретного пользователя.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое первичный ключ (PK)? Какими свойствами он обладает?

**Первичный ключ, или `PRIMARY KEY`,** — столбец (или набор столбцов), который однозначно идентифицирует строку таблицы.

Например, если `users.id` является PK, то двух пользователей с `id = 10` в таблице быть не может.

Значения первичного ключа должны быть уникальными и не могут быть `NULL`. В таблице может быть только один `PRIMARY KEY`, но он может быть составным (включать в себя несколько столбцов). Первичный ключ не обязан называться `id` и может быть любого типа.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое внешний ключ (FK)? Зачем он нужен?

**Внешний ключ, или `FOREIGN KEY` (FK),** — столбец или набор столбцов одной таблицы, который ссылается на столбец другой таблицы.

Например, в заказе может быть ссылка на пользователя, которому он принадлежит:

```
orders.user_id → users.id
```

Главная задача FK — поддерживать ссылочную целостность данных. Если `orders.user_id` является внешним ключом, БД не позволит записать ссылку на несуществующего пользователя.

В отличие от PK, значение FK не обязано быть уникальным: один пользователь может иметь много заказов, поэтому его `id` может многократно встречаться в `orders.user_id`.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Какие бывают типы связей между таблицами: 1:1, 1:M, M:M? Как они реализуются?

*   **`1:1`** — одной записи первой таблицы соответствует одна запись второй.<br>

    Обычно реализуется внешним ключом + ограничением уникальности.<br>

    Например, `user_profiles.user_id` — `FK` на `users.id` и одновременно `UNIQUE`, чтобы у пользователя было не более одного профиля.
*   **`1:M`** — одной записи первой таблицы соответствует много записей второй.<br>

    Внешний ключ располагается на стороне «много».<br>

    Например, один пользователь имеет много заказов, поэтому `orders.user_id` — FK на `users.id`.
*   **`M:M`** — каждой записи с обеих сторон может соответствовать много записей с другой стороны.<br>

    Такая связь реализуется через промежуточную таблицу с двумя внешними ключами.<br>

    Например, связь заказов и товаров можно хранить в `order_items` со столбцами `order_id` и `product_id`. Таким образом, `M:M` фактически превращается в две связи `1:M`.
{% endhint %}
