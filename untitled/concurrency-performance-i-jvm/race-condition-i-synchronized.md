# Race condition и synchronized

Главная проблема многопоточности в Java: у каждого потока свой Stack, но объекты в Heap могут быть общими.

Например, два потока могут работать с одним объектом статистики:

```
Thread 1 ─┐
          ├──→ PaymentStatistics@1
Thread 2 ─┘
```

Пока оба потока только читают данные, проблем обычно нет. Сложность появляется, когда несколько потоков одновременно **изменяют одно и то же значение**.

Представим счётчик обработанных платежей:

```java
class PaymentStatistics {

    private int processedPayments;

    public void paymentProcessed() {
        processedPayments++;
    }
}
```

На первый взгляд кажется, что `processedPayments++` — одна операция. Но на самом деле `++` состоит из трёх действий:

1. прочитать текущее значение `processedPayments`
2. прибавить 1
3. сохранить в `processedPayments` новое значение

Допустим:

```
processedPayments = 10
```

Два потока одновременно обработали по одному платежу. Ожидаем `12`. Но выполнение может быть такое:

<figure><img src="../.gitbook/assets/image (24).png" alt="" width="563"><figcaption></figcaption></figure>

В результате `processedPayments = 11`, хотя было обработано два платежа. Один инкремент потерялся.

***

## Race condition

Проблема возникла потому, что результат программы стал зависеть от того, **в каком порядке потоки выполнят свои действия**.

> **Race condition** — ситуация, когда результат работы программы зависит от порядка работы нескольких потоков.

В примере выше возможен вариант, когда выполнение даст ожидаемый результат:

<figure><img src="../.gitbook/assets/image (25).png" alt="" width="563"><figcaption></figcaption></figure>

Результат:

```
12
```

Но возможен и другой порядок:

```
Thread 1 прочитал 10
Thread 2 прочитал 10
Thread 1 записал 11
Thread 2 записал 11
```

Результат:

```
11
```

Код **один и тот же**, входные данные **одни и те же**, но результат зависит от того, как операционная система чередовала потоки. Это и есть race condition.

Суть race condition не просто в том, что в приложении существует несколько потоков. Например, если каждый поток работает только со своими локальными переменными:

```java
public void process() {
    int attempt = 1;
}
```

у каждого вызова будет свой `attempt` в своём Stack Frame, и race condition не возникнет.

Или если потоки работают с одним объектом в heap, но этот объект не изменяемый — race condition тоже не будет.

Проблема появляется, когда потоки работают с **общим изменяемым состоянием.**

***

### Критическая секция

Вернёмся к:

```java
public void paymentProcessed() {
    processedPayments++;
}
```

Опасная часть здесь:

```
processedPayments++;
```

Именно во время выполнения этих действий другой поток не должен вмешиваться. Такая часть программы называется **критической секцией**.

> **Критическая секция** — участок кода, который работает с общим изменяемым ресурсом и для корректной работы не должен одновременно выполняться несколькими потоками.

При этом весь метод не обязательно должен быть критической секцией. Допустим:

```java
public void processPayment(Payment payment) {
    validate(payment);
    calculateCommission(payment);

    processedPayments++;

    logResult(payment);
}
```

Если:

```java
validate()
calculateCommission()
logResult()
```

не работают с тем же общим изменяемым состоянием, защищать от одновременного выполнения нужно только `processedPayments++`.&#x20;

Чем меньше критическая секция, тем меньше времени потоки мешают друг другу работать.

***

## Атомарная операция

`processedPayments++` будет корректно работать, если будет для других потоков выглядеть как **одно неделимое действие**:

```
10 → 11
```

а не:

```
прочитать 10
↓
посчитать 11
↓
записать 11
```

> **Атомарная операция** — операция, которая относительно других потоков выполняется как единое неделимое действие: либо полностью выполнена, либо полностью не выполнена, без промежуточных состояний.

Одна строка Java-кода не означает одну атомарную операцию: `i++`, `balance = balance - amount`, `count += 10` содержат чтение текущего значения, вычисление нового и запись результата. Поэтому сами по себе такие операции не являются безопасными для одновременного изменения несколькими потоками.

***

## Монитор

Нам нужен механизм, который позволит сказать:

> Этот участок кода сейчас выполняет Thread 1. Пока он не закончит, Thread 2 сюда заходить нельзя.

В Java для этого можно использовать **монитор**. Упрощённо монитор можно представить как замок, связанный с объектом. Поток перед входом в защищённый участок должен получить этот монитор.

Важно, что потоки должны использовать **один и тот же монитор**. Если Thread 1 синхронизируется на одном объекте, а Thread 2 на другом, они друг друга не блокируют.

***

## `synchronized`

Для работы с монитором в Java есть ключевое слово `synchronized`.

Например:

```java
class PaymentStatistics {

    private int processedPayments;

    public synchronized void paymentProcessed() {
        processedPayments++;
    }
}
```

Теперь, прежде чем выполнить `paymentProcessed()`, поток должен получить монитор.

Для такого `synchronized` instance-метода монитором является `this`, то есть текущий объект `PaymentStatistics`:

```java
PaymentStatistics statistics = new PaymentStatistics();
```

Если два потока вызывают:

```java
statistics.paymentProcessed();
```

Получаем:

```
Thread 1
   │
   ▼
пытается получить monitor statistics
   │
   ▼
получает
   │
   ▼
processedPayments++
   │
   ▼
освобождает monitor
```

Если Thread 2 приходит в этот момент:

```
Thread 2
   │
   ▼
пытается получить тот же monitor statistics
   │
   ▼
monitor занят
   │
   ▼
ждёт
```

После завершения первого потока второй сможет войти в метод. В результате операции уже не перемешиваются:

```java
processedPayments = 10

Thread 1:
10 → 11

Thread 2:
11 → 12
```

Получаем правильный результат, `12`.

***

`synchronized` гарантирует, что один и тот же монитор одновременно может удерживать только один поток. Поэтому два участка кода, защищённые **одним монитором**, не выполняются одновременно.

Когда один поток закончил изменение данных внутри `synchronized` и освободил монитор, следующий поток, получивший **тот же монитор**, увидит сделанные изменения.

То есть `synchronized` решает сразу две связанные проблемы:

* не даёт потокам одновременно менять защищённое состояние
* делает изменения одного потока видимыми следующему потоку

***

### `synchronized` instance-метод

Первый вариант:

```java
class PaymentStatistics {

    private int processedPayments;

    public synchronized void paymentProcessed() {
        processedPayments++;
    }
}
```

Монитор: `this`.

Можно представить так:

```java
public void paymentProcessed() {
    synchronized (this) {
        processedPayments++;
    }
}
```

Допустим:

```java
PaymentStatistics statistics = new PaymentStatistics();
```

Тогда:

```java
statistics.paymentProcessed();
```

синхронизируется на `statistics`.

Что если объектов два?

```java
PaymentStatistics first = new PaymentStatistics();
PaymentStatistics second = new PaymentStatistics();
```

Thread 1 вызывает:

```java
first.paymentProcessed();
```

Thread 2:

```java
second.paymentProcessed();
```

Мониторы разные:

* Thread 1 — monitor `first`&#x20;
* Thread 2 — monitor `second`

Поэтому оба метода **могут выполняться одновременно**.

> `synchronized` instance-метод защищает **конкретный экземпляр**, а не все объекты этого класса вообще.

***

### `static synchronized`-метод

Теперь допустим, состояние относится не к конкретному объекту, а ко всему классу:

```java
class PaymentStatistics {

    private static int processedPayments;

    public static synchronized void paymentProcessed() {
        processedPayments++;
    }
}
```

У `static`-метода нет `this`, потому что метод относится к классу, а не конкретному объекту. В этом случае монитором будет объект `PaymentStatistics.class`:

```java
public static void paymentProcessed() {
    synchronized (PaymentStatistics.class) {
        processedPayments++;
    }
}
```

```java
Thread 1 ─┐
          ├──→ monitor PaymentStatistics.class
Thread 2 ─┘
```

Поэтому вызовы `static synchronized`-метода будут синхронизироваться между собой независимо от того, сколько объектов `PaymentStatistics` создано.

***

Это частый вопрос на собеседованиях.

```java
public synchronized void instanceMethod() { // использует this
    ...
}
```

```java
public static synchronized void staticMethod() { // использует PaymentStatistics.class
    ...
}
```

Поэтому один поток может выполнять `instanceMethod()`, а другой одновременно `staticMethod()` — у них два разных монитора.

***

### `synchronized`-блок

Иногда защищать весь метод — слишком дорого. Например:

```java
public void processPayment(Payment payment) {
    validate(payment);
    calculateCommission(payment);

    synchronized (this) {
        processedPayments++;
    }

    logPayment(payment);
}
```

Здесь монитор нужен только на время `processedPayments++`, и нет смысла синхронизировать весь метод.

Если бы мы сделали `synchronized processPayment`, то один поток ждал бы не только пока второй увеличит счетчик, но и пока он выполнит валидацию, вычисление комиссии и логирование, хотя эти действия вполне можно выполнять одновременно. **В итоге выполнение кода бы сильно замедлилось без реальной необходимости.**

> `synchronized`-блок позволяет явно выбрать объект-монитор и ограничить размер критической секции.

Синтаксис:

```java
synchronized (monitor) {
    // критическая секция
}
```

Например:

```java
synchronized (this) {
    processedPayments++;
}
```

или можно завести отдельный объект:

```java
class PaymentStatistics {

    private final Object lock = new Object();

    private int processedPayments;

    public void paymentProcessed() {
        synchronized (lock) {
            processedPayments++;
        }
    }
}
```

Теперь монитором является внутренний `lock`. Это удобно, потому что объект используется специально для синхронизации только внутри класса, извне его не сможет захватить еще какой-то поток.

***

Ошибочный код:

```java
private final Object lock1 = new Object();
private final Object lock2 = new Object();

public void increment1() {
    synchronized (lock1) {
        processedPayments++;
    }
}

public void increment2() {
    synchronized (lock2) {
        processedPayments++;
    }
}
```

Каждый метод отдельно выглядит синхронизированным, но мониторы разные. Поэтому оба потока могут одновременно менять `processedPayments`, и race condition остаётся.

Правильно:

```java
private final Object lock = new Object();

public void increment1() {
    synchronized (lock) {
        processedPayments++;
    }
}

public void increment2() {
    synchronized (lock) {
        processedPayments++;
    }
}
```

Теперь оба пути доступа к общему состоянию используют один монитор.

> Недостаточно просто написать `synchronized`. Все операции с общим состоянием, которые должны быть согласованы между собой, должны использовать **один и тот же монитор**.

### Что не стоит делать внутри `synchronized`

Основное правило:

> Критическую секцию желательно делать настолько маленькой, насколько это возможно без нарушения корректности.

Особенно нежелательно держать monitor во время операций, которые могут выполняться долго и время которых плохо предсказуемо — например, во время обращения к другим сервисам по HTTP.

```java
synchronized (lock) {
    // пока HTTP-запрос выполняется, другие потоки ждут
    bankClient.sendRequest(payment);
}
```

Пока он выполняется, , которым нужен `lock`, будут ждать.

То же относится к запросам в БД, операциям с файлами и просто тяжёлым вычислениям. Чем  дольше поток держит monitor, тем дольше остальные потоки ждут, и тем меньше реальной пользы от многопоточности.

## Вопросы

{% hint style="info" icon="gitbook" %}
#### Дайте определение критической секции.

**Критическая секция** — участок кода, работающий с общим изменяемым состоянием, который для сохранения корректности не должен одновременно выполняться несколькими потоками.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое состояние гонки (race condition)? Приведите пример ситуации, в которой оно может возникнуть.

**Race condition** — ситуация, когда результат программы зависит от порядка выполнения нескольких потоков.

Например, два потока одновременно выполняют `processedPayments++`. Оба могут одновременно прочитать значение `10`, вычислить `11` и записать `11`, поэтому вместо ожидаемого `12` получим `11`. Причина в том, что `++` — составная операция: нужно прочитать значение, изменить его и записать обратно.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое атомарная операция?

**Атомарная операция** выполняется относительно других потоков как одно неделимое действие: другой поток не может вмешаться в середину операции или увидеть её частично выполненной, она для внешнего кода всегда либо полностью выполнена, либо полностью не выполнена.

На примере с `++` видно, что одна строка Java-кода не обязательно является атомарной.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое монитор в Java?

**Монитор** — механизм синхронизации, связанный с объектом. Поток должен получить monitor объекта, прежде чем войти в участок кода, синхронизированный на этом объекте. Одновременно один monitor может удерживать только один поток; остальные потоки, которым нужен тот же monitor, ждут его освобождения.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Ключевое слово `synchronized`.

Ключевое слово `synchronized` используется для защиты критической секции. Перед входом поток получает monitor, а при выходе освобождает его. Поэтому два участка кода, синхронизированные на одном monitor, не могут одновременно выполняться разными потоками.

Кроме взаимного исключения, `synchronized` гарантирует видимость изменений: после освобождения monitor одним потоком следующий поток, получивший тот же monitor, увидит сделанные изменения.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Какие существуют варианты использования `synchronized` (instance-метод, `static`-метод, `synchronized`-блок)? Какой объект используется в качестве монитора в каждом случае?

У `synchronized` есть три основных варианта.

1. Instance-метод:

```java
public synchronized void method() {
    ...
}
```

Используется monitor текущего объекта — `this`. Поэтому два потока, вызывающие метод на одном экземпляре (объекте) класса, синхронизируются между собой, а на разных экземплярах — нет.

2. `static synchronized` метод:

```java
public static synchronized void method() {
    ...
}
```

Используется monitor объекта класса — `ClassName.class`. Он общий для всех экземпляров этого класса.

3. `synchronized`-блок:

```java
synchronized (lock) {
    ...
}
```

используется monitor объекта, указанного в скобках — в этом примере `lock`.

Важно, чтобы разные участки кода, защищающие одно общее состояние, использовали **один и тот же monitor**. Иначе `synchronized` не исключит их одновременное выполнение.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Какие операции не рекомендуется выполнять внутри `synchronized`-блока и почему?

Внутри `synchronized` не рекомендуется без необходимости выполнять долгие операции: сетевые запросы, обращения к БД, работу с файлами и тяжёлые вычисления.

Пока поток выполняет такой код, он продолжает удерживать monitor. Другие потоки, которым нужен тот же monitor, вынуждены ждать, поэтому растёт задержка и уменьшается польза от многопоточности.

Критическую секцию желательно делать минимальной, но нельзя выносить из неё действия, которые должны выполняться вместе. Например, проверка баланса и его последующее изменение должны защищаться как одна операция: если отпустить monitor между проверкой и изменением, другой поток может успеть изменить баланс.
{% endhint %}
