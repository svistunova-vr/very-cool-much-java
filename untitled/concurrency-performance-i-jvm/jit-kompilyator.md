# JIT-компилятор

Рассмотрим простой метод для расчёта комиссии платежа:

{% code collapsedlinecount="10" %}
```java
public long calculateCommission(Payment payment) {
    return payment.getAmount() / 100;
}
```
{% endcode %}

Исходный Java-код процессор напрямую выполнить не может. Сначала `javac` (отдельная программа для компиляции Java-кода, идет в комплекте с Java) компилирует его в **bytecode**:

{% code collapsedlinecount="10" %}
```
PaymentService.java
        ↓
      javac
        ↓
PaymentService.class
        ↓
     bytecode
```
{% endcode %}

Bytecode — промежуточный набор инструкций JVM. Он не привязан, например, конкретно к процессорам Intel или ARM. Поэтому один и тот же `.class` может запускаться на разных устройствах, если для них существует подходящая JVM.

Но процессор в конечном итоге всё равно умеет выполнять не Java bytecode, а **машинные инструкции конкретного процессора**. Получается, JVM нужно каким-то образом превратить Java bytecode в машинный код.

Для этого в HotSpot используются интерпретатор и JIT-компиляторы.

***

## Интерпретатор

Начнём с самого простого варианта. Допустим, JVM получила bytecode метода `calculateCommission`. **Интерпретатор** может последовательно читать команды bytecode и сразу выполнять соответствующие действия.

Упрощённо:

{% code collapsedlinecount="10" %}
```
bytecode команда
        ↓
интерпретатор понимает, что она означает
        ↓
выполняет нужное действие
        ↓
берёт следующую команду
        ↓
...
```
{% endcode %}

JVM не обязана заранее преобразовывать весь `.class` в машинный код. Это удобно, потому что приложение запускается быстро.

Но здесь появляется проблема. Один раз интерпретировать метод `calculateCommission()` — не страшно, но если это платежный сервис, через который проходит много запросов:

{% code collapsedlinecount="10" %}
```
calculateCommission() → 1-й вызов
calculateCommission() → 2-й вызов
calculateCommission() → 3-й вызов
...
calculateCommission() → 1 000 000-й вызов
```
{% endcode %}

Но если каждый раз заново интерпретировать одни и те же bytecode-инструкции, приложение будет выполнять лишнюю работу.

***

## JIT-компилятор

> **JIT (Just-In-Time compiler)** — компилятор, который работает во время выполнения программы и преобразует часто выполняемый bytecode в машинный код.

Например, JVM некоторое время работает и видит, что метод `calculateCommission()` вызывается очень часто. Такой часто выполняемый код называют **hot code**, а метод — **hot method**.

В какой-то момент JVM может решить: этот метод используется настолько часто, что выгоднее один раз потратить время на его компиляцию, а затем выполнять уже готовый машинный код.

Получаем:

{% code collapsedlinecount="10" %}
```
calculateCommission() bytecode
             ↓
         JIT compiler
             ↓
машинный код для текущего CPU
```
{% endcode %}

После этого следующие вызовы метода могут использовать уже скомпилированную версию:

{% code collapsedlinecount="10" %}
```
calculateCommission()
        ↓
готовый machine code
        ↓
CPU выполняет его напрямую
```
{% endcode %}

***

### Почему тогда не скомпилировать сразу всё приложение?

Можно было бы при запуске взять все методы приложения и сразу скомпилировать каждый. Но это тоже дорого.

Представим приложение, в котором есть:

{% code collapsedlinecount="10" %}
```java
createPayment()
calculateCommission()
cancelPayment()
generateYearlyReport()
migrateLegacyPayment()
...
```
{% endcode %}

`calculateCommission()` вызывается тысячи раз в секунду. `generateYearlyReport()` запускается раз в год. `migrateLegacyPayment()` вообще существует только для старых данных и в обычной работе может ни разу не вызваться.

Если JVM при старте будет тщательно компилировать и оптимизировать **все** методы, мы потратим CPU и время на код, который, возможно, вообще никогда не понадобится.

Поэтому используется другой подход: код выполняется, JVM наблюдает, какие методы действительно часто используются и компилирует в машинный код именно их.

***

JIT может убрать лишний вызов метода. Например:

{% code collapsedlinecount="10" %}
```java
class Payment {

    private long amount;

    public long getAmount() {
        return amount;
    }
}
```
{% endcode %}

{% code collapsedlinecount="10" %}
```java
public long calculateCommission(Payment payment) {
    return payment.getAmount() / 100;
}
```
{% endcode %}

В исходном Java-коде явно присутствует вызов: `payment.getAmount()`, но если JIT видит, что маленький метод `getAmount()` постоянно используется здесь, он **может встроить его код непосредственно в вызывающий метод**.

Вместо:

{% code collapsedlinecount="10" %}
```java
return payment.getAmount() / 100;
```
{% endcode %}

получится что-то близкое по смыслу к:

{% code collapsedlinecount="10" %}
```java
return payment.amount / 100;
```
{% endcode %}

То есть отдельный вызов `getAmount()` больше не нужен. Такая оптимизация называется **method inlining — встраивание метода**.

Реальный JIT выполняет значительно больше оптимизаций, но сейчас достаточно понимать общую идею: JVM может преобразовать байткод так, чтобы он работал эффективнее.

Какие именно оптимизации будут применены к конкретному методу, заранее гарантировать нельзя — решение принимает JIT во время работы JVM.

***

### Где хранится скомпилированный код

Ранее мы разбирали основные области памяти: Heap, Stack, Metaspace. У HotSpot есть еще одна отдельная область — **Code Cache**. JIT-компилятор получает байткод, создает нативный машинный код, и HotSpot сохраняет скомпилированный код в этой области.

***

## C1 и C2

В современном HotSpot используется **tiered compilation — многоуровневая компиляция**.

У HotSpot есть два JIT-компилятора:

* **C1** компилирует относительно быстро, но не делает сложные оптимизации
* **C2** компилирует дольше, зато способен сильнее оптимизировать код

Получается компромисс: если сразу отправить каждый метод в C2, то после долгой тщательной компиляции и оптимизации получим очень хороший машинный код, но потратим много времени. Если всегда использовать только быструю компиляцию, получим не такой оптимизированный код.

Поэтому HotSpot комбинирует подходы:

1. Программа начинает работать, метод вызывается
2. Интерпретатор выполняет байткод — преобразует каждую команду по порядку в машинный код и выполняет, но пока не сохраняет этот машинный код в Code Cache. JVM в это время собирает статистику по вызовам методов.
3. Какой-то метод по статистике вызывается достаточно часто.
4. C1 компилирует его в машинный код и сохраняет в Code Cache, в следующий раз интерпретатор берет уже готовую версию из кеша.
5. Метод продолжает использоваться очень часто.
6. C2 повторно компилирует тот же байткод и использует уже более дорогие оптимизации. Его версия тоже сохраняется в Code Cache.
7. Интерпретатор теперь использует версию C2 из кеша.

Реальный HotSpot не гарантирует, что каждый метод обязательно строго проходит Interpreter → C1 → C2. Tiered compilation устроена сложнее, и JVM сама решает, какие уровни использовать. Но как базовая модель для понимания JIT и для ответа на собеседовании эта последовательность подходит.

***

### Hot циклы

Представим:

{% code collapsedlinecount="10" %}
```java
public long calculateTotal(List<Payment> payments) {
    long total = 0;

    for (Payment payment : payments) {
        total += payment.getAmount();
    }

    return total;
}
```
{% endcode %}

Метод `calculateTotal(payments)` может быть вызван всего один раз, но внутри него для списка `payments` размером 10 000 000 тело цикла выполнится десять миллионов раз.

Поэтому JVM оптимизирует не только количество вызовов методов, но и интенсивно выполняющиеся циклы.

***

## Разогрев приложения

Из-за JIT-компиляции Java-приложение сразу после запуска может работать иначе, чем через несколько минут.

Представим только что запущенный платежный сервис. В первые секунды JVM ещё практически ничего не знает о его реальной нагрузке — какие методы и участки кода будут вызываться часто и что действительно стоит оптимизировать.

Когда начинают приходить запросы, JVM выполняет код и одновременно собирает статистику. Если метод становится hot, он оптимизируется.

Начальный период называют **warm-up — разогревом приложения**.

После разогрева приложение приближается к стабильному режиму работы, когда основные часто используемые участки кода уже скомпилированы и оптимизированы.

Разогрев — не только JIT. На первые запросы могут влиять и другие процессы: инициализация классов, создание lazy объектов, заполнение кешей, установление соединений с БД и т. д.

***

HotSpot позволяет вывести информацию о том, какие методы JIT компилирует:

{% code collapsedlinecount="10" %}
```bash
java -XX:+PrintCompilation Application
```
{% endcode %}

В консоли будут появляться записи о компиляции.

Для обычной разработки следить за этим логом постоянно не нужно — он полезен именно для понимания механизма.

***

## Вопросы

{% hint style="info" icon="gitbook" %}
#### Объясните принцип работы JIT-компилятора в JVM.

`javac` сначала компилирует Java-код в bytecode, который можно одинаково запускать на любой ОС. JVM выполняет этот bytecode с помощью интерпретатора, переводя по очереди каждую команду байткода в машинный код конкретной ОС. Но постоянно заново преобразовывать одни и те же команды в машинный код неэффективно. Поэтому HotSpot во время работы приложения собирает статистику и определяет часто выполняемые методы и циклы — hot code.

**JIT (Just-In-Time compiler)** во время работы JVM компилирует такой bytecode в машинный код для текущего процессора и сохраняет его в Code Cache. Последующие вызовы берут уже готовый machine code из кеша, а не преобразуют его заново. При этом JIT может применять дополнительные оптимизации.

В HotSpot используется tiered compilation: сначала для JIT используется более быстрый C1-компилятор, и только для самого hot кода используется C2 — он тратит на оптимизацию больше времени, но код получается максимально эффективным.

Такой подход позволяет не тратить много времени при запуске на оптимизацию всего приложения, но при этом получить высокую производительность часто используемого кода после некоторого времени работы.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Что такое «разогрев» приложения?

**Разогрев приложения (warm-up)** — период после запуска, когда JVM ещё собирает информацию о реальном поведении программы, определяет hot code и JIT-компилирует и оптимизирует его. Поэтому первые вызовы некоторого кода могут выполняться медленнее, чем после разогрева.
{% endhint %}
