# Основные термины многопоточности

## Процесс

Представим обычный Java-сервис обработки платежей. Пользователи одновременно отправляют запросы:

* пользователь A → оплатить заказ
* пользователь B → перевести деньги
* пользователь C → получить историю операций

Когда мы запускаем Java-сервис, операционная система создаёт для него **процесс**.

> **Процесс** — экземпляр запущенной программы со своей областью памяти и ресурсами операционной системы.

Например, если на компьютере запущены Java-сервис платежей, IntelliJ IDEA, браузер и PostgreSQL, все это — разные процессы.

У каждого процесса своё адресное пространство памяти. **Адресное пространство** — это набор адресов памяти, которыми этот процесс может пользоваться. Когда операционная система запускает программу, процесс получает своё **виртуальное адресное пространство**. Внутри него находятся память самого приложения, Heap, Stack потоков, загруженные библиотеки и другие данные процесса.

Например:

```
Process A

виртуальный адрес 0x1000 → данные Process A
виртуальный адрес 0x2000 → объект Payment
```

```
Process B

виртуальный адрес 0x1000 → другие данные
виртуальный адрес 0x2000 → другой участок памяти
```

То есть даже одинаковый адрес `0x2000` в двух процессах **не обязан означать одну и ту же физическую память**. Операционная система изолирует процессы друг от друга и сама сопоставляет их виртуальные адреса с реальной памятью компьютера.

Поэтому если Java-процесс создал:

```java
Payment payment = new Payment();
```

объект находится в Heap **этой JVM**, а ссылка `payment` имеет смысл внутри её адресного пространства.

Другой Java-процесс имеет другой JVM process ⇒ другое адресное пространство, и не может случайно взять ссылку `payment` первого процесса и использовать её.

Если двум процессам нужно обменяться данными, для этого нужен отдельный механизм: например, сеть, файл или другой способ межпроцессного взаимодействия.

***

## Поток

Один процесс может выполнять не одну последовательность действий, а несколько. Например, наш Java-сервис одновременно: обрабатывает запросы пользоватей A, B и C. Для этого внутри процесса существуют **потоки — threads**.

Процесс удобно представить как контейнер с ресурсами, а потоки — как независимые пути выполнения кода внутри этого контейнера.

<figure><img src="../.gitbook/assets/image (22).png" alt=""><figcaption></figcaption></figure>

При этом все эти потоки относятся к **одному и тому же процессу**. Процесс владеет ресурсами, а поток выполняет код, используя ресурсы своего процесса.

***

Например, если запустить два экземпляра одного Java-приложения:

```
java PaymentApplication
java PaymentApplication
```

получим два процесса:

```
Process 1
├── Heap 1
└── Threads

Process 2
├── Heap 2
└── Threads
```

Объект `Payment@1` в `Heap 1` не является общим с `Process 2`.

А если один процесс содержит два потока:

```
Process 1

Heap
└── Payment@1

Thread 1 ──→ Payment@1
Thread 2 ──→ Payment@1
```

они могут использовать один объект.

***

#### Зачем одному процессу несколько потоков

Представим сервер, который умеет обрабатывать только один запрос за раз. Приходит запрос пользователя A — сервис начинает его выполнять. Во время обработки нужно обратиться в базу данных. Ответ базы занимает, допустим, 200 ms. Если в это время приложение вообще ничего другого делать не может, запросы других пользователей будут стоять в очереди:

```
A → работает / ждёт БД

B → ждёт завершения A
C → ждёт завершения A
D → ждёт завершения A
```

Для серверного приложения это очень неудобно. Если есть несколько потоков, один поток может ждать результат операции, а другие в это время выполнять другие запросы:

```
Thread 1 → запрос A → ждёт БД

Thread 2 → запрос B → выполняется

Thread 3 → запрос C → выполняется
```

***

## Что такое многопоточность

> **Многопоточность** — организация программы, при которой внутри одного процесса существуют несколько потоков выполнения, способных выполнять разные задачи в одни и те же промежутки времени.

Например:

```
Java process

Thread 1 → обработка платежа A
Thread 2 → обработка платежа B
Thread 3 → получение истории операций
```

Это не обязательно означает, что в каждую наносекунду все три потока реально выполняют инструкции одновременно.

***

#### Как один CPU может выполнять несколько потоков?

Представим для простоты процессор с одним ядром. Одно ядро физически не может в один момент времени выполнять инструкции сразу трёх обычных потоков.

Поэтому операционная система может дать CPU одному потоку и затем переключиться:

```
Thread 1
██████

      Thread 2
      ██████
```

Такие небольшие интервалы быстро чередуются:

<figure><img src="../.gitbook/assets/image (23).png" alt=""><figcaption></figcaption></figure>

Со стороны может казаться, что задачи выполняются одновременно, хотя в конкретный момент ядро выполняет только одну из них.

Когда система приостанавливает выполнение одного потока и продолжает другой, это называется **context switch — переключение контекста**. Чтобы позже продолжить первый поток, нужно сохранить его текущее состояние, а при возвращении восстановить его. Поэтому такие переключения требуют дополнительных ресурсов.

***

Теперь допустим, что CPU имеет несколько ядер. Тогда разные потоки действительно могут выполнять инструкции **одновременно**:

```
Core 1 → Thread 1
Core 2 → Thread 2
Core 3 → Thread 3
```

Это уже будет по-настоящему параллельное выполнение. Получается:

> Несколько потоков позволяют задачам выполняться конкурентно, но настоящая параллельность зависит от количества доступных вычислительных ресурсов.

Например, мы можем запустить 100 потоков на 4 ядрах, но в реальности CPU одновременно выполняет инструкции не всех 100 потоков, а только 4, и переключается между тем, какие 4 из 100 в данный момент выполняются.

***

### Преимущества многопоточности

Главное преимущество: пока одна задача ждет каких-то внешних ресурсов, процесс может заниматься другой.

```
Thread 1 → отправил SQL-запрос → ждёт PostgreSQL

Thread 2 → в это время обрабатывает другой HTTP-запрос

Thread 3 → в это время выполняет ещё одну задачу
```

CPU не простаивает.

Это особенно полезно для операций, где много ожидания: БД, HTTP-запросы к другим сервисам, файлы.

Многопоточность также позволяет использовать несколько ядер CPU. Если две независимые вычислительные задачи действительно можно разделить:

```
Task A → Core 1
Task B → Core 2
```

они могут закончиться быстрее, чем при последовательном выполнении на одном ядре.

***

### Недостатки многопоточности

Общая память создаёт основную сложность. Представим:

```java
class PaymentStatistics {

    private int processedPayments;
}
```

И два потока используют **один обект сервиса**:

```
Thread 1 ─┐
          ├──→ PaymentStatistics@1
Thread 2 ─┘
```

Если оба потока только читают значение, всё относительно просто. Но если оба начинают одновременно изменять его, уже важно: какой поток выполнил действие первым? что успел прочитать второй? какое значение увидит каждый?

Одно и то же приложение может получать разные результаты в зависимости от того, в каком порядке операционная система дала потокам выполнять инструкции.

***

Есть и стоимость самих потоков: для каждого потока нужно хранить его состояние выполнения, в частности Stack. Если создать очень много потоков:

```
Thread 1
Thread 2
Thread 3
...
Thread 50 000
```

это требует памяти. Кроме того, операционной системе приходится переключаться между ними:

```
Thread A → Thread B → Thread C → Thread A ...
```

Чем больше ненужных переключений, тем больше процессорного времени тратится не на бизнес-логику, а на сами переключения — сохранить контекст предыдущего потока, загрузить контекст следующего.

Поэтому больше потоков ≠ больше производительности.

Иногда добавление потоков ускоряет программу, иногда почти ничего не меняет, а иногда делает её медленнее.

***

## Конкурентность и параллельность

Представим две задачи, A и B. Если **одно** ядро выполняет их кусочками, переключаясь между ними:

```
время →

A ████        ████
B     ████████
```

Одновременно инструкции выполняются только для одной задачи. Это **concurrency — конкурентное выполнение**.

Если есть два ядра:

```
Core 1: A ███████████
Core 2: B ███████████
```

&#x20;`A` и `B` действительно исполняются в один момент времени, это **parallelism** — параллельное выполнение.

***

## Асинхронные вычисления

Теперь представим другую проблему. Методу нужно получить данные от внешнего банковского сервиса.

Синхронный вариант:

```
1. отправить запрос
2. ждать ответ
3. получить ответ
4. продолжить работу
```

Вызывающая операция **ждёт завершения другой операции**, прежде чем двигаться дальше.

При асинхронном подходе идея другая:

```
1. запустить операцию A
2. не ждать её завершения
3. заниматься другой работой
4. когда результат A будет готов — продолжить работу с ним
```

> **Асинхронность** — способ организации выполнения, при котором запуск операции не требует обязательно ждать её завершения прямо в месте запуска; результат может быть обработан позже.

***

#### **Асинхронность ≠ параллельность**

Допустим, есть задачи A и B — асинхронная система может выполнять их так:

```
A: начал работу
A: ждёт внешний ответ

B: выполняется

A: ответ пришёл
A: продолжился
```

```
время →

A ████.................████
B     █████████████████
```

Задачи могут выполняться на одном и том же ядре, асинхронность не требует обязательно параллельного выполнения.

***

#### **Параллельность ≠ асинхронность**

Например, нужно обработать два больших независимых массива данных. Можно дать их двум ядрам:

```
Core 1 → расчёт A
Core 2 → расчёт B
```

Обе задачи выполняются одновременно:

```
A ██████████████
B ██████████████
```

Это параллельность. Но вызывающий код может ждать:

```
запустили A и B
↓
ждём обе
↓
получили результаты
↓
продолжаем
```

Поэтому наличие параллельности само по себе ничего не говорит о том, является ли операция асинхронной.

***

#### Асинхронность и параллельность могут сочетаться

Например, приложение запускает две независимые операции и не ждёт завершения, а делает что-то еще. Если система при этом выполняет операции на разных ядрах, получаем одновременно асинхронность и параллельность.

* **Асинхронность** — должен ли вызывающий код ждать завершения операции?
* **Параллельность** — выполняются ли несколько операций физически одновременно?

## Вопросы

{% hint style="info" icon="gitbook" %}
#### В чем разница между процессом и потоком? Как потоки разделяют ресурсы внутри одного процесса?

**Процесс** — экземпляр запущенной программы со своим пространством памяти и ресурсами операционной системы. Например, запущенное Java-приложение работает внутри отдельного процесса.

**Поток** — последовательность инструкций внутри процесса. Один процесс может содержать несколько потоков.

Потоки одного Java-процесса используют общие ресурсы процесса. В частности, для них общий Heap, поэтому разные потоки могут обращаться к одному и тому же объекту. Metaspace с метаданными классов тоже используется совместно. При этом у каждого потока свой JVM Stack со своими stack frames и локальными переменными.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### Дайте определение многопоточности. Какие у нее преимущества и недостатки?

**Многопоточность** — организация программы, при которой внутри одного процесса используется несколько потоков выполнения.

Преимущества:

* можно обрабатывать несколько независимых задач, не останавливая весь процесс из-за ожидания одной из них
* эффективнее используется CPU во время операций с БД, сетью и другими внешними ресурсами
* при наличии нескольких ядер можно выполнять независимые вычисления физически параллельно

Недостатки:

* усложнение программы — потоки используют общую память, поэтому при одновременной работе требуется согласовывать доступ к данным
* потоки требуют памяти
* частые переключения между ними расходуют процессорное время

Поэтому увеличение количества потоков само по себе не гарантирует увеличение производительности.
{% endhint %}

{% hint style="info" icon="gitbook" %}
#### В чем разница между асинхронными и параллельными вычислениями?

**Асинхронность** — после запуска операции вызывающему коду не обязательно ждать её завершения, можно в это время заниматься другой работой, а результат обработать позже.

**Параллельность** — несколько операций физически выполняются одновременно, например на разных ядрах CPU.

Асинхронность не обязательно является параллельностью. Пока асинхронная операция ждёт ответа, другая работа может выполняться на том же ядре. И наоборот, две задачи могут выполняться параллельно на разных ядрах, но вызывающий код будет ждать завершения обеих, поэтому он не будет асинхронным.
{% endhint %}
