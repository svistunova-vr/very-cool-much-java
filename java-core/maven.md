# Maven

## Введение

Перед Maven нужно понять, как вообще Java-проект превращается из написанного нами кода в готовую для запуска программу. Допустим, мы написали:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello!");
    }
}
```

Этот код находится в файле `Main.java` и называется **исходный код (source code)**. Сюда же относятся любые другие `.java`-файлы в нашем проекте: `User.java`, `Payment.java`, `PaymentService.java` и т. д.

**JVM (Java Virtual Machine)** — это программа, которая умеет **запускать Java-приложения**. JVM нужна как промежуточный слой между Java-программой и конкретной операционной системой. Благодаря ей один и тот же Java-код можно запускать, например, на Windows, macOS и Linux — главное чтобы там была установлена JVM подходящей версии.

Но JVM не запускает `.java`-файлы как есть. Сначала код нужно **скомпилировать**.

***

> **Компиляция** — преобразование исходного Java-кода (`.java`) в байткод (`.class`), который умеет выполнять JVM.

Компиляцией занимается **компилятор Java** — `javac`. Например, можно написать в терминале:

```bash
javac Main.java
```

После этого появится новый файл `Main.class`. `.class` содержит **Java bytecode — байткод**. Это уже не исходный код, а инструкции для JVM на более низкоуровневом языке.

Если код нарушает правила Java (например, `int age = "Anna"`), ошибка обнаружится еще на этапе компиляции, и код не будет скомпилирован, пока ошибку не исправить.&#x20;

```java
Animal animal = new Cat();
animal.catchMouse();
```

если метода `catchMouse()` нет у статического типа `Animal`, — тоже ошибка компиляции.

***

После компиляции JVM может выполнить байткод. Вручную можно написать:

```bash
java Main
```

В IDE мы обычно нажимаем кнопку **Run**, поэтому эти действия скрыты и происходят автоматически.

***

> **Библиотека** — готовый чужой код, который мы подключаем к своему проекту, чтобы не писать всё самостоятельно.

Например, кто-то уже написал библиотеку для работы со строками. Мы можем использовать:

```java
StringUtils.isBlank(text);
```

вместо самостоятельной реализации всех подобных операций.

> **Зависимость (dependency)** — библиотека, которая используется в нашем проекте.

***

Java-проект может состоять из большого количества `.class` и вспомогательных файлов:

```
User.class
Order.class
Product.class
Main.class
application.properties
...
```

Перед использованием приложения или отправке его куда-либо их удобно собрать в один файл.

> **JAR (Java Archive)** — архив, в который можно упаковать Java-классы и другие файлы проекта.

> **Сборка (build)** — весь процесс подготовки проекта к использованию: компиляция кода, запуск тестов и создание готового `.jar`.

```
исходный код
     ↓
компиляция
     ↓
.class
     ↓
тесты
     ↓
упаковка
     ↓
.jar
```

> **Артефакт (artifact)** — готовый результат сборки проекта.

Например, `shop-1.0.0.jar` является артефактом — его можно запустить, загрузить на сервер, отправить другому разработчику или подключить в другой проект в качестве библиотеки.

***

## Зачем нужен Maven?

Представим реальный проект:

```
200 Java-классов
100 тестов
15 сторонних библиотек
```

Чтобы получить готовое приложение, нужно:

```
найти и скачать самостоятельно все нужные библиотеки
        ↓
добавить их в проект
        ↓
скомпилировать основной код
        ↓
скомпилировать тесты
        ↓
запустить тесты
        ↓
собрать .jar
```

Причём этот процесс нужно повторять каждому разработчику локально и в добавок на сервере.

> **Maven** — инструмент, который автоматизирует сборку Java-проекта и управление его зависимостями.

Вместо всех ручных действий можно просто написать:

```bash
mvn package
```

***

## `pom.xml`

`pom.xml` — главный файл Maven-проекта. POM — Project Object Model.

В нём описывается проект:

```xml
<project>
    ...
</project>
```

Например:

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.victory</groupId>
    <artifactId>shop</artifactId>
    <version>1.0.0</version>

    <name>Shop</name>
    <description>Приложение магазина</description>
</project>
```

Из `pom.xml` Maven узнаёт:

* что это за проект;
* какая у него версия;
* какие библиотеки ему нужны;
* как его собирать;
* какие плагины использовать;
* какие дополнительные настройки применить.

***

### Стандартная структура Maven-проекта

Maven ожидает определённую структуру каталогов:

```
project/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    └── test/
        ├── java/
        └── resources/
```

* `src/main/java` — основной код приложения (`User.java`, `OrderService.java`)
* `src/main/resources` — вспомогательные файлы (ресурсы) приложения: файлы с настройками, шаблоны email-ов, html-страницы и т. д.
* `src/test/java` — тесты для автоматической проверки функционала

После сборки Maven создаёт каталог `target/`:

```
target/
├── classes/
├── test-classes/
└── shop-1.0.0.jar
```

`target` — результат сборки, поэтому его обычно не добавляют в Git (каждый разработчик запускает `mvn package` и `.jar` собирается у него локально).

***

## Зависимости

Допустим, в приложении хотим использовать стороннюю библиотеку. Без Maven пришлось бы найти `.jar`, скачать его и вручную подключить к проекту. С Maven достаточно добавить зависимость в `pom.xml`:

```xml
<dependencies>

    <dependency>
        <groupId>org.apache.commons</groupId>
        <artifactId>commons-lang3</artifactId>
        <version>3.18.0</version>
    </dependency>

</dependencies>
```

После этого Maven сам скачает библиотеку.

***

### Откуда Maven скачивает библиотеки?

Обычно Maven ищет зависимости в **репозиториях**. Репозиторий — хранилище готовых библиотек. Одно из основных публичных хранилищ — Maven Central.

На компьютере также есть **локальный Maven repository**. Его местонахождение зависит от ОС, например: `~/.m2/repository`. Это просто папка, где Maven сохраняет однажды скачанные из Maven Central библиотеки, чтобы, если они понадобятся еще в каком-то проекте, не скачивать их заново.

***

## Координаты Maven

Maven-артефакт идентифицируется тремя основными значениями: `groupId`, `artifactId`, `version`. Их называют **Maven coordinates** или сокращённо **GAV**:

```
G → groupId
A → artifactId
V → version
```

Например:

```xml
<groupId>com.victory</groupId>
<artifactId>shop</artifactId>
<version>1.0.0</version>
```

Получаем: `com.victory:shop:1.0.0`.

***

### `groupId`

> `groupId` — идентификатор организации, команды или группы проектов.

Например:

```xml
<groupId>com.victory</groupId>
```

```xml
<groupId>org.apache.commons</groupId>
```

Часто используется обратная запись доменного имени:

```
commons.apache.org
↓
org.apache.commons
```

У одной организации может быть много Maven-проектов:

```
org.apache.commons
org.apache.logging
org.apache.pdfbox
```

***

### `artifactId`

> `artifactId` — имя конкретного проекта (артефакта) внутри `groupId`.

Например:

```xml
<artifactId>order-service</artifactId>
```

***

### `version`

> `version` — версия конкретного артефакта.

Например:

```xml
<version>1.0.0</version>
```

Можно выпустить следующую версию:

```
com.victory:order-service:1.1.0
```

Для Maven это уже другой артефакт.

Версия обычно расшифровывается так:

```
MAJOR.MINOR.PATCH
```

Например, для `1.4.2`:

* `1` — **major**, большие, потенциально несовместимые со старой версией изменения (обновились — все сломалось);
* `4` — **minor**, добавлена новая функциональность, но уже существующая продолжает работать;
* `2` — **patch**, исправления ошибок.

Почему нельзя просто обновить библиотеку для всех, кто ее использует? Новая версия может изменить поведение: удалить старый метод, который в части проектов еще используется, содержать новые баги, требовать более новую версию Java.

Поэтому каждый проект явно выбирает, какую версию использовать — один может пока работать на `1.4.2`, а другой уже перейти на `2.0.0`.

Это делает сборку **предсказуемой**: если завтра выйдет новая версия библиотеки, наш проект не сломается. Мы сами можем решить, когда поднять версию.

***

#### `SNAPSHOT`

Во время разработки часто встречается:

```xml
<version>1.0.0-SNAPSHOT</version>
```

`SNAPSHOT` означает, версия находится в разработке и её содержимое может меняться.

***

## `name`

```xml
<name>Victory Shop</name>
```

> `name` — человекочитаемое название проекта.

Оно может отличаться от `<artifactId>`:

```xml
<artifactId>victory-shop-backend</artifactId>
<name>Victory Shop</name>
```

`artifactId` участвует в идентификации артефакта Maven (например, конкретную библиотеку Maven ищет по `artifactId`), `name` — в первую очередь описание для человека.

***

## `description`

```xml
<description>
    Backend для сервиса товаров
</description>
```

> `description` — текстовое описание проекта.

Не влияет на компиляцию или выполнение программы, тоже служит в качестве дополнительной информации в первую очередь для человека.

***

## `properties`

`properties` позволяют объявлять значения один раз и затем переиспользовать их в `pom.xml` — как переменные в Java.

Например:

```xml
<properties>
    <java.version>21</java.version>
    <commons.version>3.18.0</commons.version>
</properties>
```

Использование:

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>${commons.version}</version>
</dependency>
```

***

Часто бывает, что несколько связанных библиотек обновляются синхронно, и для них нужно прописывать одну и ту же версию:&#x20;

```xml
<dependency>
    ...
    <version>3.18.0</version>
</dependency>

<dependency>
    ...
    <version>3.18.0</version>
</dependency>
```

Можно вынести:

```xml
<properties>
    <library.version>3.18.0</library.version>
</properties>
```

и использовать:

```xml
<version>${library.version}</version>
```

Теперь если надо поменять версию, это делается в одном месте ⇒ меньше риск забыть где-то поменять и получить ошибку.

***

## `dependencies`

Зависимости проекта находятся внутри:

```xml
<dependencies>
    ...
</dependencies>
```

Например:

```xml
<dependencies>

    <dependency>
        <groupId>org.apache.commons</groupId>
        <artifactId>commons-lang3</artifactId>
        <version>3.18.0</version>
    </dependency>

</dependencies>
```

Каждый блок `<dependency>` описывает одну библиотеку.

***

### Транзитивные зависимости

Представим:

```
Наш проект
   ↓
Library A
   ↓
Library B
```

Наш проект напрямую подключает только `Library A`, но для работы `A` нужна `B`. Это называется **транзитивная зависимость**. Maven обычно сам скачает и `A` и `B`.&#x20;

Это одна из важных причин, почему вручную управлять `.jar`-файлами неудобно — пришлось бы искать транзитивные зависимости тоже.

***

## `build`

В блоке:

```xml
<build>
    ...
</build>
```

описываются настройки процесса сборки. Например:

```xml
<build>
    <plugins>

        <plugin>
            <groupId>com.diffplug.spotless</groupId>
            <artifactId>spotless-maven-plugin</artifactId>
            <version>3.10.1</version>
        </plugin>

    </plugins>
</build>
```

Здесь подключён **Spotless** — Maven plugin автоматического форматирования кода. Он может проверить, соответствует ли Java-код заданному стилю, и исправить форматирование.

***

Dependencies и plugins важно не путать.

**Dependency** — библиотека, которую использует **код нашего приложения**.

Например:

```java
StringUtils.isBlank(text);
```

Для этого проекту нужна библиотека Apache Commons. Она добавляется в `<dependencies>`.

**Plugin** — инструмент, который Maven использует **во время сборки проекта**.

Например, во время сборки Maven вызывает плагин Spotless, и он автоматически исправляет форматирование кода еще до запуска проекта.

***

## `profiles`

> **Profile** — набор Maven-настроек, который можно включать при определённой сборке.

В профиле могут быть, `properties`, `dependencies`, `plugins` или другие настройки сборки. Так один и тот же `pom.xml` может немного по-разному работать при разных условиях.

Запустить Maven с `dev` профилем:

```bash
mvn package -Pdev
```

или с `prod`:

```bash
mvn package -Pprod
```

`-P` означает "активировать Maven profile".

```xml
<profiles>
    <!-- dev - быстрая сборка без строгих проверок -->
    <profile>
        <id>dev</id>

            <!-- Не запускаем тесты -->
            <maven.test.skip>true</maven.test.skip>
        </properties>
    </profile>


    <!-- prod - более тщательная сборка с форматированием и проверками -->
    <profile>

                    <groupId>org.apache.maven.plugins</groupId>

</profiles>
```

## Жизненный цикл Maven

> **Lifecycle (жизненный цикл)** — последовательность этапов, через которые Maven может провести проект.

У Maven 3 встроенных lifecycle: `clean`, `build` (по умолчанию) и `site`.

<figure><img src="../.gitbook/assets/image (1).png" alt=""><figcaption></figcaption></figure>

Каждый lifecycle состоит из **phases — фаз**. Например, в основном lifecycle есть:

```
compile
test
package
install
...
```

***

> Главное правило: если вызвать определённую фазу, Maven выполнит **все предыдущие фазы этого lifecycle**.

Например, если напишем `mvn test`, Maven сначала выполнит предыдущие необходимые фазы:

```
...
compile
↓
test-compile
↓
test
```

***

### Lifecycle `clean`

> `clean` отвечает за удаление результатов предыдущей сборки.

Самая важная фаза здесь тоже называется `clean`. Команда `mvn clean` обычно удаляет `target/`.

Например, до:

```
project/
├── src/...
├── pom.xml
└── target/
    └── shop-1.0.jar
```

После:

```
project/
├── src/...
└── pom.xml
```

Это нужно, чтобы следующая сборка началась с нуля, без оставшихся от предыдущей сборки файлов.

***

Очень распространённая команда — `mvn clean package`.

Здесь Maven выполняет **два lifecycle**. Сначала:

```
clean lifecycle
↓
clean
↓
удаляем target
```

потом:

```
default lifecycle
↓
...
compile
↓
test
↓
package
```

Получаем новую чистую сборку проекта.

***

Важный нюанс — если просто написать, `mvn package`, Maven **не удалит автоматически `target` через lifecycle clean**. `clean` относится к другому lifecycle.

Поэтому:

```bash
mvn clean package
```

и:

```bash
mvn package
```

— не одно и то же.

***

### Lifecycle `default`

> `default` — основной жизненный цикл сборки проекта.

Именно здесь находятся большинство используемых фаз:

```
compile
test
package
install
deploy
```

Полная цепочка длиннее, но на практике почти всегда используются только основные этапы.

***

#### `compile`

`mvn compile` — компилирует основной Java-код проекта.

Например, `src/main/java` содержит `User.java`, `Order.java`, `Main.java`. После `mvn compile` появляются `.class`-файлы в `target/classes/`.

**`compile` ещё не означает создание готового `.jar`.** Он только проходит сборку до этапа компиляции основного кода.

***

#### `test`

`mvn test` — компилирует код, компилирует тесты и запускает тесты.

```
src/main/java
      ↓
compile
      ↓
src/test/java
      ↓
test-compile
      ↓
test
```

***

#### `package`

`mvn package` — собирает проект в готовый артефакт. Для обычного Java-проекта это чаще всего `.jar`.

При этом до `package` Maven уже пройдёт предыдущие фазы, включая тесты. Если тесты упадут, сборка до `package` не дойдёт.

***

#### `install`

`mvn install` делает всё, что находится до `install`:

```
compile
↓
test
↓
package
↓
install
```

и собранный `.jar`-артефакт сохраняет в **локальный Maven repository** (`~/.m2/repository`). Например, если делаем свою библиотеку:

```
com.victory:common-utils:1.0.0
```

Выполняем в её папке `mvn install`, Maven собирает её и помещает в локальный repository. Теперь в другом проекте на этом же компьютере может написать:

```xml
<dependency>
    <groupId>com.victory</groupId>
    <artifactId>common-utils</artifactId>
    <version>1.0.0</version>
</dependency>
```

и Maven сможет найти эту библиотеку локально и подключить так же, как любую другую библиотеку.

***

#### `deploy`

`mvn deploy` — отправляет собранный `.jar`-артефакт уже не в локальный repository, а в **удалённый repository**, доступный другим разработчикам.

Например, на крупных проектах часто делают свои библиотеки — с помощью `deploy` можно залить новую версию в общее хранилище, из которого другие разработчики могут ее загрузить. При этом компании используют для этого не общий Maven Central — там библиотека проекта станет доступна вообще всем — а свой аналогичный репозиторий с доступом только для разработчиков компании.

***

### Lifecycle `site`

> `site` используется для генерации сайта с информацией и отчётами о Maven-проекте.

Делаем `mvn site` — Maven создает HTML-страницы с информацией о проекте (то же, что написано у вас в `pom.xml`) и сохраняет в `target/site/`.

Почти никогда не используется, запомнить только для ответа на вопрос "какие есть жизненные циклы в Maven" на собеседовании.

***

На самом деле работу в Maven выполняют плагины. У плагинов есть конкретные функции (методы), которые они могут выполнять — они называются **goal**. Goal привязываются к фазам жизненного цикла Maven: дошли до определенного этапа (фазы) ⇒ Maven ищет, какие goal привязаны к этой фазе ⇒ выполняет их методы.

Например, мы пишем:

```bash
mvn compile
```

`compile` — **phase**, фаза. К ней привязан встроенный плагин Maven — `maven-compiler-plugin`, а конкретно его goal `compile`. Именно этот плагин и компилирует Java-код.

Можно написать команду явно:

```bash
mvn compiler:compile
```

Это запись означает "выполнить goal `complie` плагина `compiler`". Для самых частых действий в Maven есть сокращенные версии, которые используются чаще, чем полные:

```bash
mvn clean
mvn test
mvn package
mvn install
```

Для других плагинов, которые мы подключаем сами, используем полную версию:

```
plugin:goal
```

## Самые частые команды Maven

* Очистить предыдущую сборку — `mvn clean`
* Скомпилировать исходные java-файлы — `mvn compile`
* Запустить тесты — `mvn test`
* Собрать `.jar` — `mvn package`
* Очистить файлы от предыдущей сборки и сделать новую — `mvn clean package`
* Сделать сборку и установить в локальный repository — `mvn install`, если сначала нужна очистка — `mvn clean install`

***

Что произойдёт, если сделали `mvn package` и один тест упал? Цепочка до `mvn package` включает фазу `test`. Если даже один тест падает, то вся эта фаза падает, и сборка прекращается:

```
compile ✅
test    ❌
package не выполняется
```

Maven lifecycle — строгая последовательность этапов, и ошибка на одном из них не позволяет перейти дальше.
