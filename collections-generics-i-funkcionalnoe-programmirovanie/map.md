# Map

Представим сервис доставки типа Яндекс Еды. Заказ оформляется, ресторан готовит еду, затем курьер везёт её клиенту. Нужно отслеживать статус каждого заказа — пока для простоты не в отдельной базе данных, а в самом приложении:

```java
Map<Long, String> statuses = new HashMap<>();

statuses.put(10L, "Принят");
statuses.put(20L, "Готовится");

System.out.println(statuses.get(10L)); // Принят
```

Здесь `Long` — тип ключа, а `String` — тип значения. Ключи и значения могут быть любыми типами данных — например, вместо строки со статусом можно хранить enum или даже целый объект заказа; принцип поиска по ключу от этого не изменится.

***

## Внутреннее устройство `HashMap`

Если хранить заказы в списке и искать нужный по `id` обычным перебором, в худшем случае придётся проверить все записи:

```java
for (Order order : orders) {
    if (order.getId() == idToFind) {
        return order.getStatus();
    }
}
```

Если нужный нам заказ находится в конце списка или его вообще нет, придется проверить все элементы. Если заказ встретится раньше, то мы сразу вернем его статус через `return`, и дальнейшие итерации выполняться не будут.

Получается, худший случай — нам придется посмотреть каждый элемент списка: для списка из 5 элементов — 5 итераций цикла, для списка из 10 — 10, и т. д. Обобщая, сложность поиска — `O(n)`.

`HashMap` использует **хеш-таблицу**. Под капотом обычный массив, его ячейки называют **бакетами.** `HashMap` по ключу быстро определяет, в каком бакете искать, и затем проверяет записи только в этой ячейке.

<figure><img src="../.gitbook/assets/image (4).png" alt=""><figcaption></figcaption></figure>

Допустим, у массива 8 ячеек с индексами:

```
0  1  2  3  4  5  6  7
```

И у нас есть «магическая» функция, которая **по ключу может сказать, в какую ячейку нужно положить запись**:

```
f(17) → 1
```

Тогда при **добавлении** заказа с `id = 17` мы сначала вызываем эту функцию и кладём его в бакет №1.

При **поиске** делаем то же самое:

```
17 ?
 ↓
f(17)
 ↓
1
```

После этого нам уже не нужно проверять все 20 заказов. Мы сразу переходим к бакету №1 и проверяем только записи внутри него:

```
бакет 1:

17 → Order #17
25 → Order #25
41 → Order #41
```

Вместо 20 элементов пришлось проверить максимум три. Именно на этой идее и строится быстрый поиск в `HashMap`: **сначала определить небольшой участок, где может находиться ключ, а затем искать только внутри него**.

***

Как придумать такую функцию? Для `id` заказа задача простая, потому что `id` является числом — можно взять **остаток от деления на количество бакетов**. Например, если бакетов 8:

```
17 % 8 = 1
42 % 8 = 2
11 % 8 = 3
20 % 8 = 4
```

> Получившееся число всегда находится в диапазоне от `0` до `7`, поэтому его удобно использовать как индекс массива.&#x20;

При добавлении: `17 % 8 = 1` ⇒ запись отправляется в бакет с индексом 1. При поиске: `17 % 8 = 1` ⇒ снова получаем 1 и сразу знаем, где искать.

Но здесь возникает интересная ситуация:

```
17 % 8 = 1
25 % 8 = 1
41 % 8 = 1
```

Разные ключи могут указать на один и тот же бакет. Поэтому **бакет должен уметь хранить несколько записей**. Позже мы отдельно разберём, как `HashMap` работает с такой ситуацией.

Но появляется более серьёзная проблема. `HashMap` разрешает использовать ключи не только типа `Integer`:

```java
Map<Integer, Order> orders;
Map<String, User> users;
Map<Product, Price> prices;
```

Как определить номер бакета для строки `"ivan@example.com"` или объекта `Product`? Нельзя написать `Product % 8` — сначала объект нужно каким-то образом **превратить в число**.

> Для этого в Java у каждого объекта есть метод `hashCode()` — он берет любой объект и превращает его в `int`.&#x20;

Например, концептуально процесс можно представить так:

```
"ivan@example.com"
        ↓
    hashCode()
        ↓
    183726451
        ↓
вычисляем индекс бакета
        ↓
        3
```

Теперь схема работает для любого типа ключа:

```
объект
  ↓
hashCode()
  ↓
число
  ↓
определение индекса
  ↓
бакет массива
```

При добавлении элемента `HashMap` получает `hashCode()` ключа и на его основе определяет бакет. При поиске она снова получает `hashCode()` **того ключа, который мы ищем**, и приходит в тот же бакет. То есть `hashCode()` решает важную задачу: позволяет свести произвольный Java-объект к числу, которое уже можно использовать при выборе ячейки хеш-таблицы.

{% hint style="warning" icon="circle-info" %}
Остаток от деления используется для понимания идеи. Настоящий `HashMap` в Java вычисляет индекс более оптимизированно (с помощью побитовых операций):

```java
int h = key.hashCode();
int hash = h ^ (h >>> 16);
int index = (table.length - 1) & hash;
```

Но если упростить, суть та же.
{% endhint %}

Метод `hashCode()` определён ещё в базовом классе `Object` ("предок" любого класса в Java), поэтому он существует у любого объекта Java:

```java
key.hashCode();
```

Если класс не переопределяет его, используется реализация, унаследованная от `Object`:

<figure><img src="../.gitbook/assets/image (5).png" alt=""><figcaption></figcaption></figure>

`native` означает, что Java сама не реализует этот метод, а использует реализацию на каком-то другом языке, более низкоуровневом, типа C или C++ — какая конкретно реализация используется, зависит от версии JVM, ОС и других факторов. Главное — `native` методы обычно очень быстрые, быстрее чем если бы они были реализованы на самой Java.

Для своих собственных классов `hashCode()` можно переопределить. Классический Java-подход — вычислять результат из полей объекта, постепенно смешивая их значения, часто умножая на простые числа (здесь не будем углубляться в математику, которая за этим стоит — если интересно, почитайте сами):

```java
@Override
public int hashCode() {
    int result = Long.hashCode(id);
    result = 31 * result + type.hashCode();
    return result;
}
```

**Такой код чаще всего не нужно писать вручную — его умеет генерировать IDE и Lombok.**

Но выбирать поля для `hashCode()` произвольно нельзя: у него есть важная связь с методом `equals()`, об этом позже.

***

Хеш-код **физически не может быть уникальным** — `int` в Java ограничен диапазоном от `-2,147,483,648` to `2,147,483,647`, а объектов в Java создать можно бесконечное количество. К тому же, даже если хеш-код разный, могут совпасть остатки от деления на количество бакетов, и разные ключи попадут в один бакет.

Мы уже увидели такую ситуацию:

```
17 % 8 = 1
25 % 8 = 1
41 % 8 = 1
```

Все три ключа указывают на один бакет. Такая ситуация называется **коллизией**.

> **Коллизия хеш-функции** — совпадение хешей у разных исходных объектов. При обсуждении хеш-таблиц коллизией также называют попадание разных ключей в один бакет.

`HashMap` изначально спроектирован с расчётом на то, что в одном бакете может находиться несколько записей. Упрощённо можно представить `HashMap` так:

```
массив бакетов

0 → ...
1 → [17 → Order #17] → [25 → Order #25] → [41 → Order #41]
2 → ...
3 → ...
```

То есть ячейка массива хранит не обязательно одну запись. Если несколько элементов попали в один бакет, они хранятся внутри этого бакета вместе. Каждая такая запись содержит примерно такие поля:

```java
class Node<K, V> {
    int hash;   // хеш
    K key;      // ключ
    V value;    // значение
    Node<K, V> next; // ссылка на следующий элемент в том же бакете (если есть)
}
```

Получается связная цепочка:

```
Node
 ↓
Node
 ↓
Node
```

Можно сказать, что при коллизиях `HashMap` хранит элементы бакета в **связном списке**.

***

#### Как тогда происходит поиск?

Предположим, мы выполняем `orders.get(25)`. Сначала всё происходит так же, как уже рассматривали раньше — `HashMap` получает хеш ключа:

```
25
 ↓
hashCode()
 ↓
hash
```

По хешу определяется бакет:

```
hash
 ↓
бакет 1
```

Теперь `HashMap` уже не ищет среди всех элементов таблицы, а только среди записей бакета с индексом 1.

```
бакет 1

17 → Order #17
25 → Order #25
41 → Order #41
```

Но как понять, какая запись среди них нужна? Одного `hashCode()` для этого недостаточно.Ведь разные ключи могут иметь одинаковый хеш. Поэтому внутри бакета `HashMap` дополнительно сравнивает ключи.

```
нашли нужный бакет
        ↓
проверяем записи внутри него
        ↓
совпадает hash?
        ↓
совпадает key?
```

Для окончательной проверки ключа используется `equals()`. Например:

```
ищем key = 25

17.equals(25) → false
25.equals(25) → true
```

После этого `HashMap` возвращает соответствующее значение `Order #25`.

Получается разделение обязанностей:

* `hashCode()` — быстрый, но не очень точный, помогает сузить область поиска
* `equals()` — медленнее, но идеально точный, помогает в небольшой области найти точное совпадение ключа

Именно поэтому для ключей `HashMap` важны **оба метода**.

***

#### Что происходит при `put()`?

```java
map.put(key, value);
```

`HashMap` сначала определяет нужный бакет. Если бакет пустой:

```
бакет 3
—
```

запись просто добавляется туда:

```
бакет 3
[key → value]
```

Если там уже есть записи:

```
бакет 3
[A → value1]
[B → value2]
```

`HashMap` проверяет ключи. Если такого ключа ещё нет, появляется новая запись:

```
[A → value1]
[B → value2]
[C → value3]
```

Если ключ **уже существует**:

```java
map.put("user-1", "Alice");
map.put("user-1", "Kate");
```

новая запись с таким же ключом не создаётся. Вместо этого значение существующей записи заменяется: `"user-1" → "Kate"`.

***

Но разве длинный список внутри бакета снова не делает поиск медленным? Делает. В идеальном случае элементы распределены между бакетами примерно равномерно:

```
0 → 2 элемента
1 → 1 элемент
2 → 3 элемента
3 → 1 элемент
4 → 2 элемента
```

Тогда после вычисления бакета нужно проверить совсем немного записей. Но представим плохое распределение:

```
0 → 0 
1 → 200 элементов
2 → 0
3 → 0
4 → 0
```

Теперь поиск внутри бакета 1 снова начинает напоминать обычный перебор списка. Например, `hashCode()`, всегда возвращающий `1`, создаёт именно такую проблему. Именно поэтому для `HashMap` важно, чтобы `hashCode()` **хорошо распределял разные ключи по хешам и бакетам**.

***

До Java 8 при большом количестве коллизий элементы бакета оставались связным списком. Начиная с Java 8 `HashMap` умеет преобразовать слишком длинную цепочку в **красно-чёрное дерево**.

Например, допустим, в один бакет попали ключи:

```
17 → 25 → 41 → 57 → 73 → 89 → 105 → 121
```

Пока бакет представлен связным списком, поиск ключа `121` может потребовать пройти всю цепочку:

```
17 → 25 → 41 → 57 → 73 → 89 → 105 → 121
                                      ↑
                                   нашли
```

При достаточно длинной цепочке `HashMap` может перестроить её в красно-чёрное дерево. Упрощённо оно может выглядеть так:

```
              57
            /    \
          25      89
         /  \    /  \
       17   41  73  105
                       \
                       121
```

Теперь для поиска `121` не нужно последовательно проверять все восемь элементов. Поиск идет сверху вниз — на каждом шаге сравниваем текущий элемент с тем, который ищем:

```
121 меньше или больше 57? -> больше -> идем вправо
121 меньше или больше 89? -> больше -> идем вправо
121 меньше или больше 105? -> больше -> идем вправо
121 меньше или больше 121? -> равно -> нашли
```

Получилось четыре шага вместо последовательной проверки всей цепочки. Поэтому поиск в длинном связном списке в худшем случае имеет сложность `O(n)`, а в сбалансированном дереве — `O(log n)`.

Идея здесь простая: **дерево не заставляет идти по элементам один за другим — на каждом шаге оно позволяет отбросить значительную часть оставшихся вариантов.**

В настоящем `HashMap` дерево строится не просто по числовому значению ключа: логика сравнения внутри tree-bin сложнее. Здесь важно понять именно отличие структуры поиска: **цепочка → последовательный проход, дерево → на каждом шаге отсекаем половину неподходящих элементов**.

Но `HashMap` не превращает бакет в дерево сразу после появления пары элементов. Для маленьких цепочек список проще и дешевле.

В современной реализации Java преобразование в дерево может происходить, когда количество элементов в бакете достигает **8**, но есть ещё одно условие: сам массив должен содержать как минимум **64 бакета**.

Если массив меньше, `HashMap` предпочитает сначала увеличить саму таблицу и попробовать перераспределить элементы — при расширении таблицы индекс бакета определяется заново для каждого элемента с учетом нового размера внутреннего массива.

{% hint style="danger" icon="circle-question" %}
Заказы с ключами `10L` и `26L` попали в один бакет массива из 16 ячеек. Может ли расширение до 32 бакетов разделить их?

Если у всех ключей `hashCode()` всегда возвращает `1` — решит ли расширение проблему с медленным поиском?
{% endhint %}

<details>

<summary>Ответ</summary>

В первом случае — да. Для этих ключей раньше были индексы `10 % 16 = 10` и `26 % 16 = 10`, а при длине 32 получатся индексы `10 % 32 = 10` и `26 % 32 = 26`.

Во втором случае — нет: одинаковые хеши по-прежнему дадут одинаковый индекс. Добавление бакетов само по себе не исправляет хеш-функцию, которая возвращает одну константу.

</details>

### Capacity, load factor

**Capacity** — количество бакетов во внутреннем массиве. **Size** — количество сохранённых пар ключ-значение. Это разные величины: в одном бакете может лежать несколько записей, а часть бакетов может быть пустой.

Обычный `new HashMap<>()` изначально создает массив на 16 бакетов и использует коэффициент нагрузки 0.75. В OpenJDK массив создаётся лениво — при первой вставке.

> **Load factor — коэффициент нагрузки**, который используется для расчёта порога расширения таблицы по количеству записей.

Для таблицы из 16 бакетов с коэффициентом 0.75 порог равен `16 × 0.75 = 12`. При добавлении тринадцатого **нового ключа** этот порог будет превышен. Обычное расширение увеличит ёмкость до 32 и перераспределит записи. При большом числе коллизий расширение может произойти и раньше — по правилу, разобранному в разделе о деревьях.

{% hint style="info" %}
`0.75` не означает «заняты 75% бакетов». Для порога учитывается **общее количество записей**. Десять узлов в одном бакете дают `size() == 10`, а не `1`.
{% endhint %}

Меньший коэффициент нагрузки заставляет раньше расширять таблицу: плотность записей ниже, но памяти на массив нужно больше. Больший коэффициент экономит место под массив, однако обычно увеличивает число записей в бакетах и замедляет поиск. Значение 0.75 выбрано как компромисс.

При расширении `HashMap` использует уже сохранённые хеши, чтобы разложить элементы по новым бакетам.

Если заранее известно, что хранилище будет большим, подходящая начальная ёмкость уменьшит число расширений. Но чрезмерный запас тоже имеет цену: расход памяти и обход большой таблицы. Обычно начинать стоит со стандартных настроек.

## `null` в `HashMap`

`HashMap` допускает один **ключ** `null` и сколько угодно **значений** `null`. Повторный `put(null, ...)` заменит значение у того же ключа.

`get()` возвращает `null` как для отсутствующего ключа, так и для явно сохранённого значения `null`.

```java
Map<Long, String> statuses = new HashMap<>();

statuses.put(10L, null);

System.out.println(statuses.get(10L));         // null
System.out.println(statuses.get(99L));         // null
System.out.println(statuses.containsKey(10L)); // true
System.out.println(statuses.containsKey(99L)); // false
```

Метод `containsKey()` позволяет отличить эти случаи.

***

## Контракт `equals()` и `hashCode()`

В главе про `String` мы уже различали совпадение ссылок и равенство содержимого. Для ключей это означает: два отдельных объекта могут представлять **один и тот же заказ**.

Допустим, нам понадобился собственный тип идентификатора `OrderKey`. Будем считать два ключа равными, если у них одинаковый `id`.

> Если `a.equals(b)` возвращает `true`, то `a.hashCode()` и `b.hashCode()` **обязаны совпадать**. Наоборот не обязательно — мы уже разбирали, что `hashCode()` может случайно совпасть у разных объектов.

Почему это нужно? `HashMap` сначала выбирает бакет и проверяет хеш. Если один и тот же объект в разные моменты времени имеет разный `hashCode()`, поиск может закончиться ещё **до сравнения через `equals()`** — проверяться будут разные бакеты.

```java
final class OrderKey {

    private final long id;

    OrderKey(long id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) { // та же ячейка памяти - равны
            return true;
        }
        if (!(obj instanceof OrderKey)) { 
            return false; // если объект даже не относится к тому же типу, точно не равны
        }

        OrderKey other = (OrderKey) obj;
        return id == other.id; // тут сами выбираем по каким полям сравнивать
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }
}
```

Проверка `instanceof` убеждается, что перед нами `OrderKey`; после неё приведение `(OrderKey) obj` позволяет обратиться к полю `id`. Для `null` проверка `instanceof` вернёт `false`.

&#x20;`Long.hashCode(id)` вычисляет хеш для значения `long`. Класс сделан `final`, поэтому наследники не могут переопределить `equals()` и `hashCode()` и сломать проверку.

```java
OrderKey first = new OrderKey(10L);
OrderKey second = new OrderKey(10L);

System.out.println(first == second);                         // false
System.out.println(first.equals(second));                    // true
System.out.println(first.hashCode() == second.hashCode());   // true

Map<OrderKey, String> statuses = new HashMap<>();
statuses.put(first, "Принят");

System.out.println(statuses.get(second)); // Принят
```

***

### Контракт `equals()`

Для не-`null` объектов `equals()` должен соблюдать следующие правила:

| Правило                           | Смысл                                                                  |
| --------------------------------- | ---------------------------------------------------------------------- |
| Рефлексивность                    | `a.equals(a)` возвращает `true`                                        |
| Симметричность                    | `a.equals(b)` и `b.equals(a)` дают одинаковый ответ                    |
| Транзитивность                    | Если `a` равен `b`, а `b` равен `c`, то `a` равен `c`                  |
| Согласованность повторных вызовов | Пока участвующие в сравнении данные не меняются, результат не меняется |
| Сравнение с `null`                | `a.equals(null)` возвращает `false`                                    |

Переопределяя `equals()`, нужно обеспечить согласованный с ним `hashCode()`.

***

### Что произойдёт при нарушении контракта?

Представим ошибочную версию `OrderKey`: `equals()` сравнивает `id`, а `hashCode()` возвращает отдельное поле `hash`, переданное в конструктор.

```java
final class OrderKey {
    private final long id;
    private final int hash;

    OrderKey(long id, int hash) {
        this.id = id;
        this.hash = hash;
    }

    @Override
    public int hashCode() {
        return hash;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof OrderKey)) {
            return false;
        }
        OrderKey other = (OrderKey) obj;
        return id == other.id;
    }
}
```

У двух ключей одинаковый `id = 10`, но хеши равны `10` и `26`. После сохранения статуса с первым ключом поиск по второму может не найти запись.

Причём **даже совпадение бакета не спасает**. В массиве из 16 бакетов оба хеша дадут индекс `10`, но далее `HashMap` проверяет записи уже по полному хешу, а не по остатку, и они отличаются. Так что `HashMap` отсеет запись еще до вызова `equals()`.

***

### Почему опасно изменять ключ?

> Даже согласованные методы не спасут, если после вставки изменить данные ключа, которые участвуют в равенстве.

Допустим, у другой, **изменяемой версии** `OrderKey` есть `setId()`, а `hashCode()` вычисляется из `id`:

```java
OrderKey key = new OrderKey(10L);
Map<OrderKey, String> statuses = new HashMap<>();

statuses.put(key, "Принят");
key.setId(26L);
```

При вставке узел сохранил старый хеш. После изменения `get(key)` вычислит новый. Даже если индекс бакета совпадёт, сохранённый хеш уже не совпадает с текущим.

**`HashMap` не следит за изменениями полей ключа и не обновляет `Node` автоматически.**

Для поиска статуса заказа лучше использовать стабильный неизменяемый идентификатор: `Long`, `String` или собственный `OrderKey`. **Статус заказа может меняться, а идентификатор, по которому мы его ищем, должен оставаться прежним.**

***

### `String`, `final` и Lombok

`String` считается хорошим ключом для `HashMap`, потому что строку нельзя изменить после создания. Например:

```java
String key = "ORDER-10";
map.put(key, order);
```

В `HashMap` сохранился ключ `"ORDER-10"`. Если потом написать:

```java
key = "ORDER-11";
```

мы **не изменили ключ внутри `HashMap`**. Мы просто заставили переменную `key` ссылаться на другой объект. В самой `Map` по-прежнему находится `"ORDER-10" → order` и его по-прежнему можно найти:

```java
map.get("ORDER-10");
```

Проблема возникает с **изменяемыми объектами**. Например:

```java
UserKey key = new UserKey(10);
map.put(key, order);
key.setId(11);
```

Здесь изменился **тот же самый объект**, который уже лежит внутри `HashMap` как ключ. Если `hashCode()` зависит от `id`, то раньше его хеш вычислялся для `id = 10`, а теперь — для `id = 11`.

В результате `HashMap` может начать искать ключ уже в другом бакете и не найти запись, хотя объект физически всё ещё находится внутри `Map`.

Поэтому правило такое:

> Поля объекта, от которых зависят `equals()` и `hashCode()`, лучше не изменять, пока объект используется как ключ `HashMap`.

А `String` безопасен в этом отношении именно потому, что изменить содержимое существующей строки невозможно.

`final` такого свойства объекту не даёт:

```java
final UserKey key = new UserKey(10);
```

нельзя сделать:

```java
key = new UserKey(11);
```

но можно:

```java
key.setId(11);
```

То есть `final` запрещает заменить ссылку на другой объект, но **не делает сам объект неизменяемым**. Переменную нельзя переключить на другую ячейку памяти, но можно прям в этой ячейке поменять какие-то значения.

Lombok тоже не решает за нас, **какие поля должны определять равенство ключа**. Например:

```java
@Data
final class OrderKey {

    private long id;
    private String status;
}
```

Аннотация `@Data` среди прочего включает генерацию `equals()` и `hashCode()` По умолчанию Lombok использует в них все поля класса. Поэтому в нашем случае и `id`, и `status` участвуют в сравнении ключей.

Упрощённо сгенерированный код можно представить так:

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) {
        return true;
    }

    if (!(obj instanceof OrderKey other)) {
        return false;
    }

    return id == other.id
            && Objects.equals(status, other.status);
}

@Override
public int hashCode() {
    return Objects.hash(id, status);
}
```

То есть для Lombok эти объекты разные:

```java
new OrderKey(10, "CREATED");
new OrderKey(10, "PAID");
```

потому что отличается `status`, хотя по `id` это один и тот же заказ.

Кроме того, `@Data` автоматически сгенерирует сеттеры для полей:

```java
key.setId(10);
key.setStatus("CREATED");
```

Из-за этого можно случайно изменить объект уже после того, как он стал ключом `HashMap`:

```java
OrderKey key = new OrderKey(10, "CREATED");
map.put(key, order);
key.setStatus("PAID");
```

Но запись была помещена в `HashMap` по **старому хешу**. Сам объект остался в прежнем бакете, а при новом поиске `HashMap` вычислит уже новый `hashCode()` и может пойти в другой бакет.

Поэтому:

```java
map.get(key)
```

может неожиданно вернуть `null`, хотя этот же объект раньше был добавлен в `Map`.

Важно понимать: проблема здесь не в Lombok. `@Data` просто автоматически сгенерировал `equals()`, `hashCode()` и сеттеры. **Какие поля действительно должны определять ключ и должен ли ключ вообще быть изменяемым — решает разработчик.**

Если нужно, чтобы `equals()` и `hashCode()` использовали **только `id`**, можно написать так:

```java
@Data
@EqualsAndHashCode(onlyExplicitlyIncluded = true) // включить только помеченные поля
final class OrderKey {

    @EqualsAndHashCode.Include
    private long id;

    private String status;
}
```

Теперь

```java
new OrderKey(10, "CREATED");
new OrderKey(10, "PAID");
```

для `equals()` будут считаться равными, потому что у них одинаковый `id`.

В идеале еще сделать `id` неизменяемым:

```java
@Data
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
final class OrderKey {

    @EqualsAndHashCode.Include
    private final long id;

    private String status;
}
```

Тогда `id`, от которого зависят `equals()` и `hashCode()`, нельзя будет поменять после создания объекта.

{% hint style="danger" icon="circle-question" %}
В `Map<Long, Order>` изменился статус объекта `Order`, который лежит в значении. Может ли это само по себе сломать поиск заказа по ключу?
{% endhint %}

<details>

<summary>Ответ</summary>

Поиск по ключу не ломается: для выбора бакета используются `hashCode()` и `equals()` ключа `Long`, а не значения `Order`.

</details>

## `LinkedHashMap`

Предположим, оператору доставки нужно видеть заказы в том порядке, в котором они были добавлены в список на экране. Обычная `HashMap` **не гарантирует порядок**.

> `LinkedHashMap` — хеш-таблица, записи которой дополнительно связаны общим двусвязным списком для поддержания порядка.

Здесь важно не перепутать два вида связей: список внутри бакета `HashMap` нужен для обработки коллизий, а общий список `LinkedHashMap` проходит **через все записи**, даже если они находятся в разных бакетах.

***

### Порядок вставки

По умолчанию `LinkedHashMap` сохраняет порядок **добавления** ключей:

```java
Map<Long, String> statuses = new LinkedHashMap<>();

statuses.put(30L, "Принят");
statuses.put(10L, "Готовится");
statuses.put(20L, "Принят");

System.out.println(statuses);
// {30=Принят, 10=Готовится, 20=Принят}

statuses.put(10L, "В пути");

System.out.println(statuses);
// {30=Принят, 10=В пути, 20=Принят}
```

Обновление значения через `put()` не переместило существующий заказ в конец. Если же удалить ключ и добавить заново, это будет новая вставка — запись окажется в конце.

***

### Порядок доступа

Другой режим — **access order**, порядок последних обращений. Его включает третий аргумент `true`:

```java
Map<Long, String> recentlyViewed = new LinkedHashMap<>(16, 0.75f, true);

recentlyViewed.put(30L, "Принят");
recentlyViewed.put(10L, "Готовится");
recentlyViewed.put(20L, "Принят");

recentlyViewed.get(30L);

System.out.println(recentlyViewed);
// {10=Готовится, 20=Принят, 30=Принят}
```

Первые два аргумента — начальная ёмкость и коэффициент нагрузки; суффикс `f` обозначает число типа `float`. При успешном `get(30L)` запись № 30 переместилась в конец: к ней обратились последней. `put()` с обновлением существующего ключа тоже считается обращением.

Порядок поддерживается за счёт дополнительных ссылок и их обновления. Поэтому требуется больше памяти, чем у обычной `HashMap`; но основные операции при хорошем распределении хеша будут такими же быстрыми, как у `HashMap`.&#x20;

***

## `TreeMap`

Теперь другое требование: заказы должны выводиться **по возрастанию идентификатора**, независимо от порядка добавления.

```java
Map<Long, String> statuses = new TreeMap<>();

statuses.put(30L, "Принят");
statuses.put(10L, "Готовится");
statuses.put(20L, "Принят");

System.out.println(statuses);
// {10=Готовится, 20=Принят, 30=Принят}
```

> `TreeMap` хранит записи в красно-чёрном дереве и поддерживает сортировку по ключам.

При поиске ключа дерево сравнивает его с ключом текущего узла: если ключ, который мы ищем, меньше текущего, значит он находится в левой ветви, если больше — в правой. Чтобы поиск был примерно одинаково быстрым для любых двух разных элементов, одна ветвь не должна быть сильно длинее другой — `HashMap` под капотом это учитывает и делает перебалансировку. Операции `get()`, `put()` и `remove()` имеют сложность `O(log n)`.

Порядок задаётся способом сравнения по умолчанию (для чисел и дат — по возрастанию, для строк — по алфавиту) или переданным `Comparator`, если сравнение по умолчанию не подходит или у нас сложный объект, который Java не знает как сравнивать.

**Результат сравнения `0` означает для `TreeMap` один и тот же ключ.** Она не использует хеширование для поиска.

Подробнее внутреннее устройство рассмотрим в главе про `TreeSet`.

***

## Сравнение реализаций

|                    | `HashMap`                                        | `LinkedHashMap`                                              | `TreeMap`                          |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------ | ---------------------------------- |
| Основная структура | Массив бакетов; в бакетах списки или деревья     | Хеш-таблица и общий двусвязный список записей                | Красно-чёрное дерево               |
| Порядок            | Не сохраняется                                   | По умолчанию порядок вставки; можно включить порядок доступа | Порядок сравнения ключей           |
| Основные операции  | В среднем `O(1)` при хорошем распределении хешей | В среднем `O(1)` при хорошем распределении хешей             | `O(log n)`                         |
| Как находится ключ | По хешу и равенству ключей                       | По хешу и равенству ключей                                   | По результату сравнения ключей     |
| Пример             | Найти статус заказа по `id`                      | Вывести заказы в порядке добавления                          | Вывести заказы по возрастанию `id` |

## Основные методы `HashMap`

Создадим `HashMap`:

```java
Map<String, Integer> prices = new HashMap<>();
```

`put()` — добавить или изменить значение

```java
prices.put("coffee", 250);
prices.put("tea", 180);ё
```

Теперь в `Map`:

```
"coffee" → 250
"tea"    → 180
```

Если такой ключ уже существует, старое значение заменяется:

```java
prices.put("coffee", 300);
```

Получим:

```
"coffee" → 300
```

В `Map` не может быть двух записей с одинаковым ключом.

***

`get()` — получить значение по ключу

```java
Integer price = prices.get("coffee");
```

Результат — `300`.

Если такого ключа нет:

```java
prices.get("pizza");
```

метод вернёт `null`.

Но код:

```java
if (prices.get("pizza") == null) {
    ...
}
```

не всегда означает, что ключ отсутствует: теоретически ключ мог быть в Map с явным значением `null`.

***

`containsKey()` — проверить наличие ключа

```java
if (prices.containsKey("coffee")) {
    System.out.println("Товар найден");
}
```

Аналогично можно проверить наличие значения:

```java
prices.containsValue(300);
```

Но для `HashMap` основная идея — быстрый поиск именно **по ключу**. Поиск по значению требует просмотра всех элементов.

***

`remove()` — удалить запись

```java
prices.remove("coffee");
```

После этого ключа `"coffee"` в `Map` больше нет.

Можно удалить запись только при совпадении и ключа, и значения:

```java
prices.remove("tea", 180);
```

***

`getOrDefault()` — получить значение или значение по умолчанию

Часто нам нужно написать:

```java
Integer price = prices.get("coffee");

if (price == null) {
    price = 0;
}
```

Для этого есть более удобный метод:

```java
int price = prices.getOrDefault("coffee", 0);
```

Если `"coffee"` есть в `Map`, получим его значение.

Если нет:

```java
prices.getOrDefault("pizza", 0);
```

получим `0`.

***

`putIfAbsent()` — добавить только если ключа ещё нет

```java
prices.putIfAbsent("coffee", 250);
```

Если `"coffee"` отсутствует, запись будет добавлена. Если ключ уже есть, существующее значение останется:

```java
prices.put("coffee", 300);
prices.putIfAbsent("coffee", 250);
```

В `Map` по-прежнему:

```
"coffee" → 300
```

***

Количество записей:

```java
prices.size();
```

Проверка на пустоту:

```java
prices.isEmpty();
```

Удаление всех записей:

```java
prices.clear();
```

***

#### Как перебрать содержимое `Map`

Получить все ключи:

```java
prices.keySet();
```

Все значения:

```java
prices.values();
```

Или сразу пары `key-value`:

```java
for (Map.Entry<String, Integer> entry : prices.entrySet()) {
    System.out.println(entry.getKey() + " = " + entry.getValue());
}
```

Если нужны одновременно и ключ, и значение, обычно используют именно `entrySet()`.

***

### Пример использования

Представим, что у нас есть список городов, из которых пользователи сделали заказы:

```java
List<String> cities = List.of(
        "Москва",
        "Казань",
        "Москва",
        "Самара",
        "Казань",
        "Москва"
);
```

Хотим получить статистику:

```
Москва → 3
Казань → 2
Самара → 1
```

Здесь `HashMap` хорошо подходит. Ключом будет город:

```
Москва
Казань
Самара
```

а значением — количество его появлений в списке. Создаём `Map`:

```java
Map<String, Integer> counts = new HashMap<>();
```

И начинаем обходить список. При первой встрече `"Москва"` в `Map` ещё ничего нет:

```java
counts.get("Москва"); // null
```

Значит, добавляем:

```java
counts.put("Москва", 1);
```

Получаем:

```
"Москва" → 1
```

Позже встречаем `"Москва"` ещё раз. Теперь:

```java
counts.get("Москва"); // 1
```

Увеличиваем значение:

```java
counts.put("Москва", 2);
```

Ещё одна `"Москва"`:

```java
counts.put("Москва", 3);
```

Полное решение:

```java
Map<String, Integer> counts = new HashMap<>();

for (String city : cities) {
    Integer count = counts.get(city);

    if (count == null) {
        counts.put(city, 1);
    } else {
        counts.put(city, count + 1);
    }
}
```

Но такой сценарий встречается настолько часто, что его удобно упростить через `getOrDefault()`:

```java
Map<String, Integer> counts = new HashMap<>();

for (String city : cities) {
    int count = counts.getOrDefault(city, 0);
    counts.put(city, count + 1);
}
```

Можно даже записать в одну строку:

```java
for (String city : cities) {
    counts.put(city, counts.getOrDefault(city, 0) + 1);
}
```

Ещё более короткий вариант — метод `merge()`, специально созданный для подобных задач:

```java
for (String city : cities) {
    counts.merge(city, 1, Integer::sum);
}
```

Смысл такой:

* если ключа ещё нет — положить `1`;
* если ключ уже есть — сложить старое значение с `1`.

## Вопросы

{% hint style="info" icon="gitbook" %}
**Опишите устройство `HashMap`.**

`HashMap` — реализация `Map` на основе хеш-таблицы. Внутри находится массив бакетов, в бакетах — узлы, в которых хранится ключ, значение, вычисленный хеш и связь со следующим узлом в том же бакете. При `put()` и `get()` `Map` вычисляет хеш ключа, выбирает по нему бакет (упрощенно — по остатку от деления хеша на количество бакетов) и ищет в нём подходящий ключ, проверяя сначал уже полный хеш, а не остаток, и при его совпадении — равенство ключей по `equals()`. Если при вставке найден равный ключ, обновляется существующее значение; иначе добавляется новое. При хорошем распределении хешей основные операции имеют среднюю сложность `O(1)`. Порядок не гарантируется.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**Что такое хэш-функция?**

Хеш-функция преобразует исходные данные в числовой хеш. У объектов Java для этого есть `hashCode()`, возвращающий `int`. Хеш-код не обязан быть уникальным: разные ключи могут иметь одинаковый хеш.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**Что такое коллизия?**

Коллизия хеш-функции — совпадение хешей у разных объектов. Для хеш-таблицы коллизией также называют попадание разных ключей в один бакет; это возможно и при разных хешах, если у них одинаковый остаток. Например, ключи `10L` и `26L` в таблице из 16 бакетов имеют один индекс.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**Как `HashMap` работает с коллизиями (связные списки, преобразование в деревья в Java 8+)?**

В одном бакете может храниться несколько узлов, связанных в список. Для поиска проверяются записи внутри выбранного бакета. Начиная с Java 8 длинный список может преобразоваться в красно-чёрное дерево. В OpenJDK 17 используются `TREEIFY_THRESHOLD = 8` и минимальная ёмкость 64 бакета; при обычных вставках в список проверка срабатывает на девятом узле. Если таблица меньше 64, сначала выполняется расширение. Дерево создаётся только внутри бакета (это не превращает `HashMap` в `TreeMap`); оно также не отменяет необходимости хорошего хеширования.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**Что такое коэффициент нагрузки (load factor)?**

Это параметр для расчёта порога расширения хеш-таблицы по числу записей. По умолчанию он равен 0.75: при ёмкости 16 получаем 12, тринадцатый добавленный ключ приводит к его превышению. Учитывается количество пар, а не доля занятых бакетов. Если коэффициент меньше, нужно больше памяти под таблицу, но поиск быстрее; если коэффициент больше, бакетов в массиве меньше, но поиск дольше. При большом числе коллизий таблица может расшириться раньше по правилу `TREEIFY_THRESHOLD`.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**Какой контракт между методами `equals()` и `hashCode()`?**

Если два объекта равны по `equals()`, их хеш-коды обязаны совпадать. Наоборот не требуется: хеш-коды могут быть равны у разных объектах. Сам `equals()` должен быть рефлексивным, симметричным, транзитивным, давать одинаковый результат при неизменных данных и возвращать `false` при сравнении не-`null` объекта с `null`.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**К каким последствиям может привести нарушение контракта при использовании объектов в качестве ключей в `HashMap`?**

Если равные ключи дают разные хеши, `get()` и `remove()` могут не найти сохранённую запись, а `put()` может создать отдельную дублирующую запись вместо обновления существующей. Даже попадание в один бакет не спасает: `Map` в начале проверяет элементы по полному `hashCode()`, сохраненному при добавлении элемента, и только потом по `equals()`. Изменение участвующих в равенстве полей ключа после вставки тоже делает работу ненадёжной: `Map` не обновляет сохранённый хеш автоматически. Поэтому ключ должен иметь согласованные методы и быть неизменяемым. Одинаковый хеш у разных ключей при корректном `equals()` — другая ситуация: он ухудшает производительность, но сам по себе не нарушает контракт.
{% endhint %}

{% hint style="info" icon="gitbook" %}
**В чем заключаются особенности `LinkedHashMap` и `TreeMap`?**

`LinkedHashMap` сочетает хеш-таблицу с общим двусвязным списком записей. По умолчанию она сохраняет порядок вставки, но можно поменять режим и сохранять порядок последних обращений. Например, можно сохранять порядок добавления заказов или отслеживать недавно просмотренные. За поддержание порядка приходится платить дополнительными ссылками и их обновлением.

`TreeMap` основана на красно-чёрном дереве и упорядочивает записи по ключам: по их естественному порядку или заданному `Comparator`. Она использует сравнение, а не хеширование; сравнение с результатом `0` означает один ключ. Её основные операции имеют сложность `O(log n)`, тогда как у `LinkedHashMap` при хорошем хешировании — в среднем `O(1)`.
{% endhint %}
