# HashMap, equals(), hashCode(), LinkedHashMap и TreeMap

## `HashMap`, `equals()`, `hashCode()`, `LinkedHashMap` и `TreeMap`

Мы уже знаем, что `Map` хранит данные в виде пар **ключ → значение**.

Например:

```java
Map<Long, String> users = new HashMap<>();

users.put(1L, "Anna");
users.put(2L, "Ivan");

System.out.println(users.get(1L)); // Anna
```

По ключу `1L` можно быстро найти связанное с ним значение `"Anna"`.

Но каким образом `HashMap` понимает, **где именно искать нужный ключ**, если внутри неё находятся тысячи или миллионы записей?

Если бы при каждом вызове `get()` пришлось последовательно проверять все ключи:

```
ключ 1 — не подходит
ключ 2 — не подходит
ключ 3 — не подходит
...
ключ 50 000 — нашли
```

поиск становился бы всё медленнее с ростом количества элементов.

`HashMap` устроена иначе — она использует **хеширование**.

***

### Внутреннее устройство `HashMap`

Упрощённо внутри `HashMap` находится **массив бакетов**.

> **Бакет (bucket)** — ячейка внутреннего массива `HashMap`, в которой могут храниться одна или несколько пар ключ-значение.

Например:

```
table

[0] → null
[1] → key=15, value="Anna"
[2] → null
[3] → key=42, value="Ivan"
[4] → null
[5] → key=27, value="Kate"
...
```

Каждая сохранённая пара представлена внутренним объектом примерно следующего вида:

```java
class Node<K, V> {
    int hash;
    K key;
    V value;
    Node<K, V> next;
}
```

Это не полный код класса из JDK, а упрощённая модель.

У узла хранятся:

* хеш ключа;
* сам ключ;
* значение;
* ссылка `next` на следующий элемент в том же бакете.

Зачем нужен `next`, раз бакет — одна ячейка массива? Потому что иногда **несколько разных ключей попадают в один бакет**. Эту ситуацию разберём ниже.

***

### Что такое хеш-функция?

Представим ключ:

```java
"anna@mail.ru"
```

Нельзя использовать всю строку как индекс массива:

```
table["anna@mail.ru"]
```

Индекс массива должен быть числом.

Нужен способ преобразовать ключ:

```
"anna@mail.ru"
        ↓
    некоторое число
        ↓
 индекс бакета
```

Для этого используется хеширование.

> **Хеш-функция** преобразует данные в числовое значение — хеш.

В Java у объектов для этого существует метод:

```java
hashCode()
```

Он возвращает `int`.

Например:

```java
String name = "Anna";
System.out.println(name.hashCode());
```

Важно понимать: **`hashCode()` не обязан возвращать уникальное число для каждого объекта**.

Количество возможных объектов практически не ограничено, а `int` может содержать только ограниченное количество разных значений. Поэтому одинаковые хеш-коды возможны и сами по себе не являются ошибкой.

#### `hashCode()` и индекс бакета — не одно и то же

Иногда работу `HashMap` слишком сильно упрощают:

```
key.hashCode()
    ↓
индекс бакета
```

На самом деле между ними есть ещё несколько действий.

Современная `HashMap` сначала получает `key.hashCode()`, затем дополнительно преобразует полученный хеш, чтобы лучше распределить его биты, и уже после этого определяет индекс во внутреннем массиве.

Упрощённо:

```java
int h = key.hashCode();
int hash = h ^ (h >>> 16);
```

а индекс бакета вычисляется примерно как:

```java
index = (table.length - 1) & hash;
```

Пока необязательно подробно разбирать побитовые операции `^`, `>>>` и `&`. Здесь важно другое:

```
key
 ↓
hashCode()
 ↓
внутреннее преобразование HashMap
 ↓
индекс бакета
```

То есть `hashCode()` **помогает выбрать место поиска**, но сам по себе не является индексом массива.

***

### Как работает `put()`

Допустим:

```java
Map<String, Integer> ages = new HashMap<>();
ages.put("Anna", 20);
```

Упрощённо происходит следующее.

#### 1. Вычисляется хеш ключа

```java
"Anna".hashCode()
```

Затем `HashMap` выполняет своё дополнительное преобразование хеша.

#### 2. Определяется бакет

По полученному хешу выбирается индекс во внутреннем массиве:

```
hash
 ↓
bucket 5
```

#### 3. Проверяется содержимое бакета

Если бакет пуст:

```
[5] → null
```

туда добавляется новый узел:

```
[5] → ["Anna", 20]
```

Если в бакете уже что-то находится, `HashMap` должна выяснить, это **тот же ключ** или другой.

Для этого недостаточно только хеша. Упрощённо проверяются:

```
hash
+
equals()
```

Если найден существующий ключ, равный новому:

```java
ages.put("Anna", 20);
ages.put("Anna", 21);
```

новая пара не добавляется. Меняется значение существующей записи:

```
"Anna" → 21
```

Поэтому:

```java
System.out.println(ages.size()); // 1
```

Если же ключ другой, но попал в тот же бакет, возникает **коллизия**.

***

### Что такое коллизия?

> **Коллизия** — ситуация, когда разные ключи попадают в один бакет хеш-таблицы.

Например:

```
key A
  ↓
bucket 3

key B
  ↓
bucket 3
```

Это нормальная ситуация.

Коллизия **не означает ошибку** и не означает, что один ключ обязательно заменит другой.

Например, два объекта могут иметь:

```java
first.hashCode() == second.hashCode()
```

но при этом:

```java
first.equals(second) == false
```

Тогда это два разных ключа, и оба должны храниться в `HashMap`.

#### Одинаковый `hashCode()` не означает одинаковые объекты

Например:

```java
class UserKey {

    private final long id;

    public UserKey(long id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return 1;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }

        if (!(obj instanceof UserKey other)) {
            return false;
        }

        return id == other.id;
    }
}
```

У любого объекта этого класса:

```java
hashCode() == 1
```

Создадим:

```java
UserKey first = new UserKey(1);
UserKey second = new UserKey(2);
```

Получим:

```java
first.hashCode() == second.hashCode() // true
first.equals(second)                  // false
```

Поэтому:

```java
Map<UserKey, String> map = new HashMap<>();

map.put(first, "Anna");
map.put(second, "Ivan");

System.out.println(map.size()); // 2
```

`HashMap` не считает ключи одинаковыми только потому, что совпали их хеши.

***

### Как `HashMap` хранит несколько элементов в одном бакете?

Представим, что три разных ключа попали в один бакет.

Нельзя просто записать новый элемент поверх предыдущего, иначе данные потеряются. Поэтому внутри одного бакета может находиться несколько узлов.

#### Связный список

Упрощённо:

```
table[5]
   ↓
[key=A, value=10]
   ↓ next
[key=B, value=20]
   ↓ next
[key=C, value=30]
   ↓
 null
```

Если `HashMap` ищет `key=C`, она:

1. сразу попадает в нужный бакет;
2. затем проверяет элементы внутри этого бакета;
3. находит нужный ключ.

Если коллизий мало, такой список короткий и проблемы практически нет.

***

### Почему большое количество коллизий плохо?

Нормальный случай:

```
bucket 1 → A
bucket 2 → B
bucket 3 → C
bucket 4 → D
```

Плохое распределение:

```
bucket 1 → A → B → C → D → E → F → G → ...
```

Теперь внутри одного бакета снова приходится искать по множеству элементов.

Например, если написать:

```java
@Override
public int hashCode() {
    return 1;
}
```

корректность коллекции сама по себе не нарушается, если `equals()` реализован правильно.

Но **качество хеширования становится очень плохим**: все ключи стремятся попасть в один бакет.

Это важное различие:

```
плохой hashCode()
        ↓
обычно проблема производительности

нарушенный контракт equals/hashCode
        ↓
может нарушить корректность поиска ключей
```

***

### Преобразование списка в дерево в Java 8+

Чтобы длинный список внутри одного бакета не становился слишком медленным, начиная с Java 8 `HashMap` умеет преобразовывать такой бакет в **сбалансированное дерево**.

Упрощённо:

```
до:

A → B → C → D → E → ...

после:

        D
      /   \
     B     F
    / \   / \
   A   C E   G
```

В `HashMap` используется красно-чёрное дерево.

Подробно разбирать устройство такого дерева сейчас не требуется. Для этой главы достаточно понимать идею: в длинном списке приходится последовательно проверять элементы, а дерево позволяет быстрее отбрасывать большие части вариантов поиска.

В реализации есть константа:

```java
TREEIFY_THRESHOLD = 8;
```

Но распространённая формулировка «когда в бакете появляется 8 элементов, список сразу превращается в дерево» слишком грубая.

Учитывается ещё размер самой таблицы. Минимальная ёмкость таблицы для преобразования бакета в дерево:

```java
MIN_TREEIFY_CAPACITY = 64;
```

Если таблица ещё маленькая, `HashMap` предпочитает сначала **увеличить её размер**, чтобы попробовать распределить элементы по большему количеству бакетов.

Для обычного ответа достаточно:

> При большом количестве элементов в одном бакете `HashMap` начиная с Java 8 может заменить связный список красно-чёрным деревом. В реализации есть порог `TREEIFY_THRESHOLD = 8`, но преобразование в дерево происходит только при достаточно большой таблице — минимум 64 бакета; иначе сначала выполняется расширение таблицы.

{% hint style="danger" icon="circle-question" %}
Почему при длинном списке в одном бакете `HashMap` иногда сначала увеличивает весь массив, а не сразу превращает список в дерево?

Подумайте, какую проблему может решить увеличение количества бакетов.
{% endhint %}

***

### Как работает `get()`

Допустим:

```java
String value = map.get(key);
```

Упрощённо `HashMap` делает следующее:

```
key
 ↓
hashCode()
 ↓
внутренний hash
 ↓
индекс бакета
 ↓
поиск ключа внутри бакета
 ↓
value
```

Если бакет содержит только один подходящий элемент — поиск заканчивается быстро.

Если там находится связный список, проверяются элементы списка. Если бакет преобразован в дерево — поиск выполняется по дереву.

Для подтверждения того, что найден именно нужный ключ, используется не только хеш, но и проверка самого ключа, в частности `equals()`.

Поэтому в среднем `get()` и `put()` у хорошо распределённой `HashMap` считаются операциями порядка:

```
O(1)
```

### Capacity и load factor

У `HashMap` есть два важных параметра:

```
capacity
load factor
```

#### Capacity

> **Capacity** — количество бакетов во внутреннем массиве.

Например:

```
capacity = 16
```

означает, что внутренняя таблица рассчитана на 16 бакетов.

Стандартная начальная ёмкость `HashMap` — `16`.

При этом внутренняя таблица создаётся лениво: обычный `new HashMap<>()` не обязан сразу выделять массив из 16 бакетов — фактическое создание происходит при первой необходимости.

#### Load factor

> **Load factor — коэффициент нагрузки**, определяющий, насколько `HashMap` может заполниться до автоматического увеличения внутренней таблицы.

Значение по умолчанию:

```java
0.75
```

Если:

```
capacity = 16
loadFactor = 0.75
```

порог расширения:

```
16 × 0.75 = 12
```

После превышения порога `HashMap` увеличивает внутреннюю таблицу и перераспределяет элементы.

#### Почему нельзя просто сделать load factor очень маленьким?

Например:

```
loadFactor = 0.1
```

Коллекция будет очень рано увеличивать массив. Это уменьшает плотность заполнения, но расходует больше памяти.

#### А почему не поставить `1.0` или ещё больше?

Тогда `HashMap` будет экономнее расходовать память, но в среднем увеличится количество элементов, приходящихся на бакеты, а значит может вырасти число коллизий и стоимость поиска.

Поэтому стандартное значение `0.75` является разумным компромиссом для большинства задач.

#### Важный нюанс

Если:

```
capacity = 16
threshold = 12
```

это **не означает**, что 12 элементов обязательно занимают 12 разных бакетов.

`load factor` связан с **общим количеством записей относительно capacity**, а не с процентом непустых бакетов.

{% hint style="danger" icon="circle-question" %}
В `HashMap` находится 10 элементов, но все они попали в один бакет.

Можно ли сказать, что карта заполнена только на `1 / capacity`, потому что непустой бакет всего один?

Как при этом должен учитываться `size`?
{% endhint %}

***

### Расширение `HashMap`

Когда количество элементов превышает допустимый порог, внутренней таблице становится тесно.

Упрощённо:

```
capacity = 16
        ↓
resize
        ↓
capacity = 32
```

После расширения элементы распределяются по новому массиву.

Это операция дороже обычного `put()`, поэтому если заранее известно, что карта будет хранить очень много записей, можно подобрать подходящую начальную ёмкость.

Для обычного кода вручную рассчитывать её требуется далеко не всегда.

Главное понимать:

```
слишком маленькая capacity
        ↓
много resize

слишком большая capacity
        ↓
лишний расход памяти
```

***

### `null` в `HashMap`

`HashMap` разрешает использовать:

* один `null` в качестве ключа;
* `null` в качестве значений.

Например:

```java
Map<String, Integer> map = new HashMap<>();

map.put(null, 10);
System.out.println(map.get(null)); // 10
```

Если повторно выполнить:

```java
map.put(null, 20);
```

нового ключа не появится:

```java
System.out.println(map.size());    // 1
System.out.println(map.get(null)); // 20
```

Это тот же самый ключ `null`, поэтому значение заменится.

## Контракт `equals()` и `hashCode()`

В главе про `String` мы уже встречали `equals()` и знаем, что этот метод может определять **логическое равенство объектов**.

Например:

```java
String first = new String("Java");
String second = new String("Java");

first == second      // false
first.equals(second) // true
```

Для `HashMap` это особенно важно, потому что ключ нужно не только направить в правильный бакет, но и понять, **является ли найденный объект тем же логическим ключом**.

Для этого `equals()` и `hashCode()` должны работать согласованно.

### Главное правило

> Если два объекта равны по `equals()`, их `hashCode()` обязательно должны быть одинаковыми.

То есть:

```java
a.equals(b) == true
```

обязательно требует:

```java
a.hashCode() == b.hashCode()
```

Обратное неверно.

Если:

```java
a.hashCode() == b.hashCode()
```

объекты вполне могут быть разными:

```java
a.equals(b) == false
```

Это обычная коллизия.

Можно запомнить:

```
equals == true
      ↓ обязательно
одинаковый hashCode
```

Но:

```
одинаковый hashCode
      ↓ НЕ обязательно
equals == true
```

***

### Почему это необходимо `HashMap`?

Представим два логически одинаковых ключа:

```java
UserKey first = new UserKey(10);
UserKey second = new UserKey(10);
```

Пусть:

```java
first.equals(second) // true
```

То есть для нашей программы это **один и тот же пользователь**.

Добавляем:

```java
map.put(first, "Anna");
```

Позже пытаемся найти запись с помощью другого объекта:

```java
map.get(second);
```

Чтобы поиск работал:

```
second.hashCode()
        ↓
тот же бакет, куда положили first
        ↓
first.equals(second)
        ↓
true
        ↓
значение найдено
```

Поэтому равные ключи должны давать одинаковый хеш.

***

### Пример корректной реализации

Допустим, пользователь определяется по `id`.

```java
class UserKey {

    private final long id;

    public UserKey(long id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }

        if (!(obj instanceof UserKey other)) {
            return false;
        }

        return id == other.id;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }
}
```

И `equals()`, и `hashCode()` используют одно и то же логически значимое поле — `id`.

Поэтому:

```java
UserKey first = new UserKey(10);
UserKey second = new UserKey(10);

first.equals(second)                  // true
first.hashCode() == second.hashCode() // true
```

Теперь:

```java
Map<UserKey, String> map = new HashMap<>();
map.put(first, "Anna");

System.out.println(map.get(second)); // Anna
```

работает ожидаемо.

***

### Контракт самого `equals()`

Помимо связи с `hashCode()`, у `equals()` есть собственные правила.

Для ненулевых объектов он должен быть:

* **рефлексивным** — `a.equals(a)` всегда `true`;
* **симметричным** — если `a.equals(b)`, то и `b.equals(a)`;
* **транзитивным** — если `a` равен `b`, а `b` равен `c`, то `a` должен быть равен `c`;
* **стабильным**, пока данные объектов не изменились;
* для любого ненулевого `a`: `a.equals(null)` должен возвращать `false`.

Но для работы с `HashMap` особенно важно запомнить связь:

```
equals() → hashCode()
```

Если переопределяем логическое равенство объектов, обычно требуется согласованно переопределить и `hashCode()`.

***

### Что произойдёт, если нарушить контракт?

Например:

```java
class UserKey {

    private final long id;
    private final int hash;

    public UserKey(long id, int hash) {
        this.id = id;
        this.hash = hash;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof UserKey other)) {
            return false;
        }

        return id == other.id;
    }

    @Override
    public int hashCode() {
        return hash;
    }
}
```

Создадим:

```java
UserKey first = new UserKey(1, 10);
UserKey second = new UserKey(1, 20);
```

По `equals()`:

```java
first.equals(second) // true
```

Но:

```java
first.hashCode()  // 10
second.hashCode() // 20
```

Контракт нарушен.

Теперь:

```java
Map<UserKey, String> map = new HashMap<>();

map.put(first, "Anna");
System.out.println(map.get(second));
```

`HashMap` вычислит другой хеш и может начать поиск **совсем в другом бакете**.

До объекта `first` она даже не дойдёт, поэтому `equals()` между ними может вообще не быть вызван.

И получим отсутствие значения, хотя с точки зрения нашего `equals()` ключи равны.

#### Могут появиться два логически одинаковых ключа

Например:

```java
map.put(first, "Anna");
map.put(second, "Ivan");
```

Если ключи направились в разные бакеты, `HashMap` не обнаружит, что:

```java
first.equals(second) == true
```

и сохранит две записи.

Именно поэтому нарушение контракта может влиять **не только на скорость, но и на корректность программы**.

***

### Почему ключи `HashMap` лучше не изменять?

Даже правильно написанные `equals()` и `hashCode()` могут привести к неожиданному результату, если изменить ключ **после добавления в карту**.

Например:

```java
class UserKey {

    private int id;

    public UserKey(int id) {
        this.id = id;
    }

    public void setId(int id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof UserKey other)) {
            return false;
        }

        return id == other.id;
    }

    @Override
    public int hashCode() {
        return id;
    }
}
```

Создаём:

```java
UserKey key = new UserKey(1);
Map<UserKey, String> map = new HashMap<>();
map.put(key, "Anna");
```

При добавлении:

```
id = 1
 ↓
hash = 1
 ↓
bucket для hash=1
```

Теперь изменим ключ:

```java
key.setId(2);
```

Его текущий `hashCode()` уже другой.

Вызываем:

```java
System.out.println(map.get(key));
```

`HashMap` ищет бакет уже по новому хешу, но запись физически осталась там, куда была помещена раньше.

Поэтому можно получить:

```
null
```

хотя запись никуда не удалялась.

Даже `map.remove(key)` может её не найти.

#### Карта не следит за изменениями ключа

`HashMap` не знает, что внутри объекта изменилось поле, и не переносит ключ автоматически в другой бакет.

Поэтому особенно опасно изменять поля, которые участвуют в `equals()` и `hashCode()`, после помещения объекта в `HashMap`.

***

### Почему `String` хорошо подходит для ключа?

В главе про `String` мы уже видели, что `String` — immutable.

После создания:

```java
String key = "user-1";
```

содержимое объекта изменить нельзя.

Значит, нельзя случайно получить для того же объекта ситуацию:

```
hash при put = один
hash при get = другой
```

Это одна из причин, почему строки очень удобно использовать в качестве ключей:

```java
Map<String, User> users = new HashMap<>();
```

#### Lombok и изменяемые ключи

Ранее мы уже познакомились с Lombok.

Например, `@Data` может сгенерировать в том числе `equals()` и `hashCode()`.

Это удобно, но важно понимать **по каким полям определяется равенство**.

Если объект изменяемый:

```java
@Data
class UserKey {
    private long id;
    private String email;
}
```

и поля, участвующие в сгенерированных `equals()` / `hashCode()`, изменить после помещения объекта в `HashMap`, можно получить ту же проблему с потерянным ключом.

Поэтому автоматическая генерация методов не отменяет необходимости понимать их контракт.

Допустим, `hashCode()` у класса всегда возвращает `0`, но `equals()` реализован совершенно правильно.

Будет ли `HashMap` возвращать неправильные значения?

Или проблема будет в чём-то другом?
{% endhint %}

## `LinkedHashMap`

Обычная `HashMap` **не гарантирует порядок обхода элементов**.

Например:

```java
Map<Integer, String> map = new HashMap<>();

map.put(30, "C");
map.put(10, "A");
map.put(20, "B");
```

Не нужно рассчитывать, что при обходе элементы обязательно будут идти в порядке добавления или по возрастанию ключа.

Если программе важен предсказуемый порядок, существует `LinkedHashMap`.

> **`LinkedHashMap` — это хеш-таблица, которая дополнительно связывает все записи двусвязным списком и благодаря этому поддерживает определённый порядок обхода.**

Она наследуется от `HashMap` и сохраняет её основную идею хеширования.

Дополнительно записи связаны между собой примерно так:

```
A ⇄ B ⇄ C ⇄ D
```

### Порядок вставки

По умолчанию используется **insertion order — порядок вставки**.

```java
Map<Integer, String> map = new LinkedHashMap<>();

map.put(30, "C");
map.put(10, "A");
map.put(20, "B");

System.out.println(map);
```

Получим:

```
{30=C, 10=A, 20=B}
```

Если повторно записать значение существующего ключа:

```java
map.put(10, "NEW");
```

получим:

```
{30=C, 10=NEW, 20=B}
```

Запись не перемещается в конец только потому, что значение было обновлено.

### Порядок доступа

У `LinkedHashMap` есть ещё один режим — **access order**.

Например:

```java
Map<String, Integer> map =
        new LinkedHashMap<>(16, 0.75f, true);

map.put("A", 1);
map.put("B", 2);
map.put("C", 3);
```

Изначально:

```
A → B → C
```

Теперь:

```java
map.get("A");
```

Так как мы только что обратились к `A`, она переместится в конец порядка:

```
B → C → A
```

Такой режим полезен, например, когда нужно отслеживать, какие элементы использовались недавно. Его можно использовать как основу для LRU-кэша, но подробно проектирование кэшей сейчас разбирать не требуется.

### Цена сохранения порядка

`LinkedHashMap` должна хранить дополнительные ссылки между элементами.

Поэтому по сравнению с `HashMap` она обычно требует немного больше памяти и дополнительной работы для поддержания порядка.

При этом основные операции при хорошем хешировании всё ещё остаются близкими к `O(1)`.

***

## `TreeMap`

`TreeMap` решает другую задачу.

> **`TreeMap` хранит записи отсортированными по ключу.**

Например:

```java
Map<Integer, String> map = new TreeMap<>();

map.put(30, "C");
map.put(10, "A");
map.put(20, "B");

System.out.println(map);
```

Получим:

```
{10=A, 20=B, 30=C}
```

Здесь порядок определяется не временем добавления, а **значениями ключей**.

### Как устроен `TreeMap`

`TreeMap` не использует массив бакетов как `HashMap`.

Внутри находится **красно-чёрное дерево**.

Упрощённо:

```
       20
      /  \
    10    30
```

При поиске можно понять:

```
искомый ключ меньше 20
        ↓
идём налево
```

или:

```
искомый ключ больше 20
        ↓
идём направо
```

Поэтому `get()`, `put()` и `remove()` выполняются за:

```
O(log n)
```

### Как `TreeMap` понимает порядок?

Есть два основных варианта:

```
естественный порядок ключей
```

или:

```
переданное правило сравнения
```

Для этого в Java используются `Comparable` и `Comparator`.

Но они идут дальше отдельными вопросами, поэтому подробно разбирать их здесь не будем.

Пока достаточно понимать:

```
HashMap
    ↓
hashCode + equals
    ↓
выбор и поиск в бакете
```

```
TreeMap
    ↓
сравнение ключей
    ↓
движение по дереву
```

Позже отдельно разберём `Comparable`, `Comparator`, особенности равенства при сравнении и то, как по похожему принципу работает `TreeSet`.

***

## Сравнение реализаций

|                      | `HashMap`                             | `LinkedHashMap`                          | `TreeMap`                   |
| -------------------- | ------------------------------------- | ---------------------------------------- | --------------------------- |
| Основная структура   | Хеш-таблица                           | Хеш-таблица + двусвязный список          | Красно-чёрное дерево        |
| Порядок              | Не гарантируется                      | Обычно порядок вставки                   | Сортировка по ключу         |
| Другой режим порядка | —                                     | Можно использовать порядок доступа       | Задаётся правилом сравнения |
| `get()` / `put()`    | В среднем `O(1)`                      | В среднем `O(1)`                         | `O(log n)`                  |
| Что определяет ключ  | `hashCode()` + `equals()`             | `hashCode()` + `equals()`                | Сравнение ключей            |
| Когда использовать   | Нужен быстрый поиск, порядок не важен | Нужен быстрый поиск и стабильный порядок | Нужен порядок по ключу      |

Если нужен просто быстрый поиск по ключу, обычно выбирают `HashMap`.

Если нужен порядок добавления — `LinkedHashMap`.

Если ключи должны находиться в отсортированном порядке — `TreeMap`.

## Задачи

{% hint style="success" icon="star" %}
Что будет выведено?

```java
class Key {

    private final int id;

    Key(int id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return 1;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof Key other)) {
            return false;
        }

        return id == other.id;
    }
}

public class Main {

    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();

        map.put(new Key(1), "A");
        map.put(new Key(2), "B");
        map.put(new Key(1), "C");

        System.out.println(map.size());
        System.out.println(map.get(new Key(1)));
        System.out.println(map.get(new Key(2)));
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ:

```
2
C
B
```

У всех объектов `hashCode() == 1`, поэтому возникает большое количество коллизий.

Но одинаковый хеш **не означает одинаковый ключ**.

Первая запись добавляет ключ с `id = 1`.

Вторая имеет тот же хеш, но `equals()` между ключами возвращает `false`, поэтому сохраняется как второй ключ.

Далее добавляется ещё один объект с `id = 1`. `HashMap` приходит в тот же бакет и находит существующий ключ, для которого `equals() == true`. Поэтому новая запись не добавляется — значение `"A"` заменяется на `"C"`.

Итог:

```
id=1 → C
id=2 → B
```

Проблемой одинакового `hashCode()` становится производительность, а не невозможность хранить разные ключи.

</details>

Но хеши разные:

Получилась невозможная с точки зрения контракта ситуация:


```java
class Key {

    private int id;

    Key(int id) {
        this.id = id;
    }

    void setId(int id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return id;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof Key other)) {
            return false;
        }

        return id == other.id;
    }
}

public class Main {

    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();

        Key key = new Key(1);
        map.put(key, "value");

        key.setId(2);

        System.out.println(map.get(key));
        System.out.println(map.size());

        map.remove(key);
        System.out.println(map.size());
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Получим:

```
null
1
1
```

При `map.put(key, "value")` у ключа `id = 1`, следовательно его `hashCode()` равен `1`. `HashMap` сохраняет запись в бакете, соответствующем этому хешу.

Затем `key.setId(2)` меняет поле, участвующее и в `equals()`, и в `hashCode()`.

При `map.get(key)` карта заново рассчитывает хеш и начинает искать запись уже в другом месте. Поэтому получает `null`, хотя сама запись всё ещё существует и `size()` остаётся равен `1`.

По той же причине `map.remove(key)` не может найти её в ожидаемом бакете, и размер снова остаётся `1`.

Именно поэтому поля ключа, участвующие в `equals()` и `hashCode()`, нежелательно изменять после помещения объекта в хеш-коллекцию.

</details>

Что будет выведено?

```java
public class Main {

    public static void main(String[] args) {
        Map<String, Integer> map =
                new LinkedHashMap<>(16, 0.75f, true);

        map.put("A", 1);
        map.put("B", 2);
        map.put("C", 3);
```

```
{C=3, A=1, B=2}
```

Здесь `new LinkedHashMap<>(16, 0.75f, true)` создаёт `LinkedHashMap` в режиме **access order**.

После вставок порядок:

```

```

После `map.get("A")`:

```
B → C → A
```

После `map.get("B")`:

```
C → A → B
```

Поэтому итоговый вывод:

```
{C=3, A=1, B=2}
```

Если бы использовали обычный `new LinkedHashMap<>()`, порядок оставался бы порядком вставки.

</details>
