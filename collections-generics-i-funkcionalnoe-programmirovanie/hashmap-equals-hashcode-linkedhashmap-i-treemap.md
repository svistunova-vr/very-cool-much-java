# HashMap, equals(), hashCode(), LinkedHashMap и TreeMap

В главе о паттернах мы уже работали с заказом доставки. Продолжим этот сюжет: заказ оформлен, ресторан готовит еду, затем курьер везёт её клиенту. В приложении нужно показывать актуальный статус каждого заказа.

Представим учебный сервис доставки типа Яндекс Еды. Для небольших примеров будем хранить статусы заказов в памяти: по номеру заказа можно узнать, принят он, готовится или уже в пути. Код ниже иллюстрирует работу коллекций и не описывает внутреннее устройство конкретной компании.

```java
Map<Long, String> statuses = new HashMap<>();

statuses.put(10L, "Принят");
statuses.put(20L, "Готовится");

System.out.println(statuses.get(10L)); // Принят
```

Здесь `Long` — тип ключа, а `String` — тип значения. Позже вместо строки со статусом можно будет хранить целый объект заказа. Принцип поиска по ключу от этого не изменится.

Мы уже знаем, что `Map` хранит пары **ключ → значение**. Теперь разберёмся, как `HashMap` находит заказ, если таких пар тысячи, почему важны `equals()` и `hashCode()` и какую реализацию выбрать, когда нужен определённый порядок.

В коротких примерах ниже показан код для `main`. Классы коллекций находятся в пакете `java.util`; в задачах с полным кодом необходимые импорты указаны явно.

## Внутреннее устройство `HashMap`

Если хранить заказы в списке и искать нужный по `id` обычным перебором, в худшем случае придётся проверить все записи. `HashMap` использует **хеш-таблицу**: сначала вычисляет место поиска по ключу и затем проверяет записи только в этом месте.

Внутри находится массив `table`. Его ячейки называют **бакетами** (`bucket`). Ячейка содержит `null`, если бакет пуст, или ссылку на первый узел с записью.

У узла есть четыре существенные для нас части:

| Часть узла | Что хранит                                           |
| ---------- | ---------------------------------------------------- |
| `hash`     | Хеш, вычисленный при добавлении ключа                |
| `key`      | Ключ, например идентификатор заказа                  |
| `value`    | Значение, например статус заказа                     |
| `next`     | Ссылка на следующий узел в этом бакете, если он есть |

**Один бакет может содержать несколько записей.** При этом `size()` считает пары ключ-значение, а не количество занятых ячеек массива.

### Что такое хеш-функция?

Идентификатором заказа может быть строка `"ORDER-10"`. Её нельзя напрямую использовать как индекс массива: индекс должен быть целым числом в пределах длины массива.

> **Хеш-функция** преобразует исходные данные в хеш — числовое значение, которое помогает выбрать место хранения и поиска.

В Java у объектов есть метод `hashCode()`, возвращающий `int`. Но **хеш-код не обязан быть уникальным**: разные объекты могут получить одинаковое число. Возможных строк больше, чем возможных значений `int`.

Важно различать три вещи:

| Понятие           | Назначение                                                    |
| ----------------- | ------------------------------------------------------------- |
| `key.hashCode()`  | Хеш-код, который возвращает сам ключ                          |
| Внутренний `hash` | Результат дополнительного преобразования хеш-кода в `HashMap` |
| Индекс бакета     | Номер ячейки массива, вычисленный с учётом его длины          |

Например, для ненулевого ключа в OpenJDK 17 расчёт выглядит так:

```java
int h = key.hashCode();
int hash = h ^ (h >>> 16);
int index = (table.length - 1) & hash;
```

Это фрагмент внутреннего алгоритма, а не код, который нужно писать при использовании `Map`. Операции `>>>`, `^` и `&` работают с битами числа: дополнительное преобразование смешивает старшие и младшие биты, а последняя строка выбирает индекс в массиве, длина которого — степень двойки.

Для понимания дальнейшего достаточно запомнить: **`hashCode()` помогает вычислить индекс, но сам индексом не является**.

### Как работает `put()`

Вернёмся к статусам заказов:

```java
Map<Long, String> statuses = new HashMap<>();

statuses.put(10L, "Принят");
statuses.put(26L, "Готовится");
statuses.put(30L, "Принят");
```

При обычной начальной таблице из 16 бакетов эти небольшие ключи `Long` распределятся так:

| Индекс бакета | Записи в нём                                |
| ------------- | ------------------------------------------- |
| `10`          | `10L → "Принят"`, затем `26L → "Готовится"` |
| `14`          | `30L → "Принят"`                            |
| Остальные     | Пусто                                       |

У `10L` и `26L` разные хеш-коды, но при такой длине массива получается **один индекс бакета**. `HashMap` должна уметь хранить обе записи.

При вызове `put(key, value)` она:

1. Вычисляет хеш ключа и индекс бакета.
2. Если бакет пуст, помещает туда новый узел.
3. Если записи уже есть, ищет среди них тот же логический ключ: сначала проверяет сохранённый хеш, затем совпадение ссылок или равенство по `equals()`.
4. Если ключ найден, заменяет его значение. Если нет — добавляет отдельный узел.

Теперь обновим статус заказа № 10:

```java
statuses.put(10L, "В пути");

System.out.println(statuses.get(10L)); // В пути
System.out.println(statuses.size());  // 3
```

Четвёртая запись не появилась. Для уже существующего ключа изменилось значение. Например, так можно заменить статус заказа после его передачи курьеру.

### Что такое коллизия?

> **Коллизия хеш-функции** — совпадение хешей у разных исходных данных. При обсуждении хеш-таблицы коллизией также называют попадание разных ключей в один бакет.

Это связанные, но не одинаковые случаи. Одинаковые хеши направляют ключи в один бакет. Однако совпасть может и только индекс: так произошло с `10L` и `26L` в таблице из 16 бакетов.

**Коллизия не означает, что новая запись затрёт предыдущую.** Замена значения происходит, когда найден равный ключ, а не просто совпавший бакет или хеш.

Если `first.hashCode() == second.hashCode()`, но `first.equals(second)` возвращает `false`, это два разных ключа. При корректном контракте оба могут храниться в `HashMap`.

### Связный список внутри бакета

Когда разные ключи попадают в один бакет, их узлы могут быть связаны через поле `next`. В нашем примере узел заказа № 10 ссылается на узел заказа № 26.

Чтобы найти заказ № 26, `HashMap` сначала выбирает бакет `10`, затем проверяет записи внутри него. Перебирать остальные бакеты ей не требуется.

Если в бакете один-два узла, поиск короткий. Но если почти все ключи попали в один длинный список, внутри него снова приходится выполнять много проверок. Например, `hashCode()`, всегда возвращающий `1`, создаёт именно такую проблему.

**Постоянный хеш сам по себе не нарушает контракт. Он ухудшает распределение ключей и производительность.**

### Преобразование списка в дерево в Java 8+

Начиная с Java 8 `HashMap` умеет заменять длинный список в бакете **красно-чёрным деревом** — разновидностью сбалансированного дерева. Балансировка не даёт ему вытянуться в длинную цепочку.

Идея дерева — при поиске выбирать подходящую ветку и отбрасывать часть оставшихся вариантов. Но преобразуется **отдельный бакет**, а не вся `HashMap`. Остальные бакеты могут оставаться пустыми или содержать списки.

В реализации OpenJDK 17 есть два важных порога:

| Константа              | Значение | Что означает                                                  |
| ---------------------- | -------- | ------------------------------------------------------------- |
| `TREEIFY_THRESHOLD`    | `8`      | Порог, участвующий в решении о преобразовании длинного списка |
| `MIN_TREEIFY_CAPACITY` | `64`     | Минимальное количество бакетов для преобразования в дерево    |

При последовательном добавлении разных ключей обычным `put()` в один список проверка на преобразование срабатывает при добавлении **девятого узла**, когда до вставки в списке уже было восемь. Если таблица содержит меньше 64 бакетов, вместо преобразования выполняется её расширение.

Поэтому фраза «появилось восемь элементов — обязательно получилось дерево» неточна. Числа и момент проверки — детали реализации, а не обещание интерфейса `Map`.

Дерево помогает ускорять поиск, но не делает любой плохой `hashCode()` безвредным. Если хеши совпали и по самим ключам нельзя выбрать единственную ветку, поиск может потребовать проверки нескольких ветвей. **Безусловно обещать `O(log n)` для любого поиска в бакете-дереве нельзя.** В документации отдельно отмечено, что порядок сравнения ключей может помогать разрешать совпадения хешей. [Документация `HashMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html).

### Как работает `get()`

Вызов `statuses.get(26L)` повторяет начало алгоритма вставки: вычисляет хеш, выбирает бакет и ищет в нём равный ключ. Если ключ найден, возвращается значение. Если нет — `null`.

Проверка хеша идёт **до** проверки равенства ключей. Поэтому `equals()` не обязательно вызывается для каждого узла выбранного бакета. Если ссылки совпали, дополнительный вызов `equals()` тоже не нужен.

При хорошем распределении ключей основные операции `get()` и `put()` в среднем близки к `O(1)`: объём поиска не растёт пропорционально общему числу заказов. Для `put()` здесь усредняется также стоимость редких расширений таблицы. Само расширение дороже обычной вставки.

## Capacity, load factor и расширение

**Capacity** — количество бакетов во внутреннем массиве. **Size** — количество сохранённых пар. Это разные величины: в одном бакете может лежать несколько записей, а часть бакетов может быть пустой.

Обычный `new HashMap<>()` использует начальную ёмкость 16 и коэффициент нагрузки 0.75. В OpenJDK массив создаётся лениво — при первой вставке.

> **Load factor — коэффициент нагрузки**, который используется для расчёта порога расширения таблицы по количеству записей.

Для таблицы из 16 бакетов с коэффициентом 0.75 порог равен `16 × 0.75 = 12`. При добавлении тринадцатого **нового ключа** этот порог будет превышен. Обычное расширение увеличит ёмкость до 32 и перераспределит записи.

Обновление статуса существующего заказа не увеличивает `size()`, поэтому само по себе не пересекает этот порог. При большом числе коллизий расширение может произойти и раньше — по правилу, разобранному в разделе о деревьях.

{% hint style="info" %}
`0.75` не означает «заняты 75% бакетов». Для порога учитывается **общее количество записей**. Десять узлов в одном бакете дают `size() == 10`, а не `1`.
{% endhint %}

Меньший коэффициент нагрузки заставляет раньше расширять таблицу: плотность записей ниже, но памяти на массив нужно больше. Больший коэффициент экономит место под массив, однако обычно увеличивает число записей в бакетах и стоимость поиска. Значение 0.75 выбрано как компромисс. [Параметры `HashMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html).

Во время расширения OpenJDK использует сохранённые в узлах хеши для выбора новых бакетов. **Расширение не является повторной проверкой логического равенства всех ключей и не исправляет изменённый ключ.**

Если заранее известно, что хранилище будет большим, подходящая начальная ёмкость уменьшит число расширений. Но чрезмерный запас тоже имеет цену: расход памяти и обход большой таблицы. Обычно начинать стоит со стандартных настроек, понимая причину возможных затрат.

### `null` в `HashMap`

`HashMap` допускает один ключ `null` и значения `null`. Повторный `put(null, ...)` заменит значение у того же ключа.

В сервисе доставки мы можем отдельно установить правило «у заказа обязательно есть `id`». **Допустимость значения для коллекции не заменяет бизнес-проверку.**

Есть и практическая тонкость: `get()` возвращает `null` как для отсутствующего ключа, так и для явно сохранённого значения `null`.

```java
Map<Long, String> statuses = new HashMap<>();

statuses.put(10L, null);

System.out.println(statuses.get(10L));         // null
System.out.println(statuses.get(99L));         // null
System.out.println(statuses.containsKey(10L)); // true
System.out.println(statuses.containsKey(99L)); // false
```

Метод `containsKey()` позволяет отличить эти случаи.

## Контракт `equals()` и `hashCode()`

В главе про `String` мы уже различали совпадение ссылок и равенство содержимого. Для ключей это означает: два отдельных объекта могут представлять **один и тот же заказ**.

Допустим, нам понадобился собственный тип идентификатора `OrderKey`. Будем считать два ключа равными, если у них одинаковый `id`.

### Главное правило

> **Если `a.equals(b)` возвращает `true`, то `a.hashCode()` и `b.hashCode()` обязаны совпадать. Обратное не требуется.**

Кроме того, повторные вызовы `hashCode()` в рамках одного запуска должны давать одинаковый результат, пока не изменились данные, используемые в `equals()`. Между разными запусками одинаковое значение для произвольного объекта не гарантируется. [Контракт `Object.hashCode()`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Object.html#hashCode\(\)).

Почему это нужно? `HashMap` сначала выбирает бакет и проверяет хеш. Если два логически равных ключа дают разные хеши, поиск может закончиться ещё **до сравнения через `equals()`**.

### Корректный ключ заказа

```java
final class OrderKey {

    private final long id;

    OrderKey(long id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }
        if (!(obj instanceof OrderKey)) {
            return false;
        }

        OrderKey other = (OrderKey) obj;
        return id == other.id;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }
}
```

Проверка `instanceof` убеждается, что перед нами `OrderKey`; после неё приведение `(OrderKey) obj` позволяет обратиться к полю `id`. Для `null` проверка `instanceof` вернёт `false`.

В обоих методах используется одно и то же поле `id`. `Long.hashCode(id)` вычисляет хеш для значения `long`. Класс сделан `final`, поэтому в этом примере не приходится учитывать наследников со своим определением равенства.

```java
OrderKey first = new OrderKey(10L);
OrderKey second = new OrderKey(10L);

System.out.println(first == second);                         // false
System.out.println(first.equals(second));                    // true
System.out.println(first.hashCode() == second.hashCode());   // true

Map<OrderKey, String> statuses = new HashMap<>();
statuses.put(first, "Принят");

System.out.println(statuses.get(second)); // Принят
```

При поиске мы передали **другой объект**, но он представляет тот же логический ключ. Поэтому запись найдена.

### Контракт самого `equals()`

Для ненулевых объектов `equals()` должен соблюдать следующие правила:

| Правило                           | Смысл                                                                  |
| --------------------------------- | ---------------------------------------------------------------------- |
| Рефлексивность                    | `a.equals(a)` возвращает `true`                                        |
| Симметричность                    | `a.equals(b)` и `b.equals(a)` дают одинаковый ответ                    |
| Транзитивность                    | Если `a` равен `b`, а `b` равен `c`, то `a` равен `c`                  |
| Согласованность повторных вызовов | Пока участвующие в сравнении данные не меняются, результат не меняется |
| Сравнение с `null`                | `a.equals(null)` возвращает `false`                                    |

Переопределяя `equals()`, нужно обеспечить согласованный с ним `hashCode()`. Просто сгенерировать один метод и оставить другой без внимания недостаточно. [Контракт `Object.equals()`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Object.html#equals\(java.lang.Object\)).

### Что произойдёт при нарушении контракта?

Представим ошибочную версию `OrderKey`: `equals()` сравнивает `id`, а `hashCode()` возвращает отдельное поле `hash`, переданное в конструктор. Полный пример есть во второй задаче.

У двух ключей одинаковый `id = 10`, но хеши равны `10` и `26`. После сохранения статуса с первым ключом поиск по второму может не найти запись.

Причём **даже совпадение бакета не спасает**. В массиве из 16 бакетов оба хеша дадут индекс `10`, но сохранённые хеши узлов различаются. `HashMap` отсеет запись до вызова `equals()`.

Если затем добавить второй ключ, вместо обновления может появиться ещё одна запись с логически тем же `id`. В сервисе доставки это превращается в практическую ошибку: статус заказа не найден или обновился не там, где ожидалось.

Различайте две ситуации:

| Реализация ключа                                       | Последствие                                                                       |
| ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| У разных ключей одинаковый хеш, а `equals()` корректен | Ключи различаются правильно, но поиск может замедлиться                           |
| У равных по `equals()` ключей разные хеши              | Нарушен контракт: нельзя полагаться на корректность поиска, обновления и удаления |

### Почему опасно изменять ключ?

Даже согласованные методы не спасут, если после вставки изменить данные ключа, которые участвуют в равенстве.

Допустим, у другой, **изменяемой версии** `OrderKey` есть `setId()`, а `hashCode()` вычисляется из `id`:

```java
OrderKey key = new OrderKey(10L);
Map<OrderKey, String> statuses = new HashMap<>();

statuses.put(key, "Принят");
key.setId(26L);
```

При вставке узел сохранил старый хеш. После изменения `get(key)` вычислит новый. Даже если индекс бакета совпадёт, сохранённый хеш уже не совпадает с текущим.

**`HashMap` не следит за изменениями полей ключа и не перестраивает запись автоматически.** Поиск и удаление могут перестать находить её, хотя `size()` по-прежнему учитывает узел. Полный код и результат для OpenJDK 17 разобраны в третьей задаче.

По контракту `Map` поведение не определено, если ключ меняется так, что это влияет на сравнение через `equals()`. Поэтому конкретный результат примера не нужно превращать в универсальную гарантию для всех реализаций. [Требования к ключам `Map`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Map.html).

Для поиска статуса заказа проще использовать стабильный идентификатор: `Long`, `String` или собственный неизменяемый `OrderKey`. **Статус заказа может меняться, а идентификатор, по которому мы его ищем, должен оставаться прежним.**

### `String`, `final` и Lombok

Строка неизменяема: содержимое объекта `"ORDER-10"` нельзя отредактировать. Поэтому ключ не изменится незаметно для карты. Если присвоить переменной другую строку, это будет смена ссылки в переменной, а не изменение уже сохранённого ключа.

Само слово `final` у переменной такого свойства не даёт: оно запрещает менять ссылку, но не поля объекта по этой ссылке.

Lombok тоже не выбирает правильный ключ за нас. Например:

```java
@Data
final class OrderKey {
    private long id;
    private String status;
}
```

В таком классе `@Data` по умолчанию сгенерирует методы равенства с участием обоих полей и сеттеры. [Документация Lombok](https://projectlombok.org/features/Data). Если изменить `status` после помещения ключа в `HashMap`, возникнет проблема изменяемого ключа.

Для поиска заказа по `id` статус вообще не должен определять равенство ключей. Мы уже решили эту задачу в неизменяемом `OrderKey` выше: у него только стабильный `id`, согласованные методы и нет сеттеров.

{% hint style="danger" icon="circle-question" %}
В карте `Map<Long, Order>` изменился статус объекта `Order`, который лежит в значении. Может ли это само по себе сломать поиск заказа по `Long`-ключу?

Что изменится, если использовать объект заказа как ключ и включить его статус в `equals()` и `hashCode()`?
{% endhint %}

<details>

<summary>Разбор</summary>

В первом случае поиск по ключу не ломается: для выбора бакета используются `hashCode()` и `equals()` ключа `Long`, а не значения `Order`.

Во втором меняются данные, по которым карта ищет ключ. Сохранённый при вставке хеш может перестать соответствовать текущему состоянию объекта, и запись станет недоступна через обычный поиск.

Это ещё одна причина отделять стабильный идентификатор заказа от его изменяемого состояния.

</details>

## `LinkedHashMap`: сохраняем порядок

Предположим, оператору доставки нужно видеть заказы в том порядке, в котором они были добавлены в список на экране.

Обычная `HashMap` **не гарантирует порядок обхода**. Даже если на небольшом наборе числа случайно выводятся по возрастанию, это не обещание сортировки.

> **`LinkedHashMap` — хеш-таблица, записи которой дополнительно связаны общим двусвязным списком для поддержания порядка обхода.**

Здесь важно не перепутать два вида связей: список внутри бакета `HashMap` нужен для обработки коллизий, а общий список `LinkedHashMap` проходит **через все записи**, даже если они находятся в разных бакетах.

### Порядок вставки

По умолчанию `LinkedHashMap` сохраняет порядок добавления ключей:

```java
Map<Long, String> statuses = new LinkedHashMap<>();

statuses.put(30L, "Принят");
statuses.put(10L, "Готовится");
statuses.put(20L, "Принят");

System.out.println(statuses);
// {30=Принят, 10=Готовится, 20=Принят}

statuses.put(10L, "В пути");

System.out.println(statuses);
// {30=Принят, 10=В пути, 20=Принят}
```

Обновление значения через `put()` не переместило существующий заказ в конец. Если же удалить ключ и добавить заново, это будет новая вставка — запись окажется в конце.

Порядок добавления в карту не обязательно совпадает с датой создания заказа. Например, если загрузить старые заказы в другом порядке, `LinkedHashMap` сохранит именно порядок загрузки.

### Порядок доступа

Другой режим — **access order**, порядок последних обращений. Его включает третий аргумент `true`:

```java
Map<Long, String> recentlyViewed =
        new LinkedHashMap<>(16, 0.75f, true);

recentlyViewed.put(30L, "Принят");
recentlyViewed.put(10L, "Готовится");
recentlyViewed.put(20L, "Принят");

recentlyViewed.get(30L);

System.out.println(recentlyViewed);
// {10=Готовится, 20=Принят, 30=Принят}
```

Первые два аргумента — начальная ёмкость и коэффициент нагрузки; суффикс `f` обозначает число типа `float`. При успешном `get(30L)` запись № 30 переместилась в конец: к ней обратились последней. `put()` существующего ключа в этом режиме тоже считается обращением.

Так можно отслеживать недавно просмотренные заказы: в начале будут те, к которым дольше всего не обращались. Это основа **LRU-кэша** — хранилища, из которого при нехватке места удаляют давно не использованные записи. Но сам режим `accessOrder = true` **не устанавливает ограничение размера и ничего автоматически не удаляет**.

Порядок поддерживается за счёт дополнительных ссылок и их обновления. Поэтому требуется больше памяти, чем у обычной `HashMap`; основные операции при хорошем хешировании сохраняют среднюю сложность `O(1)`. Правила вставки и доступа описаны в [документации `LinkedHashMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html).

***

## `TreeMap`: сортируем по ключу

Теперь другое требование: заказы должны выводиться **по возрастанию идентификатора**, независимо от порядка добавления.

```java
Map<Long, String> statuses = new TreeMap<>();

statuses.put(30L, "Принят");
statuses.put(10L, "Готовится");
statuses.put(20L, "Принят");

System.out.println(statuses);
// {10=Готовится, 20=Принят, 30=Принят}
```

> **`TreeMap` хранит записи в красно-чёрном дереве и поддерживает сортировку по ключам.**

При поиске числового ключа дерево сравнивает его с ключом текущего узла: меньший ищет в левой ветви, больший — в правой. Балансировка поддерживает небольшую высоту дерева. Операции `get()`, `put()` и `remove()` имеют сложность `O(log n)`.

Порядок задаётся естественным сравнением ключей или переданным `Comparator`. Для `Long` естественный порядок — числовой; собственные правила сравнения через `Comparable` и `Comparator` разберём в следующих вопросах модуля.

**Результат сравнения `0` означает для `TreeMap` один и тот же ключ.** Она не использует хеширование для поиска. Подробности согласования сравнения с `equals()` также идут дальше. [Документация `TreeMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/TreeMap.html).

Есть важное ограничение: `TreeMap<Long, Order>` упорядочивает заказы **по `Long`-ключу**. Она не начнёт автоматически сортировать их по статусу или времени доставки, которые хранятся внутри значения. Способы задавать другие правила сортировки разберём отдельно.

***

## Сравнение реализаций

|                            | `HashMap`                                        | `LinkedHashMap`                                              | `TreeMap`                         |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------ | --------------------------------- |
| Основная структура         | Массив бакетов; в бакетах списки или деревья     | Хеш-таблица и общий двусвязный список записей                | Красно-чёрное дерево              |
| Порядок обхода             | Не гарантируется                                 | По умолчанию порядок вставки; можно включить порядок доступа | Порядок сравнения ключей          |
| Основные операции          | В среднем `O(1)` при хорошем распределении хешей | В среднем `O(1)` при хорошем распределении хешей             | `O(log n)`                        |
| Как находится ключ         | По хешу и равенству ключей                       | По хешу и равенству ключей                                   | По результату сравнения ключей    |
| Пример из сервиса доставки | Найти статус заказа по `id`                      | Обойти заказы в порядке добавления или последнего обращения  | Обойти заказы по возрастанию `id` |

Дерево в отдельном бакете `HashMap` **не превращает её в `TreeMap` и не добавляет сортировку всех ключей**.

Выбор зависит от требования: быстрый поиск статуса без обещаний порядка — `HashMap`; порядок добавления заказов — `LinkedHashMap`; порядок номеров заказов — `TreeMap`.

## Задачи

Ниже — учебные задачи, переработанные для примера с заказами доставки. Каждую нужно запускать отдельно: одноимённые классы в разных задачах показывают разные варианты реализации.

В задачах 2 и 3 намеренно нарушены требования к ключам. Указанный вывод относится к разобранной реализации OpenJDK 17; это демонстрация причины ошибки, а не гарантия корректного использования `Map`.

### 1. Несколько заказов с одинаковым хешем

{% hint style="success" icon="star" %}
Что будет выведено? Сколько разных заказов останется в карте?

```java
import java.util.HashMap;
import java.util.Map;

final class OrderKey {
    private final long id;

    OrderKey(long id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return 1;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof OrderKey)) {
            return false;
        }
        OrderKey other = (OrderKey) obj;
        return id == other.id;
    }
}

public class Main {
    public static void main(String[] args) {
        Map<OrderKey, String> statuses = new HashMap<>();

        statuses.put(new OrderKey(10L), "Принят");
        statuses.put(new OrderKey(20L), "Готовится");
        statuses.put(new OrderKey(10L), "В пути");

        System.out.println(statuses.size());
        System.out.println(statuses.get(new OrderKey(10L)));
        System.out.println(statuses.get(new OrderKey(20L)));
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ:

```
2
В пути
Готовится
```

По шагам:

1. Первая вставка создаёт запись для `id = 10`.
2. У ключа `id = 20` тот же хеш, но `equals()` возвращает `false`. Поэтому создаётся второй узел в том же бакете.
3. Третий объект имеет `id = 10`. Его хеш совпадает с сохранённым, а `equals()` находит равный ключ. Значение `"Принят"` заменяется на `"В пути"`.
4. Поиски с новыми объектами `OrderKey` работают: они равны уже сохранённым ключам по `id`.

Постоянный хеш не нарушил корректность результата. Проблема проявится в стоимости поиска при росте числа ключей.

</details>

### 2. Равные ключи с разными хешами

{% hint style="success" icon="star" %}
Что будет выведено в OpenJDK 17? Почему попадание ключей в один бакет не исправляет ошибку?

```java
import java.util.HashMap;
import java.util.Map;

final class OrderKey {
    private final long id;
    private final int hash;

    OrderKey(long id, int hash) {
        this.id = id;
        this.hash = hash;
    }

    @Override
    public int hashCode() {
        return hash;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof OrderKey)) {
            return false;
        }
        OrderKey other = (OrderKey) obj;
        return id == other.id;
    }
}

public class Main {
    public static void main(String[] args) {
        OrderKey first = new OrderKey(10L, 10);
        OrderKey second = new OrderKey(10L, 26);
        Map<OrderKey, String> statuses = new HashMap<>();

        System.out.println(first.equals(second));

        statuses.put(first, "Принят");
        System.out.println(statuses.get(second));

        statuses.put(second, "В пути");
        System.out.println(statuses.size());
        System.out.println(statuses.get(first));
        System.out.println(statuses.get(second));
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ для OpenJDK 17:

```
true
null
2
Принят
В пути
```

По шагам:

1. `equals()` сравнивает только `id`, поэтому два ключа равны.
2. При первой вставке сохраняется узел с хешем `10`.
3. Поиск по `second` вычисляет хеш `26`. В таблице из 16 бакетов оба хеша дают индекс `10`, однако **сравнение сохранённого хеша с искомым не проходит**. До проверки равенства ключей дело не доходит.
4. По той же причине второй `put()` создаёт отдельный узел.
5. Каждый из последующих поисков находит запись со своим хешем. Вместо одного обновлённого статуса получилось два разных значения для логически одного заказа.

Исправление: вычислять хеш согласованно с равенством, например через `Long.hashCode(id)`, как в основной части главы.

</details>

### 3. Ключ изменился после сохранения

{% hint style="success" icon="star" %}
Что будет выведено в OpenJDK 17? Почему передача того же объекта в `get()` не помогает?

```java
import java.util.HashMap;
import java.util.Map;

final class OrderKey {
    private long id;

    OrderKey(long id) {
        this.id = id;
    }

    void setId(long id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof OrderKey)) {
            return false;
        }
        OrderKey other = (OrderKey) obj;
        return id == other.id;
    }
}

public class Main {
    public static void main(String[] args) {
        OrderKey key = new OrderKey(10L);
        Map<OrderKey, String> statuses = new HashMap<>();

        statuses.put(key, "Принят");
        key.setId(26L);

        System.out.println(statuses.get(key));
        System.out.println(statuses.size());

        statuses.remove(key);
        System.out.println(statuses.size());
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ для OpenJDK 17:

```
null
1
1
```

По шагам:

1. При вставке у ключа `id = 10`; узел запоминает хеш `10`.
2. Сеттер меняет поле в том же объекте. Теперь его `hashCode()` возвращает `26`, но хеш внутри узла остаётся старым.
3. `get(key)` приходит в тот же бакет, однако отбрасывает запись из-за несовпадения хешей. Совпадение ссылок проверяется после хеша и не спасает поиск.
4. Узел не был удалён, поэтому `size()` равен `1`.
5. `remove(key)` также не находит подходящую запись, и размер остаётся прежним.

Проблема не обязательно в другом бакете: в этом примере индекс как раз совпал. Ошибка в том, что ключ изменился, а сохранённые сведения о нём — нет.

Исправление: сделать идентификатор неизменяемым. Если бизнес-операция действительно требует заменить ключ, удалить запись по **старому корректному ключу до его изменения**, а затем добавить её с новым. Для уже испорченной карты обычный `remove(key)` может быть бесполезен.

</details>

### 4. Одинаковое содержимое массивов

{% hint style="success" icon="star" %}
Предположим, код заказа пришёл в виде массива байтов. Что будет выведено?

```java
import java.util.HashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        byte[] first = {1, 2, 3};
        byte[] second = {1, 2, 3};

        Map<byte[], String> statuses = new HashMap<>();
        statuses.put(first, "Готовится");

        System.out.println(statuses.get(first));
        System.out.println(statuses.get(second));
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ:

```
Готовится
null
```

По шагам:

1. `first` и `second` содержат одинаковые числа, но это разные объекты.
2. Массивы не переопределяют `equals()` для сравнения содержимого: для них равенство определяется совпадением ссылок.
3. Первый поиск передаёт сохранённый объект и находит запись.
4. Второй поиск передаёт другой массив. Даже если бы его хеш случайно совпал, равенство ключей не подтвердилось бы.

Здесь контракт не нарушен — выбранная логика равенства просто не соответствует задаче.

Если код заказа текстовый, удобнее использовать строковый ключ. Если важен именно набор байтов, нужен отдельный тип ключа с согласованными `equals()` и `hashCode()` по содержимому и защитой этого содержимого от изменений.

### 5. Порядок обращений к заказам

{% hint style="success" icon="star" %}
Что будет выведено? Как изменится ответ, если заменить создание карты на `new LinkedHashMap<>()`?

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        Map<Long, String> statuses =
                new LinkedHashMap<>(16, 0.75f, true);

        statuses.put(30L, "Принят");
        statuses.put(10L, "Готовится");
        statuses.put(20L, "Принят");

        statuses.get(30L);
        statuses.put(10L, "В пути");

        System.out.println(statuses);
    }
}
```
{% endhint %}

<details>

<summary>Решение</summary>

Ответ:

```
{20=Принят, 30=Принят, 10=В пути}
```

По шагам:

| Действие             | Порядок ключей от начала к концу |
| -------------------- | -------------------------------- |
| Три вставки          | `30`, `10`, `20`                 |
| `get(30L)`           | `10`, `20`, `30`                 |
| `put(10L, "В пути")` | `20`, `30`, `10`                 |

В режиме доступа существующая запись перемещается в конец и при успешном `get()`, и при `put()`. Значение заказа № 10 обновляется, а новая запись не создаётся.

При обычном `new LinkedHashMap<>()` сохранится порядок вставки:


### Пункт 9

{% hint style="success" %}
**Опишите устройство `HashMap`.**

`HashMap` — реализация `Map` на основе хеш-таблицы. Внутри находится массив бакетов, а записи хранят ключ, значение, вычисленный хеш и связи с другими узлами. Порядок обхода не гарантируется.
{% endhint %}

{% hint style="success" %}
**Что такое хэш-функция?**

Хеш-функция преобразует исходные данные в числовой хеш. У объектов Java для этого есть `hashCode()`, возвращающий `int`. `HashMap` дополнительно преобразует этот хеш-код и с учётом длины массива получает индекс бакета. Хеш-код не равен индексу и не обязан быть уникальным: разные ключи могут иметь одинаковый хеш.
{% endhint %}

{% hint style="success" %}
**Что такое коллизия?**

Коллизия хеш-функции — совпадение хешей у разных данных. Для хеш-таблицы коллизией также называют попадание разных ключей в один бакет; это возможно и при разных хешах. Например, ключи `10L` и `26L` в разобранной таблице из 16 бакетов имеют один индекс. Коллизия допустима: разные по `equals()` ключи должны храниться отдельно.
{% endhint %}

{% hint style="success" %}
**Как `HashMap` работает с коллизиями (связные списки, преобразование в деревья в Java 8+)?**

В одном бакете может храниться несколько узлов, связанных в список. Для поиска проверяются записи внутри выбранного бакета. Начиная с Java 8 длинный список может преобразоваться в красно-чёрное дерево. В OpenJDK 17 используются `TREEIFY_THRESHOLD = 8` и минимальная ёмкость 64 бакета; при обычных вставках в список проверка срабатывает на девятом узле. Если таблица меньше 64, сначала выполняется расширение. Дерево создаётся только внутри бакета и не сортирует всю карту; оно также не отменяет необходимости хорошего хеширования.
{% endhint %}

{% hint style="success" %}
**Что такое коэффициент нагрузки (load factor)?**

Это параметр для расчёта порога расширения хеш-таблицы по числу записей. По умолчанию он равен 0.75: при ёмкости 16 обычный порог равен 12, и тринадцатый новый ключ приводит к его превышению. Учитывается количество пар, а не доля занятых бакетов. Меньший коэффициент требует больше памяти под таблицу, больший обычно увеличивает плотность записей и стоимость поиска. При большом числе коллизий таблица может расшириться раньше по отдельному правилу.
{% endhint %}

### Пункт 10

{% hint style="success" %}
**Какой контракт между методами `equals()` и `hashCode()`?**

Если два объекта равны по `equals()`, их хеш-коды обязаны совпадать. Одинаковые хеш-коды не требуют равенства объектов. В рамках одного запуска хеш должен быть постоянным, пока не меняются данные, участвующие в `equals()`. Сам `equals()` должен быть рефлексивным, симметричным, транзитивным, давать стабильный результат при неизменных данных и возвращать `false` при сравнении ненулевого объекта с `null`. В нашем `OrderKey` равенство определяется по стабильному `id`, и хеш вычисляется согласованно с ним.
{% endhint %}

{% hint style="success" %}
**К каким последствиям может привести его нарушение при использовании объектов в качестве ключей в `HashMap`?**

Если равные ключи дают разные хеши, `get()` и `remove()` могут не найти сохранённую запись, а `put()` — создать отдельную запись вместо обновления. Даже попадание в один бакет не спасает: карта проверяет сохранённый хеш до равенства ключей. Изменение участвующих в равенстве полей ключа после вставки тоже делает работу ненадёжной: карта не обновляет сохранённый хеш автоматически. Поэтому ключ должен иметь согласованные методы и стабильное состояние. Одинаковый хеш у разных ключей при корректном `equals()` — другая ситуация: он ухудшает производительность, но сам по себе не нарушает контракт.
{% endhint %}

### Пункт 11

{% hint style="success" %}
**В чем заключаются особенности `LinkedHashMap` и `TreeMap`?**

`LinkedHashMap` сочетает хеш-таблицу с общим двусвязным списком записей. По умолчанию она сохраняет порядок вставки, а при включённом режиме доступа — порядок последних обращений. Например, можно сохранять порядок добавления заказов или отслеживать недавно просмотренные. За поддержание порядка приходится платить дополнительными ссылками и их обновлением.

`TreeMap` основана на красно-чёрном дереве и упорядочивает записи по ключам: по их естественному порядку или заданному `Comparator`. Она использует сравнение, а не хеширование; сравнение с результатом `0` означает один ключ. Её основные операции имеют сложность `O(log n)`, тогда как у `LinkedHashMap` при хорошем хешировании — в среднем `O(1)`. В нашем примере `TreeMap` подходит для обхода заказов по возрастанию `id`, но не сортирует автоматически по полям значения.
{% endhint %}
